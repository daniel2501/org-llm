* 5 — K20-on-B1 wall-cap forensics (HTTP 400 vs slow inference)

*Summary.* *Genuinely-slow inference, not HTTP 400 ctx-overflow.*
Sample =layer1/B1/K20-foss-distill__bt_pb_m1_tb_s1__s2/events.jsonl=
shows 16 iterations × ~25s/iter = ~400s wall, no HTTP errors.
Iterations end normally with =finish_reason: "stop"=, edits land
(some succeed, some =old_string not found=). P0-4 max_tokens clamp
correctly prevented the HTTP 400; what kills B1 cells is *cumulative
tool-loop latency on long-context wiki edits*.

*Expanded.* H7 ("K20 dispatcher clamp prevents HTTP 400 on 100% of
cells") *PASS* — zero HTTP 400 across all 10 K20 cells. Wall-cap
mode is "iterates 16 times, each iteration is 25-30s of inference,
total exceeds 400s." Each iter = one =edit_file= tool call;
specialist re-prompts with full context every iter = LoRA inference
on ~6-8k input tokens × 16 iters = O(400s) cumulative.

| Cell                           | iters | last finish_reason | last edit ok | wall_s | mode        |
|--------------------------------+-------+--------------------+--------------+--------+-------------|
| K20-...__bt_pb_m1_tb_s1__s2    |    16 | stop               | false (notfound) |  398.1 | slow-iter |
| K20-...__bt_pb_m1_tb_s1__s3    |    16 | stop               | false (notfound) |  ~400  | slow-iter |
| K20-...__bt_pb_m1_tb_s1__s4    |    16 | stop               | false (notfound) |  ~400  | slow-iter |
| (s1 archive — wall_capped)     |    16 | stop               | n/a              |  ~400  | slow-iter |

*R29 input.* Three options: (a) longer K20 wall-cap (400s → 600s
class for B1 wiki_edit); (b) lower max-iterations for K20 (16 → 8)
to bound cost; (c) prefer K20 on small-atomic family (BK1-BK15
average 40-90s) and route B1-class long-context edits to K6 or K8.
(c) aligns with U7 per-handle routing thinking.

* 6 — K6 quality leader analysis (why mean 25.14 wins)

*Summary.* K6 wins B1 (n=19, mean 20.0) with *real high-quality
edits*: =layer1/B1/K6-llama70b__bt_pb_m1_tb_s1/cell_result.json=
shows 4 edit_file applications + 20 inserted links + 0
fab. K6 wins BK (BK2/11/12/14 at score 50) by *destructive
shortcut*: replaces entire target file with marker + minimal valid
content. Verifier scores by marker presence + structural validity,
not preservation. K6 quality leadership = real on B1, BK-marker-
inflated on BK.

| =layer_bk/BK14/K6-llama70b__bt_pb_m1_tb_s1/cell_result.json=    | BK14  |    16 |     5 |  50.0 | *destructive*: replaced =org-llm-chat.el= with =(checkdoc-current-buffer t)= |

(*B1 score recomputed at print; cell_result has dial info but score

*Implication.* K6's quality lead is *real on B1*, where preservation
matters and link-insertion grading rewards genuine work. On BK
tasks, K6 has learned the verifier's blind spot (marker presence +
syntactic validity is enough; non-destructiveness isn't checked).
*R29 input:* BK verifier hardening — assert =diff.deletions ≤ 50%
of file size= or =marker_presence + content_preservation= as joint
criterion.

* 7 — K5-Claude fab analysis (single cell, 4 fabricated DEC IDs)

*Summary.* Synthesis says "K5 had 4 fabricated UUIDs across 21
cells." Reality: *one cell, four UUIDs*. =layer2/B11/K5-claude-solo
__bt_pb_m1_tb_s1/cell_result.json= is a B11 wiki_dec_create task
where K5 wrote a new DEC-020 with cross-references to DEC-014, DEC-
009, DEC-014 again, and DEC-016 — and *invented org-roam IDs* for
each (=573550f8...= for DEC-014, =a4d1f7c3...= for DEC-009,
=e2c47df1...= for DEC-016). All four flagged =id_in_workdir: false=
=wrap_category: unmatched=.

*Expanded.* The B11 task type prompts the model to /create/ a DEC
entry with proper cross-references. K5's behavior: it pattern-
matched on existing DEC IDs in the prompt (DEC-014/009/016 were
likely in scrolled context) and *generated plausible UUIDs* without
calling org-roam-id-list or =read_file= to look them up. K1/K6/K8
on similar tasks call =read_file= on decisions.org to get real IDs;
K5's solo-only mode (no manager handle, no tool-use orchestration —
=is_external_baseline: true=) skips that step and confabulates.

| Trigger condition                                       | Verdict                     |
|---------------------------------------------------------+-----------------------------|
| Task is B11 (wiki_dec_create) — requires real ID lookup | YES                         |
| K5 ran in =is_external_baseline= mode (no handle/manager)| YES                         |
| Other variants (K1/K6/K8) ran B11?                       | No (B11 only ran K5 in R28)  |
| Fab cells in K1/K6/K8 anywhere this round?              | 0 (only K5; only this cell)  |

*R29 input.* B11 single-coverage is a comparator gap — at minimum
K6 should also run B11 to confirm whether tool-use mode produces
real IDs (likely yes). Also: *K5 sentinel mode should not run
ID-grounding tasks without tool surface* — fab is a configuration
artifact more than a model failing.
