* What this page is

The single source of truth for *how org-llm is shaped*: the
layers, the data plane, the control plane, the seams between
them, and which file owns which concern.

This is the *map*. Every section links to the focused wiki page
that owns the deep dive — embeddings, MCP, the LLM proxy,
recipes, walk, etc. Read this page when you want the whole
picture in one screen; follow the links when you want detail.

The README's =## Architecture= section is the 60-second pitch
(one ASCII diagram). This page is the next layer down.

** Intended audience

org-llm is in solo development today (n=1) but its eventual
distribution is FOSS-for-everyone. This page is written for:

1. *The current developer* — fast lookup for "where does X
   live, why is it shaped this way?"
2. *Future contributors* — context to make load-bearing
   changes safely (the design rules + invariants exist for
   reasons; the page documents the reasons).
3. *Curious users tracing how a feature works* — agents may
   surface this page in =org-llm ask= responses about the app
   itself; it should read coherently to a stranger.

A consequence of audience 2+3: design decisions on this page
default to the *FOSS bar* — what's defensible for unknown
users running on unknown vaults, not just what works on the
dev's box. Two-track features (shared baseline vs user-personal
literate config) get called out as such; "works for me at n=1"
is never the verdict for a feature that ends up in the shared
baseline.

See =project_personal_now_foss_later.md= in the agent memory
store for the underlying policy.

Six things are non-obvious from this diagram and worth saying
out loud:

1. *The vault is authoritative; SQLite is derived.* Re-running
   =org-llm index= + =embed= rebuilds the whole engine state
   from =~/org/=. Nothing in =~/.local/share/org-llm/= is
   load-bearing for the user's data — only for the engine's
   speed and convenience. Wiping it loses caches, snapshots,
   audit logs; it never loses notes.
2. *The literate source IS a vault note.* =~/org/20260425230731-
   org_llm.org= is both the canonical source for every
   Python/SQL/elisp file AND a regular org-roam node — so
   =org-llm ask "how does the recipe runner work?"= can retrieve
   the implementation by RAG just like any other concept. Tangle
   direction is one-way: literate org → repo files. The repo
   checkout under =~/repos/org-llm/= is the editable mirror, not
   a second source of truth.
3. *=org-llm-config.org= round-trips with the =config= table.*
   [[file:../../org_llm/literate_config.py][=literate_config.py=]] tangles =config= rows out to the vault
   file (so you can edit knobs in Emacs) AND parses them back in.
   Knob =config_org_autosync= controls whether every =org-llm
   config set= re-tangles automatically.
4. *Code corpus and skills do NOT have separate storage.* The
   code corpus reuses the =files= + =nodes= tables — each
   indexed source file becomes a node tagged =code:<lang>=,
   sharing the same embedding pipeline as notes. Skills are
   org-babel blocks living inside vault notes (registered by
   =:SKILL_NAME:= properties), executed in-place; no skills
   directory, no skills DB.
5. *The LLM proxy is the orchestration seam.* It sits between
   the surface (opencode) and the model (Ollama / cloud). All
   agent-prefix routing, recipe pre-fetch, tool-call repair,
   slow-model watchdog, and =/sys*= short-circuits happen here
   — not in the surface, not in the model.
6. *Tags have two buckets, never one.* =nodes.tags= is the
   source-of-truth from the org file — the indexer rewrites it
   on every =index= run and the auto-tagger never touches it.
   =nodes.auto_tags= is the LLM layer, written ONLY by =tag
   --apply= and never touched by the indexer. Reads that want
   "all tags" use =merged_tags()=. The split is what makes =tag
   --redo= safe — re-tagging previously-auto-tagged nodes can't
   clobber hand-curated org-file tags. Same idea will likely
   apply if/when other LLM-layered metadata lands (auto-titles,
   auto-summaries): keep the source-of-truth column and the
   LLM-derived column separate.

Most code is one big Python package: =org_llm/= is ~50 modules.
The only TypeScript is the opencode TUI plugin
([[file:../../extensions/opencode/src/][=extensions/opencode/src/=]]) plus the bundled Pi adapter
([[file:../../org_llm/pi_extension/pi-org-llm.ts][=pi_extension/pi-org-llm.ts=]]); the only elisp is the Emacs
companion ([[file:../../extensions/emacs/][=extensions/emacs/=]]). The MCP server, LLM proxy,
CLI, indexer, and recipe runner are all Python in the same
package — but each is its own OS process when running, sharing
the same SQLite *file* (not a single connection — see [[*Concurrency — many writers, one DB file, no WAL][concurrency]]).

*** Why only one host gets the proxy

opencode lets us write the baseURL into its config, so we can
point it at =http://127.0.0.1:<proxy-port>= and run our 23
interceptors before traffic hits Ollama. Claude Code talks to
its own Anthropic backend with no equivalent override; Pi
manages its own provider plumbing. Phase 22's design bet was
*"orchestration without round-trips"* — recipes only work when
we control the request seam. That's why opencode is the

** Design rule — events vs metrics vs feedback

Specialised tables look like one pattern but actually serve three
different needs. New tables should be classified up-front:

| category     | shape                          | mirrors history?       | examples                        |
|--------------+--------------------------------+------------------------+---------------------------------|
| *Events*     | one row per system action      | yes — keep history full | =crew_log=, future audit tables |
| *Metrics*    | timeseries; high-volume        | no — would flood        | =sensor_log=                    |
| *Feedback*   | user reaction; qualitatively   | no — different signal   | =insight_engagement=            |
|              |   different from system action |                        |                                 |

Why the distinction matters: a query like "what did the system do
at 14:32?" should hit =history= and get clean event rows. If we
mirrored metrics or feedback into =history=, that query would
conflate "doctor ran a probe" with "user dismissed an insight
card" with "battery dropped 3%" — three legitimately different
signals. Each gets its own specialised table; only events
maintain a unified-log mirror.

The same rule applies to specialised slice tables (like
=crew_log=): mirror to =history= so the unified log is complete,
but keep the specialised columns for fast queries.

** Concurrency — many writers, one DB file, no WAL

Each entry point ([[file:../../org_llm/cli.py][=cli.py=]], [[file:../../org_llm/mcp_server.py][=mcp_server.py=]], [[file:../../org_llm/llm_proxy.py][=llm_proxy.py=]],
[[file:../../org_llm/auto_embedder.py][=auto_embedder.py=]]) is a separate OS process. They open their
own SQLAlchemy engines but write to the same =org-llm.db= file.

[[file:../../org_llm/db.py][=db.py=]]'s =_load_sqlite_vec= sets only =PRAGMA foreign_keys =
ON= — *not* =PRAGMA journal_mode = WAL=. SQLite therefore runs
in default rollback-journal mode, which means concurrent writes
serialise via file-level locking. Reads can run in parallel with
reads, but a write while another write is in progress blocks
with =SQLITE_BUSY=.

In practice this works because writes are short (~1 ms each) and
the Python sqlite3 driver retries =SQLITE_BUSY= for up to 5
seconds by default. The latent risk: if the auto-embedder ever
holds a write transaction across an embed loop (currently it
doesn't — it commits per-batch), it would lock out the user's
=org-llm capture= for seconds. If we add a long-running writer
(e.g. dbt build), enabling WAL would be the right move:

#+begin_src python
# In _load_sqlite_vec, add:
dbapi_conn.execute("PRAGMA journal_mode = WAL")
#+end_src

WAL allows readers and one writer to operate concurrently without
blocking, at the cost of a =-wal= and =-shm= sidecar file. Until
we have a long-running writer, the simpler default is fine.

* Control plane — the LLM proxy is the seam

Every cloud or local model call from a surface goes through
[[file:../../org_llm/llm_proxy.py][=llm_proxy.py=]] (concept page: [[id:47ba2143-c53a-409a-8286-2b3759794608][LLM proxy]]). The proxy declares
=DEFAULT_INTERCEPTORS=, a list of 23 functions ([[id:daaf30cd-4316-4f20-befa-5831328708c6][interceptors]])
run in order against every chat-completions request. Each
function inspects the request and either returns a =ProxyResponse=
(short-circuit — synthesise a reply, never call the upstream
model) or returns =None= (fall-through — possibly having mutated
the request).

** Pattern note — chain of responsibility, with middleware mixed in

This is the *Chain of Responsibility* pattern (GoF). It shows up
across the industry under several names — servlet filters
(Java), Express / Koa middleware (Node), Django middleware
(Python), Spring's =HandlerInterceptor=, Angular's
=HttpInterceptor=, gRPC interceptors, axios hooks. The shapes
are all variants of "a request flows through a chain; each link
either handles it or passes."

Strict terminology distinguishes:

- *Interceptor* — can short-circuit (return early without
  calling the next link).
- *Middleware* — always passes through, only mutates the
  request or response.

Org-llm's chain has both. Phase 1 entries in the diagram below
are interceptors-strict-sense — each one *can* short-circuit by
returning a =ProxyResponse=. Phase 2 entries are middleware —
they always fall through with mutations only. We call all 23
"interceptors" colloquially because the type signature is
shared (=Interceptor = Callable[[ProxyRequest], Optional[ProxyResponse]]=),
but the behavioural split matters: it's why the diagram
distinguishes the two phases.

Important scoping note: this chain runs against opencode's
chat-completions traffic only. Claude Code and Pi bypass the
proxy entirely (their LLM transport is outside our control — see
[[*3. Surfaces — how org-llm reaches the user][surfaces]]). The =/sys*= short-circuits, recipe pre-fetch,
=@<agent>= persona swap, and tool-call repair all live inside
this chain — meaning they only fire when the user is in
opencode.

Five things worth knowing about this chain:

1. *Recipe matching is inside =intercept_agent_prefix=, not its
   own interceptor.* When a user types =@scribe summarise my
   dailies=, the agent_prefix interceptor parses the prefix,
   swaps in scribe's persona, calls =match_recipe()= against the
   residual text, and — if a recipe matches — calls
   =execute_recipe()= to pre-fetch the data and inject a
   =MANAGER PRE-FETCH= block into the system prompt. The proxy
   then falls through and the agent narrates in ONE cloud call.
   See [[id:3ed81ee4-e28d-4daf-87fb-c1645b58a05c][recipes.org]] for the three layers of that mechanism.
2. *First match wins for short-circuits; mutations stack.* The
   ordering in =DEFAULT_INTERCEPTORS= is significant: e.g.
   =sysexport= runs before =sys_commands= so =/sysexport= hits
   the dedicated handler instead of being swept up by the
   generic =/sys*= short-circuit. Mutations in Phase 2 each
   touch a different field of the request, so order matters less
   — but =pii_redact= deliberately runs before =model_routing=
   so we don't route a redacted prompt to the wrong model.
3. *Several interceptors are knob-gated.* =proxy_repair_markdown_tools=
   gates =tool_call_repair=; =proxy_capture_narration= gates
   stream-buffering for narration capture; =proxy_local_only=
   conditionally appends =local_only= to the chain at startup.
   All knobs live in the =config= table and round-trip via
   =org-llm-config.org=.
4. *Tool-call adapters split the work between dialects.*
   =synth_tool_call= teaches non-tool-supporting models (gemma)
   to emit tool calls via prompt-engineered XML. =tool_dialect_translate=
   converts Kimi/qwen3 dialect output to OpenAI format.
   =tool_call_repair= extracts tool calls from markdown-JSON
   blocks (a common malformation across small local models) and
   either executes locally (if the tool is in [[file:../../org_llm/org_tools.py][=org_tools.py=]]) or
   forwards a clean tool_calls array upstream.
5. *Audit is universal.* Every request — short-circuited or
   forwarded — writes one =AuditEntry= JSONL line via =AuditLogger=
   to =~/.local/share/org-llm/llm-audit.jsonl=, with the matching
   interceptor's name in =intercepted_by= (or =forward= if none
   matched). This is how we attribute behaviour to interceptors
   when something goes wrong.

The proxy is what keeps orchestration *zero extra round-trips* in
the common case: =agent_prefix= → =match_recipe= → =execute_recipe=
→ pre-fetch block → ONE cloud call. No separate "manager turn"
exists in the chain because there doesn't need to be one.

** Model-license gating — FOSS-first by default

Cloud models in [[file:../../org_llm/cloud.py][=cloud.py=]]'s =CloudModelInfo= rows carry a
=license_tier= field with three values:

| tier            | examples                                                   | gated by                       |
|-----------------+------------------------------------------------------------+--------------------------------|
| =foss=          | Apache 2.0, MIT, GPL — DeepSeek R1, Llama 3.3, Qwen 2.5    | always available               |
| =open_weight=   | Llama / Qwen / Moonshot community licenses                 | always available               |
| =proprietary=   | =anthropic/=, =openai/= (closed API), Gemini               | knob =proprietary_models_enabled= |

When =proprietary_models_enabled=false= (the default), the cloud
catalog filters out closed-API rows; =org-llm models --tune=
won't suggest them. Users who want Sonnet / GPT-5 explicitly
flip the knob.

The textual =license= field on each row is fed through
=_classify_license_tier()= when =license_tier= isn't explicit;
the heuristic is *conservative — anything ambiguous becomes
proprietary* so the FOSS gate doesn't accidentally leak closed
models.

** Credentials — `pass` is the only store

API keys for cloud providers live in
=~/.password-store/org-llm/<provider>/api_key= and are read by
[[file:../../org_llm/creds.py][=creds.py=]]. =pass= unwraps the gpg-encrypted entry on demand
so the keys never sit in plaintext on disk.

[[file:../../org_llm/creds.py][=creds.py=]] is Guix-aware: it tries =~/.guix-profile/bin/pass=,
=~/.guix-home/profile/bin/pass=, then falls back to whichever
=pass= is on =PATH=. =gpg= lookups follow the same pattern.
There is no env-var fallback by design — if =pass= can't unlock
the key, the proxy refuses cloud rather than prompting or
crashing mid-request.

| =proxy_local_only=              | false   | session kill switch — refuses every cloud target               |
| =proxy_cloud_first=             | false   | route every chat-completion to cloud, skip local entirely      |
| =proxy_cloud_failover_enabled=  | true    | per-turn fallback when local stalls past TTFB                  |
| =proxy_first_byte_timeout_ms=   | 30000   | TTFB threshold; 0 disables                                     |
| =proprietary_models_enabled=    | false   | gate that includes/excludes closed-API rows from the catalog    |
| =cloud_provider=                | (unset) | active provider slug (must be in =PROVIDERS=)                  |
| =cloud_model=                   | (unset) | active cloud model id (provider-specific)                      |

* Self-care — keeping the system honest

Four loops keep the engine, the index, and the host healthy.
Three are deterministic with optional LLM polish; one is
on-demand. All write through to =history= (kind = =doctor= /
=auto_embedder= / =stale=) so a unified =org-llm history= query
shows the full self-care trail.

Three properties of the self-care layer worth pinning:

1. *Deterministic-first, LLM second.* Every loop computes a
   deterministic answer first (probe values, file mtime deltas,
   exception-pattern matches), then optionally lets the LLM
   polish or contextualise. Examples:
   =deterministic_summary()= runs before =llm_optimization_advice()=;
   =rescue.match_structured()= is consulted before
   =sanitize_llm_advice()= is shown. This means self-care still
   works when the LLM is offline or rate-limited — the LLM only
   adds prose around already-correct facts.
2. *Activity context turns metrics into events.* =sensor_log='s
   =context= column carries a summary of the last few =history=
   rows alongside each reading. So the LLM advice path can say
   "your CPU was pegged at 8.0 while =ask --reason deepseek-r1=
   ran for 240s — consider routing reasoning to cloud" instead
   of just "your CPU is high." Crosses the events-vs-metrics
   boundary in a controlled way (see the [[*Design rule — events vs metrics vs feedback][design rule]]).
3. *Loops compose.* Auto-embedder keeps the index fresh →
   staleness sweep audits the freshened data → insight cards
   surface the candidates → the user reacts → doctor reads
   =insight_engagement= via =--diagnose-cards= to surface
   per-generator quality patterns → suggests config changes.
   The chain only works because each loop writes its result
   somewhere downstream loops can read.
