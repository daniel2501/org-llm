The single source of truth for *active* org-llm development —
what to do next, what's blocked, what needs validating, what
needs deciding. This is the agenda surface; [[id:43e1b335-656b-45ba-8d6d-7d9b9f2e9c4d][roadmap.org]] stays

** How to use this file

- Every actionable item is a TODO heading with a workflow state
  (=TODO=, =NEXT=, =STARTED=, =HOLD=, =WAITING=, =DONE=,
  =CANCELLED=).
- Tags express category, layer, and criticality:
  - *Category:* =:validation:= =:bug:= =:plan:= =:test:= =:doc:=
    =:perf:= =:research:=
  - *Layer:* =:proxy:= =:mcp:= =:recipes:= =:agents:= =:cli:=
    =:opencode:= =:emacs:= =:pi:= =:db:= =:vault:= =:cloud:=
  - *Criticality:* =:load-bearing:= (orchestration, recipes,
    proxy, agent_baseline) · =:polish:= (themes, splash) ·
    =:research:= (exploring options)
- =:PRIORITY:= property: =A= = pinned, must do · =B= = scheduled
  · =C= = idea bin
- =:VALIDATED:= property: ISO date the item was last hands-on
  certified. Older than ~30 days = re-validate.
- =SCHEDULED:= for date-driven work (remote agents, deadlines).
- =DEADLINE:= for hard stops (merge freezes, demos).

* North star

** What org-llm is

*Claude Code for Org Mode* — assistants that help the user
manage their life in org-mode in ways they would never have time
to do without an agent system. Wide-scoped on purpose; opinionated
about the stack (org-mode / Doom / FOSS CLI tools / tangle / dbt
/ SQL / FOSS LLMs).

** The three quality gates

Every feature, refactor, and decision is tested against these
three gates (in order — each gate has veto power over the next):

1. *Be really good at what the app does.* Does this make
   org-llm a better Claude-Code-for-org-mode — better at
   agent-driven life management? If it doesn't move that
   needle, default to skepticism.
2. *Not too complex.* Could the same value land in a simpler
   shape? Three similar lines beats a premature abstraction.
   New module + new table + new knob + new agent for one
   feature is a high bar.
3. *Manage required complexity well.* The app IS wide-scoped
   (orchestration · agents · surfaces · self-care · stack
   maximalism). Complexity that's required must be made
   tractable: clear seams, deterministic-first paths, single
   sources of truth, documented invariants. Complexity that
   compounds without management = thicket = off the rails.

These gates govern this entire tracker. Validation = "does it
pass gate 1?" Architecture review = "does it pass gates 2-3?"

- Cross-platform install validated (macOS + Ubuntu + Termux).
- Load-bearing orchestration features all *certified*: each one

* Pace + estimates                                              :@pace:

The estimation discipline: every TODO/NEXT item gets an
=:EFFORT:= (initial estimate) when it's created or first
considered. When the item lands DONE, =:ACTUAL:= captures what
it really took. Over time the ratio =:ACTUAL: / :EFFORT:= becomes
the calibration we use to size future sprints.

** Convention

- =:EFFORT:= — org-mode standard, e.g. =30m=, =1h=, =2h=, =1d=,
  =2d=. Set when the item enters TODO/NEXT (or earliest
  contemplation).
- =:ACTUAL:= — same format, set when the item moves to DONE. Be
  honest — if it took 4× the estimate, write 4×; that's the
  calibration signal.
- =:STARTED-AT:= and =:COMPLETED-AT:= — wallclock dates (org
  inactive timestamps work). The state-change bracket; not the
  same as actual focused effort because work is interleaved.
- For multi-session work: optional org-mode clocking
  (=C-c C-x C-i= start, =C-c C-x C-o= stop). Sums become
  =:ACTUAL:= when done.

** Calibration buckets (current best-guess; refine over time)

| bucket     | range          | shape                                                            |
|------------+----------------+------------------------------------------------------------------|
| trivial    | <30m           | single-file edit; copy text; add a one-liner; no tests           |
| quick      | 30m–2h         | feature in one file w/ minimal test; small bug fix               |
| small      | 2h–half-day    | new module + tests + docs in one area                            |
| medium     | half-day–1d    | cross-cutting, touches 3–5 files; new CLI verb wired             |
| big        | 1–2d           | refactor + integration; A/B-validated decision; new agent        |
| multi-day  | 2d+            | architecture sweep; cross-surface migration; multi-recipe rework |

These buckets are inputs to the planning conversation. If an
=:EFFORT:= is bigger than =medium=, the item should probably be
split.

**** Why the four failing recipes lose

actually retrieve before narrating, which produces grounded,
cited answers. This is the failure mode that violates gate 1
(be good at the job) — speed + tokens win don't matter when the
output is fabricated.

**** Why each FAIL recipe loses

The three FAIL recipes share one failure mode: condensed
pre-fetch hides what's missing, letting the model fabricate
around silence.

- *=dailies_routine_filter= (A5 — "most common routine items"):*
  pre-fetch caps at top 3; model presents the cap as the full
  set + invents a date range ("from 2025-10-26 to 2026-04-11")
  not in the source. recipes_off lists 5 items honestly without
  the date claim.
- *=weekly_mood_review= (A6 — "mood over past month"):*
  pre-fetch feeds zero-counts for sentiment categories; model
  reads absence-of-evidence as evidence-of-flatness ("no reports
  of … positive feelings, gratitude, or connection"). recipes_off
  retrieves real entries and finds active self-care.
- *=weather_aware_agenda= (A7 — "weather + schedule, prioritise"):*
  pre-fetch is sparse enough that the model invents details — a
  fictional "outdoor meeting with Jane from 10 AM to 2 PM" + a
  fabricated "rainy morning, afternoon clear" forecast. recipes_off
  cites real overdue tasks with file paths AND honestly surfaces
  "couldn't fetch weather: location not configured."

**** Decision: iterate, then re-judge (n=1 dev → n=many FOSS)

Initial recommendation was "dump 3 fails." Revised on
[2026-05-03] after framing context: recipes are 2 days old, dev
is solo, but eventual users are FOSS-many. At n=1 the
iteration cost is low and the design intent is fresh — fix
beats dump. At n=many the iteration's exit state has to be
defensible for unknown vaults — fixes must be defensive, not
just dev-vault-friendly.

The failure modes above are concrete and pre-fetch-template
fixable:

   as flatness.
3. *Surface error states.* "Location not configured" lands in

** TODO Phase 25 — invert authority: DB is truth, files are UI    :plan:db:foundation:load-bearing:
:PROPERTIES:
:PRIORITY:        A
:GATE:            1,3
:EFFORT:          multi-day (5-phase arc, weeks not days)
:PHASE_CANDIDATE: yes
:SOURCE:          2026-05-03 directional decision
:END:

Today: vault on disk = source of truth; SQLite = derived cache.
Stated in architecture.org five places ("vault authoritative;
SQLite derived"). Implies: DB wipeable; vault must be
backed-up separately; mass ops require disk walks; cross-file
queries require code, not SQL.

*Inverted target:* SQLite (or successor) = source of truth;
=~/org/*.org= = rendered UI surface. Users edit org files in
Emacs as today; engine ingests changes; engine renders changes
back. DB carries *everything*: raw file bytes + parsed
structure + embeddings + history + config + crew log + sensors
+ insight engagement + creds digest. One file (or one
replicated DB) IS the entire org-llm state.

*** Why this is gate-1 worth doing

- *Mass operations* — "rename =:old:= → =:new:= across vault"
  becomes one SQL statement + re-render of affected files.
  Today it's a vault scan + per-file edit + rewrite.
- *Cross-file queries* — "every TODO older than 30 days with
  priority A" is a one-liner. Today it's code.
- *Single backup target* — SQLite dump = full state. No "did I
  push my vault to git?" gap. Today the =self snapshot= verb
  bundles package source + DB but *not* the vault.
- *Atomic transactions* — tag + content + embedding updates
  land together or roll back together. Today they're three
  separate disk operations with no atomicity.
- *History of the vault itself* — WAL or DB-of-git lets us
  query "what did this note say last week?" without a separate
  vault git repo.
- *Sync / multi-device* — SQLite over Litestream (or successor
  on Postgres) = trivial replication. Today the vault is
  pinned to one box.
- *dbt over EVERYTHING* — Phase 12.7's dbt scope is currently
  the engagement table. With everything in DB, dbt models the
  *vault content directly* — analytics over notes is a
  one-liner.

This isn't a refactor for elegance. Each bullet is a feature
the app can't currently deliver because the DB doesn't hold
enough.

*** Why this is gate-2/3 hard

- *Round-trip fidelity is the boss fight.* Org-mode files have
  subtle invariants: file-level keywords, property drawers,
  blank-line discipline, comment lines, mode lines, code
  blocks, exact whitespace, end-of-line style. Disk → DB →
  disk *must* reproduce byte-for-byte (or close to it; user
  must be able to re-open the file and not flinch). This is
  what kills naïve "store parsed AST, regenerate from AST"
  designs in practice.
- *Two writers competing.* User edits in Emacs (disk write).
  Engine writes DB (e.g. embedding refresh, tag-rename op).
  Conflict resolution is non-trivial. Today the indexer reads
  disk-authoritative; in the new world, both must merge.
- *Editor integrations don't know about the DB.* Emacs +
  org-roam + Doom keybinds work on disk. Either the DB stays a
  slave to disk edits (= current model, just with raw bytes
  added) OR there's a watcher loop that re-renders affected
  files atomically OR users adopt an org-llm-aware mode (locks
  them into the stack — gate-2 risk).
- *Hidden Emacs state.* Folding, narrowing, cursor position
  are not in files but in the editor. DB-driven re-render must
  not blow these away when files change underneath.
- *SQLite at scale.* Vault content + embeddings + history can
  grow. User signaled willingness to outgrow SQLite — DuckDB
  (column store, analytics-friendly), Postgres + pgvector
  (replaces sqlite-vec, mature) are real candidates. Each adds
  operational complexity (Postgres = a service to run; DuckDB
  = different concurrency model).
- *No-WAL concurrency latent risk* (already noted in
  architecture.org § Concurrency) becomes a *blocker*. If DB
  is authoritative, write contention matters. Phase 25 must
  ship WAL.

*** Recommended ship order (6 sub-phases)

Revised 2026-05-03 to insert *25.4 git ingestion* before
DB-authoritative engine ops. Reason: conflict resolution in
the new model IS a git problem (user-edit-vs-engine-edit =
git merge). With git semantics in the DB by 25.4, conflict
resolution becomes a known-solved problem instead of one we
invent.

1. *Phase 25.1 — DB as full mirror (vault still authoritative).*
   Add =File.raw_content= column. Indexer writes raw bytes
   alongside parsed structure. Validate round-trip: dump from
   DB → rendered file == original disk file (byte-equal or
   diff'd through a tolerant comparator). Iterate on the dev's
   vault until 100%. ~3-5 days.

2. *Phase 25.2 — backup + restore tooling.* Once round-trip
   verified: =org-llm backup [path]= produces a single archive
   (SQLite dump + creds digest manifest + version stamp).
   =org-llm restore <archive>= unpacks with confirmation +
   integrity check. Reuses =self snapshot= substrate. ~1d.

3. *Phase 25.3 — WAL + concurrency hardening.* =PRAGMA
   journal_mode = WAL=. Test multi-process write contention
   (proxy + auto-embedder + CLI). Document the new concurrency
   model. ~half-day.

4. *Phase 25.4 — git ingestion as audit/history layer (NEW).*
   Snowflake-style "git repo as DB" pattern, FOSS-implemented.
   Add tables =git_commits= (sha, ts, author, msg) +
   =file_versions= (file_id, commit_sha → raw_content_blob,
   mtime). Use =pygit2= (libgit2 bindings, MIT FOSS) to ingest
   =~/org/= git history. Current-state view materialised from
   the latest commit per file.

   *Wins:* free versioning · free diff/blame queries · branch
   + tag references as queryable state · "what did this note
   say last Tuesday?" → SQL · multi-device sync via push/pull
   instead of DB-replication · backup is just =git push=.

   *Engine-write isolation:* engine writes (embeddings,
   auto_tags, vault_fact cache) live in gitignored DB tables
   only. Git tracks user edits to =*.org= files; engine state
   never pollutes git history.

   ~3-5 days. Composes with 25.5's conflict resolution.

5. *Phase 25.5 — DB-authoritative for engine ops.* Mass
   operations (=org-llm tag --rename foo bar=, content edits
   triggered by agents) read/write DB and trigger re-render of
   affected files. Disk watcher (auto-embedder evolution)
   ingests user-side edits and merges using *git merge
   primitives from 25.4* — conflict resolution becomes a
   known-solved problem. ~1-2 weeks of careful work.

6. *Phase 25.6 — full inversion.* Architecture.org's "vault
   authoritative" principle becomes "DB authoritative; vault
   is rendered UI." All engine reads go to DB; disk is touched
   only for user-facing render. Multi-device sync becomes a
   feature. ~1 week.

7. *(Optional) Phase 26 — beyond SQLite.* If perf or analytics
   demand, evaluate DuckDB / Postgres+pgvector. Schema lift
   shouldn't be hard if Phase 25.x is well-designed. Decision
   gate: are we hitting actual SQLite limits, or is it
   premature?

   Sub-decision: Dolt (Apache 2.0; foss MySQL fork with
   git-style branching at row level) is technically the
   "purest" implementation of the inverted model — but locks
   us out of sqlite-vec / the SQLite ecosystem we depend on.
   Shape A (git-ingested-into-our-DB) avoids this dependency
   shift. Reconsider Dolt only if 25.4's projection-based
   approach hits limits.

*** Argument 1 — the reframe (integration, not fusion)

The original "is Agor a component we plug in?" framing puts
Agor *under* org-llm and is unwinnable: TS daemon vs Python
CLI, web canvas vs Doom, multiplayer vs n=1. Six categorical
mismatches.

it.* Agor is the meta-surface above our stack — "which
sessions in which worktrees doing which work" — not a
substrate. Doom stays primary on the host. Vault stays
authoritative (or becomes so per Phase 25). Recipes,
captain's log, opencode plugin all stay. Agor only adds the
*air-traffic-control* layer above them.

- *Dissolve:* wrong runtime (TS vs Py is fine for sibling

- *Narrower but real:* worktrees-as-anchor (turns into the

- *Survive:* off-the-rails-complexity, Doom-as-primary

Reframe doesn't *win* the argument. It makes it *winnable* —

*** Argument 2 — worktrees as the strongest pro-Agor argument

Original con-eval dismissed worktrees as "wrong unit of
work" in one line. Wrong; they fit problems we have *today*:

- *Parallel dev streams collide on this repo weekly.* Current

- *Vault experiments without polluting =~/org/=.* Tag-rename

*Generative principle:* when the LLM does a pattern of work
repeatedly, the app should detect it, propose a deterministic
tool, validate the tool against the LLM's output, and register
it so future invocations skip the LLM entirely. Driven from
the DB; the tool itself is FOSS Python; the LLM only writes
code, not runtime decisions.

*Why this is gate-1, gate-2, AND gate-3 healthy:*
- *Gate 1:* the app gets faster and more deterministic over
  time for the user's actual workflows (not theoretical ones)
- *Gate 2:* every tool is a complexity *reduction* — replaces
  a slow expensive cloud call with a 10ms DB query
- *Gate 3:* audit log + validation framework already in place;

   savings. Pure analysis — no synthesis yet. ~2d.

The recipe A/B revealed the most damaging failure mode in the
app: the model fabricates around sparse data ("meeting with
Jane", invented forecasts, fictitious counts). The fix that
worked in the tool-use path was *grounding* — file citations,
explicit "no matches" answers, error states surfaced. This

*FOSS-bar criticality:* at n=1 the dev can spot fabrications
because they know their own vault. At n=many users can't.
Citations are how strangers confirm an answer is real before
trusting it. This is the highest-leverage gate-1 win we've
identified this session.

*** Design

A log-level knob =proxy_show_work_level= (0..4):

| level | name      | what shows                                                | default |
|-------+-----------+-----------------------------------------------------------+---------|
| 0     | off       | narration only (legacy)                                   |         |
| 1     | citations | footer listing files cited (=Sources: foo.org, …=)        | *yes*   |
| 2     | inline    | =[foo.org:42]= markers next to claims                     |         |
| 3     | trace     | tool calls + args + results above answer                  |         |
| 4     | full      | pre-fetch blocks + raw tool results + reasoning trace     |         |

- Knob =proxy_show_work_level= in =config= table

- Proxy phase-2 interceptor =intercept_show_work= — injects the
  level-appropriate cite instruction
- opencode TUI plugin renders citations distinctly (LCARS-themed,
  clickable when possible)
- CLI =ask= prints citations as a footer
- Existing =manager-log.jsonl= already carries the trace data;
  levels 3+ just surface what's there

*** Why this is a unification, not a new layer

This feature ties together infrastructure we've already built:
- *Phase 22.5a* (manager log) — narration capture wired but
  audit-only. Show-your-work makes it user-visible.
- *Phase 22.5b* (reasoning capture probe — in plan queue) — same
  idea, different framing. *Should merge into this item.*
- *Insight cards (Phase 12)* — already cite evidence in their
  bodies. Show-your-work generalises the pattern to ALL LLM
  output.
- *=llm-audit.jsonl=* — already records every call. Levels 3+
  surface what's already captured.
- *Recipe pre-fetch fix (citations + completeness markers)* —
  literally show-your-work applied to one slice. The principle
  shipped piecemeal there, ship it project-wide here.

- *Slice 1 — level 1 citations + baseline rule + knob* (1d):

* Meta — eat your own dog food

This tracker is *intermediate state*. The end-goal is for
**org-llm itself to take over the tracking work** — for this
project AND for similar large solo / small-team org-mode
initiatives. Every convention in this file is a candidate for
the eventual template. Friction captured here becomes the spec
for the app feature.

** What "self-hosted tracking" means concretely

- =org-llm tracker init= — scaffolds a tracker.org from a
  template into any vault, with the schema (TODO states, tag
  taxonomy, agenda views) baked in.
- =org-llm tracker review= — scans the vault for scattered
  planning files and proposes fold-in / archive (the
  consolidation we just did, but automated).
- =doctor -w= extension — surfaces tracker entries with
  =:VALIDATED:= older than 30 days as "stale validation"
  alerts.
- LLM agents use the tracker as their priority surface —
  recipes that read open TODOs and suggest what's next given
  the three [[*The three quality gates][quality gates]].
- Tutor onboarding step that introduces the tracker pattern.

The migration we did 2026-05-03 (scattered → central) is itself
the *spec* for what =tracker review= should automate.

** Broader principle: dev artifacts are app candidates

Every artifact built for org-llm's own development is a
candidate user-facing feature. The two roles compose: dev-process
tooling that works at n=1 today is a reference implementation
of what we could ship to FOSS users running similar large
org-mode projects.
