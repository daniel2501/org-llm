* Summary

*Summary.* Time awareness in org-llm has three layers: (1) /current-time
grounding/ — every agent prompt is anchored to the current date+time
(shipped via =intercept_time_grounding=); (2) /org-mode scheduling
primitives/ — =SCHEDULED=, =DEADLINE=, =CLOCK=, =org-habit=, recurrence
rules — the native substrate every agent already understands because
it reads org files; (3) /cross-cutting orchestration/ — when work needs
to fire on a cadence independent of any single org file (nightly
hygiene, weekly snapshots, monthly retros). Layer 3 is where Airflow,
cron, =systemd= timers, and dbt-cloud-style schedulers live; today
org-llm's scheduling at that layer is ad-hoc cron / launchd /
scheduled remote agents.

*Expanded.* This page describes the three layers, what's shipped
today, what's missing, and where Apache Airflow plausibly fits (or
doesn't). The tl;dr is: Layers 1 and 2 are done and free; Layer 3 is
where infrastructure questions live, and Airflow is a candidate but
not a near-term one.

* Layer 1 — current-time grounding (shipped)

| Aspect          | Today                                                             |
|-----------------+-------------------------------------------------------------------|
| Mechanism       | =intercept_time_grounding= (proxy interceptor)                    |
| Payload         | Current date + time injected into system prompt of every call     |
| Implication     | Agents reason about "today" / "yesterday" / "next Tuesday" anchored |
| Failure mode    | Without it: hallucinated dates, drift to training-cutoff           |
| Cross-ref       | [[file:llm-proxy.org][llm-proxy.org]] § interceptor chain                                |

User-facing times in this page are *EST* (per house convention).

* Layer 2 — org-mode scheduling primitives (shipped + native)

org-mode itself is the substrate. Every agent that reads org files
inherits these for free.

| Primitive             | Shape                              | Who reads it today           |
|-----------------------+------------------------------------+------------------------------|
| =SCHEDULED:=          | When a task should start           | @riker (Trek: TNG XO), agenda |
| =DEADLINE:=           | Hard due-by                        | @riker, @boothby (drift)     |
| =TIMESTAMP=           | Point-in-time event                | @geordi, agenda              |
| =CLOCK= blocks        | Time spent on a task               | @geordi (rolls)              |
| =org-habit=           | Recurrence (=+1d=, =++1w=, =.+1d=) | @boothby, @riker             |
| =org-agenda= dispatch | Query/view layer                   | All agents via babel/SQL     |

Per [[file:dbt-pipeline.org][dbt-pipeline.org]] § derived models, these primitives get
materialized as queryable columns (=parsed_clocks=, =parsed_dates=,
=scheduled_at=, =deadline_at=) — agents query them via SQL. No new
infrastructure needed; this layer is just /reading what's there/.

* Airflow tie-in — when does it earn its keep?

[[https://airflow.apache.org][Apache Airflow]] (Apache 2.0 — FOSS-aligned per DEC-010) is a DAG-shaped
dataflow + workflow scheduler. Strengths: dependencies, sensors,
retries, observability, backfills. Weaknesses: heavy for small
per-machine cron-shape work where =systemd= timers or cron suffice.

** Decision lens — when Airflow vs. alternatives

| Alternative                              | Wins when                                                |
|------------------------------------------+----------------------------------------------------------|
| =systemd= / cron                         | Single host, single vault, no dependencies               |
| NATS                                     | Event-shape (something happened → fan out), not time-shape |
| Phase 2026-05.20 — sync verb POC — promoted-tool runtime         | Recurring deterministic call, n=1 today                  |
| Airflow                                  | DAG-shape + sensors + retries + backfill + observability across hosts/vaults/apps |
| Prefect / Dagster                        | Same shape as Airflow, lighter footprint — side-look once "yes orchestrator" lands |

** Recommendation

Airflow becomes plausible at /n=many users/ or /cross-vault
federation/. For n=1 today, simpler primitives win. *Defer Airflow
integration; revisit once cross-vault federation lights up* (Phase 2026-06.04 — FOSS agent value-adds+
— federation). Filed in [[file:dev-tracker.org][dev-tracker.org]] § Hosting matrix as a TODO.

Caveat to the deferral: candidates *#2 (DB ↔ vault re-render)*,
*#7 (Phase 2026-05.20 — sync verb POC — self-coded tools runtime)*, *#8 (embedding refresh)*,
and *#10 (provenance backfills)* are /internal/ DAG-shape needs that
arrive *before* federation.  They are the earlier trigger and may
collapse the deferral window.

** Headless validation harness

Per =feedback_validate_orchestration_with_ab=, the eleven candidates
above are each exercised by an /agent-managed headless test/ in
=tests/test_airflow_candidates.py=.  The harness lives in
=tests/airflow_candidate_harness.py= and provides minimal
in-process simulators for the four Airflow primitives we'd lean
on: =DAG= (topological execution), =Sensor= (poll-with-timeout),
=Retry= (backoff with cap), =Backfill= (replay-over-window).

Each test asserts whether the candidate /actually/ exercises the
primitives that justify Airflow over =systemd= timers.  Verdicts
are emitted as a structured row the harness collects so an agent
(today: =@geordi= per [[file:agents.org][agents.org]] roster) can run
=pytest tests/test_airflow_candidates.py -q= and narrate the
result table.  This is the empirical prior the recommendation
above rests on.

* Two-tier tools and scheduling (DEC-013)

Per DEC-013 (two-tier tools: data + effect), scheduling sits exactly
on the boundary:

| Tier   | Example scheduling tool             | Notes                          |
|--------+-------------------------------------+--------------------------------|
| Data   | =next_run(rule)=, =list_schedules()= | Pure query — when does X next fire? |
| Effect | =schedule_cron(spec, agent)=         | Mutates host state — cron entry, =systemd= unit, remote agent |

Layer 2 (org-mode primitives) is mostly /data/ — agents read
=SCHEDULED=. Layer 3 (cross-cutting orchestration) is mostly
/effect/ — schedules fire host-side jobs.

* The "agents that schedule themselves" pattern (deferred)

An agent reading captain's-log + tracker.org + agenda could /propose
its own schedule/. Examples:

- @boothby observes hygiene runs land cleanest at 02:00 EST; proposes
  its own cron entry.
- @journalist offers "want a weekly mood review every Sunday morning
  09:00 EST?"
- @riker proposes "sprint review every other Friday 16:00 EST."

Phase 2026-05.20 — sync verb POC — self-coded tools is the natural home: LLM observes a
recurring need, proposes a deterministic tool (here: a schedule
entry), validates it, registers it; runtime calls skip LLM.

Today: out of scope. Filed for the future.
