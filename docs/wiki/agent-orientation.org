#+TITLE: Agent orientation — manifest at spawn, primer on demand
#+FILETAGS: :wiki:agents:orientation:primers:phase-24:
#+OPTIONS: toc:nil num:nil

* What this is

*Summary.* A pattern for handing a specialist agent the
domain-specific conventions it needs to do its job correctly,
without bloating its spawn-prompt with rules it may never use.
Every specialist gets a one-paragraph *manifest* at spawn that
names the core agents and their *primer namespaces*; the full
primer for any namespace is fetched *on demand* when the
specialist's task actually touches that domain. The manifest is
small, static, and load-bearing for awareness; the primers are
fresh, large, and load-bearing for correctness.

*Expanded.* org-llm has a small set of core "steward" agents —
[[id:b9e5d3c2-4a7f-48a6-9c1d-e2f3a4b5c6d7][@agentsmith]] (ships
new agents), =@curator= (sweeps wiki conventions), =@tracker=
(owns =dev-tracker.org=) — each owning a knowledge domain that
many specialists touch. Without orientation, every specialist
either re-derives conventions from the source files (slow,
error-prone) or gets them wrong on the first try (rework).
Without lazy-loading, every specialist pays the full primer
cost at spawn even when its task never touches that domain
(token bloat, stale-by-spawn-time risk). The pattern threads
the needle: a thin manifest at spawn so the specialist knows
*what it doesn't know and who to ask*, and a deterministic
primer-resolver that returns the full convention when the
specialist actually invokes it. The manifest itself is the
load-bearing claim — *if it tells you who teaches each domain,
you can ask for the primer*.

* The manifest

*Summary.* A one-paragraph block injected into every
specialist's spawn-prompt. Names each core agent, the domain it
owns, the primer namespace it exports, and any always-on rules
short enough to live inline (e.g. Rule 2b for wiki authorship).
Does *not* embed full conventions, file paths, or templates —
those are the primer's job. Sized to fit in ~10–15 lines so it
never crowds out the actual task instruction.

*Expanded.* The manifest is generated by [[id:30d4ee70-0472-4bcb-a02e-efde52bef3c6][the orchestration layer]]
at delegate time, not by the specialist. Its current shape:

#+begin_example
ORG-LLM AGENT MANIFEST (lazy primers — fetch when relevant)

- @curator owns wiki conventions. Call primer("wiki-authorship")
  before writing any docs/wiki/*.org page or report.
  Always-on: Rule 2b — every wiki concept leads with *Summary.*
  + *Expanded.*
- @tracker owns dev-tracker.org. Call primer("dev-tracker-entry")
  before adding/editing a phase entry; primer("agent-report")
  before writing a docs/notes/ post-action report.
- @agentsmith owns new-agent shape. Call primer("new-agent")
  before drafting persona/triggers/capabilities.

Manifest is awareness, not authority. Fetch the primer for full
rules, file paths, and templates.
#+end_example

The manifest is the only piece guaranteed at spawn. It must be
short enough that specialists in tight context budgets (small
local models with 8k windows) still get it. It updates only
when a core agent or namespace is added/removed — *not* when a
single rule inside a primer changes. Rule changes go in the
primer; the manifest stays stable.

*Always-on inline rules* are the exception: a rule short enough
to fit in one line *and* universal enough that any specialist
who writes a wiki page must follow it (Rule 2b is the canonical
example). Inlining one rule beats a primer round-trip for
something that short. The bar is high — most rules belong in
the primer, not the manifest.

* The primer

*Summary.* A deterministic resolver — not an LLM call — that
returns the full convention for a named namespace
(=wiki-authorship=, =dev-tracker-entry=, =agent-report=,
=new-agent=). The specialist asks for it explicitly when its
task actually touches that domain; the resolver reads the
authoritative source files (=wiki-conventions.org=,
=dev-tracker.org=, the report template) and returns a
templated response. Always fresh because it reads at call time.

*Expanded.* Each primer is the smallest piece of context
sufficient to *write a conformant artifact* in that namespace
without further consultation. A wiki-authorship primer
includes: Rule 2b shape with examples, link forms (=[[id:…]]=
vs. =[[file:…]]=), the fresh-UUID generation command, the
00-index.org integration step, and the
[[file:../../scripts/link_wiki_files.py][=scripts/link_wiki_files.py=]] verifier. A dev-tracker-entry
primer includes: the property block (=:PRIORITY:= /
=:GATE:= / =:EFFORT:= / =:PHASE_CANDIDATE:= / =:SOURCE:=), the
Recommended ship order convention, and the Connections /
Risks section template. An agent-report primer includes the
uniform structure canonized 2026-05-04 (Objective →
Dev-tracking → What landed → Decisions → Verification →
Open questions → Non-goals → Gotchas) with the
=docs/templates/agent-report.org= template path.

The primer is *deterministic by design* — see [[id:cf466e65-0fa1-4f23-8103-8205f67a6ca3][lazy-loading]] for
the policy. It's a Python resolver that reads files and
substitutes a small number of dynamic fields (today's date,
the next available UUID, the current dev-tracker phase
counter). No LLM. This means primers can be unit-tested,
versioned, and benchmarked, and primer drift is detectable by
diffing the resolver output against the source-file truth.

This is the same family as [[*Composition with existing primers][the resolver registry coming in
Phase 24.1]] — orientation primers and pre-flight resolvers
both inject deterministic context into the spawn prompt; they
differ only in *what they resolve* (resolvers: per-prompt
facts like path/agent/time; primers: per-domain conventions
like rules/templates/checklists).

* Roles by core agent

*Summary.* Today three core agents own primers: =@curator=
(wiki conventions, including report authorship), =@tracker=
(dev-tracker entries), =@agentsmith= (new-agent shape). The
roster grows when a new domain earns a steward — security
review, vault hygiene, data-analyst chart authorship are all
candidate future namespaces.

*Expanded.*

| core agent     | primer namespace        | what it teaches                                                                              |
|----------------+-------------------------+----------------------------------------------------------------------------------------------|
| =@curator=     | =wiki-authorship=       | Rule 2b, link forms, fresh UUID, 00-index.org integration, =link_wiki_files.py= verifier      |
| =@curator=     | =agent-report=          | the uniform =docs/notes/= report structure (see [[id:43e1b335-656b-45ba-8d6d-7d9b9f2e9c4d][roadmap]] § Phase 24.5)                          |
| =@tracker=     | =dev-tracker-entry=     | property block, Recommended ship order, Connections, Risks pinning                            |
| =@agentsmith=  | =new-agent=             | persona shape, triggers, =model_role=, capability declaration, registration site               |

Future candidates (none shipped):

| candidate steward      | primer namespace        | rationale                                                                                     |
|------------------------+-------------------------+-----------------------------------------------------------------------------------------------|
| =@gardener=            | =vault-hygiene=         | when a specialist edits =~/org/= it should know the orphan-link / staleness conventions       |
| =@librarian= (planned) | =metadata=              | task-instruction-prefix conventions, embedding hygiene, FILETAGS taxonomy                     |
| =@data-analyst= (spec) | =chart-yaml=            | once the [[id:a2af071e-8244-444d-8954-61317cc1ec4d][Superset]] semantic-layer registry stabilizes — chart-YAML shape promotion target  |

Adding a steward is *not* the same as adding a primer
namespace. A namespace can be owned by an existing steward
(=@curator= already owns two). Promoting a namespace to a new
steward is justified only when the volume / breadth of rules
in that domain crosses the bar that put =@curator= /
=@tracker= / =@agentsmith= on the meta roster (= triggers a
roster row, = earns its keep at gates 1/2/3).

* Composition with existing primers

*Summary.* The orientation pattern composes with — does not
replace — three existing context-injection mechanisms:
[[file:../../.opencode/AGENTS.md][AGENTS.md]] (project-level primer regenerated on launch),
[[id:3ed81ee4-e28d-4daf-87fb-c1645b58a05c][recipes]] (proxy-time pre-fetch for known intent classes), and
the upcoming [[id:9096622a-689c-4bb1-8e32-1654bce48d1c][Phase 24.1]] resolver registry (per-prompt
deterministic facts). Each operates at a different level: project,
intent, prompt, domain. They stack; nothing in the orientation
pattern duplicates them.

*Expanded.*

| mechanism                 | grain               | when it fires                       | shape                            |
|---------------------------+---------------------+-------------------------------------+----------------------------------|
| =AGENTS.md=               | project             | host launch (regenerated)            | static doc, manually authored    |
| Recipes (Phase 22 v2)     | intent class        | prompt matches recipe trigger        | manager pre-fetch + agent narrate |
| Resolvers (Phase 24.1)    | per prompt           | every =delegate()= call              | parallel pure functions, ~80ms   |
| *Orientation primer*      | per domain           | specialist explicitly requests        | deterministic resolver, on demand |
| Manifest (this page)      | per spawn            | every specialist spawn               | one short paragraph              |

Concretely, a specialist spawned to "draft a wiki page about
=auto-embedder=" would, in order:

1. Read the project-wide =AGENTS.md= primer at host launch
   (already loaded into the host's context).
2. Receive its task prompt with the manifest pre-pended.
3. The Phase 24.1 resolvers fire: =RepoResolver= establishes
   the repo root, =PathResolver= confirms =docs/wiki/= exists,
   =AgentResolver= notes =@curator= as the relevant steward.
4. The specialist, prompted by the manifest, calls
   =primer("wiki-authorship")= before writing.
5. The primer returns Rule 2b, link forms, the UUID command,
   and the verifier step. Specialist drafts conformant.
6. (Future, not in scope of this page.) The
   [[id:9096622a-689c-4bb1-8e32-1654bce48d1c][Phase 29 self-coded tools]] loop watches the audit log; if
   primer fetches consistently precede successful artifact
   writes, the primer fetch becomes a deterministic step in
   the recipe for that intent class — collapsing what's a
   per-spawn fetch today into a zero-round-trip pre-fetch.

[[id:7dcbce8b-0941-48ec-a17d-c623ba00883a][Side-quests]] is the
canonical worked example of a specialist consuming all five
mechanisms at once: AGENTS.md is already in the host context,
the manifest pre-pends at spawn, resolvers fire per-prompt,
and the specialist explicitly fetches =primer("agent-report")=
(plus =primer("dev-tracker-entry")= and =primer("wiki-authorship")=
if the work threads to those domains). The receipt convention
=(report_path, Objective_line)= flows back to the captain when
the specialist finishes. See that page for the spawn → orient
→ work → report → receipt cycle.

[[id:739868a9-f62c-43de-ac1d-1671d483a2c1][Standing orders]]
adds a sixth mechanism on the same composition seam: every
spawn-prompt's manifest gains a =standing_orders_digest= line
listing user-authoritative decisions by =(namespace, key,
version)=. The specialist fetches the body for any namespace
its task touches — same lazy-loading discipline as primers,
different write path (captain authors, primers don't). Where
primers serve *conventions* (deterministic, source-file
backed), standing orders serve *decisions* (user-authored,
DB-backed, eligible for graduation to source files via
@curator's promotion sweep).

* Risks and boundaries

*Summary.* Three risks worth pinning before starting: primers
that go stale silently, primers that the specialist forgets to
fetch, and primer namespaces that proliferate beyond the
steward roster's ability to maintain them. All three have
mitigations that fall out of the lazy-loading policy + the
deterministic-resolver shape.

*Expanded.*

- *Stale primers.* A primer that paraphrases a wiki rule
  drifts from the rule the moment the rule edits. Mitigation:
  primers are *resolvers that read the source*, not paraphrases.
  =wiki-authorship= reads =wiki-conventions.org= at call time;
  =dev-tracker-entry= reads the property-block conventions from
  =dev-tracker.org=. Drift becomes mechanically impossible.

- *Forgotten fetches.* The specialist may write a wiki page
  without calling =primer()=. Mitigation A: the manifest
  includes the call as a *prerequisite* phrasing ("call
  primer(…) *before* writing"). Mitigation B: a tool-failure
  recovery hook (Phase 24.2 family) on the wiki-write path
  that detects a missing fetch and returns a recovery
  suggestion rather than letting a non-conformant draft land.

- *Primer sprawl.* Over time the namespace list grows past
  what a manifest can fit. Mitigation: namespaces are owned
  by stewards, and a steward's namespace count is bounded by
  the same rules that bound the roster (gate-1/2/3 must hold).
  When it stops holding, the namespace either folds into a
  bigger one or earns a new steward (the agent rationalization
  pattern from agents.org).

- *Primer-as-LLM-call.* The pattern explicitly forbids primers
  from being LLM calls — that would put orientation in the
  same anti-pattern Phase 24's design rule rules out. Primers
  are deterministic resolvers. If a primer would benefit from
  reasoning, the resolver is the wrong shape; the right shape
  is to encode the reasoning as a rule and emit it
  deterministically.

* Status

*Summary.* Pattern canonized 2026-05-04. Manifest format and
namespace list above are the load-bearing claims. Implementation
queued as *Phase 24.5 — Orientation primer registry* alongside
the rest of the supervision trinity in =dev-tracker.org=.
=docs/templates/agent-report.org= is the first artifact the
=agent-report= primer namespace points at; the slice/wiki
reports at =docs/notes/2026-05-04-promotions-{slice,wiki}-report.org=
are the canonical exemplars.

*Expanded.* Implementation order proposed:

1. *24.5a — Manifest scaffold.* Static string in
   [[file:../../org_llm/orchestration.py][=org_llm/orchestration.py=]] built from the steward roster.
   Injected into every =delegate()= sub-LLM call. ~half-day.
2. *24.5b — Primer resolver package.* =org_llm/primers/= with
   =wiki_authorship.py=, =dev_tracker_entry.py=,
   =agent_report.py=, =new_agent.py=. Each is a pure
   =primer(name) → str= reading authoritative source files.
   ~1d.
3. *24.5c — MCP tool.* =primer(namespace)= registered in
   =mcp_server.py=, capability =read.wiki=. Specialists call
   it like any tool. ~1h.
4. *24.5d — Always-on inline rule list.* Rule 2b is the seed;
   any rule short + universal enough joins. Bar is high. Open.

Lazy-loading is the canonical policy this pattern instantiates;
see [[id:cf466e65-0fa1-4f23-8103-8205f67a6ca3][lazy-loading]] for the broader claim ("load context when
relevance is established, not on the chance it'll be needed")
and other places it shows up (recipes, vault facts, =/sys*=
short-circuits).
