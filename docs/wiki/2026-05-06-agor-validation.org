*Expanded.* Worktree: =019dfc19-719e-7421-bac0-08f8694bb5d1= at
=/home/daniel/.agor/worktrees/local/org-llm/bridge-crew-validate-2026-05-06=
(created via REST per bug #1). Materializer wrote 21 files, 8 dirs;
=org_llm.bridge_crew.BRIDGE_CREW= equality check across all 7 personas
× SOUL/IDENTITY/USER → all True. Phase B blocked from running a live

| Check                                        | Expected if wired | Actual         |
|----------------------------------------------+-------------------+----------------|
| =GET /worktrees/<id>.custom_context=         | populated         | field absent   |
| =agor_assistants_list= MCP                   | 1+ entries        | =total=0=      |
| =agor_assistants_{create,update}= MCP tool   | exists            | does not exist |

*The gap.* On-disk =.agor-assistants/<handle>/= is /our convention/,
not Agor's. v0.17.3 stores assistants in =worktree.custom_context.assistant=
(per =AssistantConfig= in bundled =repo-*.d.ts=); the only registration
path today is the in-app UI — there's a read-side MCP tool
(=agor_assistants_list=) but no write-side.

*v0.1 follow-up shape:* extend =bridge_crew.materialize()= to also
=PATCH /worktrees/<id>= with =custom_context.assistant={soul,
identity, user, name, description}= per persona; petition upstream
for =agor_assistants_create= MCP tool. With that, the read tool
populates and zone-triggered sessions inherit the persona role.

*Surprise.* The =bridge_crew.py= docstring is accurate verbatim — and
=agor_assistants_list= already exists, so only the write-side is
missing. The v0.1 ask is a single upstream patch, not a re-architecture.
