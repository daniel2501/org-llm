* Summary

*Summary.* R26 is the round where the bench stops being just a
measurement instrument and starts compounding wins: K20 deploys
via Together /serverless multi-LoRA/ at the base-model per-token
price (no $5.49/hr dedicated endpoint, no idle cost), the harness
gains real Emacs through =org-mcp= + =org-roam-mcp= + =vault-mcp=
inside the specialist tool surface, the test pool grows by 10
elisp/org-shape tests (BK6-BK15) that exercise capabilities the
bench has never measured, and ~$120-140 of cloud headroom is
allocated against high-leverage infra (Spheron H100 self-host,
Modal-Kimi K2, OR top-up reserve). The R25 verification gap (3 of
11 patches were dead-code) gates everything: each R26 boost ships
with an end-to-end behavioral probe before R26 launches.

*Expanded.* R15-R25 surfaced a clean operating model — K1+K8 FOSS
frontier at $0.0006/qpt, 59x layer1-matched moat over Claude — but
also a stack of unfinished work: K8 generalization unresolved, K20
endpoint blocked, MCP integrations un-wired, the harness's verifier
still regex-only, BK1-BK5 only firing on K1+K5 due to the top-3
selector bug, and the elisp/org-mode dimension of org-llm's actual
purpose (Emacs distro, not a generic agent harness) almost entirely
absent from the test pool. R26 spends the spend-headroom on
infrastructure that converts the static frontier into a moving one
— self-hosting kills broker variance, multi-LoRA makes per-handle
adapters cheap to ship, and Emacs-shaped tests close the gap
between what we measure and what org-llm is actually for. The five
R26 boosting bets in §1 each compound: serverless K20 enables A/B
without idle cost; MCP gives the harness real semantic verification;
new elisp tests reveal whether K1's lead survives off the bench's
historical wiki-edit comfort zone.

* 2. Re-analysis insights — what NEW learning came from re-reading

*Summary.* Four insights survive a careful re-read of R25 docs that
the headline syntheses understate: K8 is /not/ confirmed to
generalize (it's confirmed to recover on B1, period); the R25
patch-verification gap is structural, not incidental; Layer-BK
actually fired (R24's blocker is genuinely resolved); and the
Claude moat is *59x like-for-like*, not the headline 22x.

** Insight A — K8 generalization is unresolved, not confirmed

[[file:docs/wiki/2026-05-08-r25-case-studies.org]] §"Case study 5"
explicitly corrects the headline: "*shifts the verdict from
durable second seat to B1-specific recovery — confirmed;
cross-task generalization unresolved.*" The 4 force-listed K8
Layer-2 cells (B5, B7, B11, B25) all silent_noop'd because the
top-3 selector bug excluded K8. R25's K8 evidence is *25 successful
B1 cells + 4 Layer-2 silent_noops*. The go-forward-config doc §3
"K8 on DeepInfra is Champion" overstates what the data supports.

*R26 implication.* Don't promote K8 to "general frontier seat" yet.
Per-cell K8 must run B11 + B26 at n≥5 each /after/ the top-3
selector fix lands, before any "K8 generalizes" claim. This is
gate P0-1 + gate "K8 promotion" combined.

** Insight B — 3 of 11 R25 patches were ineffective: structural verification gap

The R25 case-studies doc §"Cross-cutting lessons → harness is the
bottleneck" + the synthesis doc §"R25's three INEFFECTIVE patches"
agree on a pattern: =_R25_VARIANT_MAX_TOKENS= was defined and never
read; =WALL_CAP= shipped a label not a kill; K33's "72b" slug
duplicates K11. *Three independent fixes for related problems all
failed independently.* The =_r25_design_patch.py= script is "too
thin to verify behavioral effect" ([[file:docs/wiki/2026-05-08-r25-case-studies.org]]
§Case Study 3, lesson 1).

*R26 implication.* Every patch in =_r26_design_patch.py= ships with a
=verify_patch_landed()= probe that exercises the behavior change
end-to-end (e.g. send a 30k-prompt-completion request, assert max
tokens limited the output to ≤4k; spawn a 500s-sleep cell, assert
WALL_CAP fires within 410s). No patch lands without its probe
returning OK. This is non-negotiable: skipping it is how R25
shipped 3 dead patches.

** Insight C — Layer-BK actually fired, R24 blocker fully resolved

[[file:docs/wiki/2026-05-08-r25-synthesis.org]] §"Layer-BK fired
with target_files fix (10/10)" confirms the BK1-BK5 long-horizon
data is now real, despite the K8/K11/K17 missing-coverage gap.
*K1 dead-even with K5 on BK1/BK2/BK4*, K5 edges BK5, both abstain
BK3. This is genuinely new evidence that FOSS handles long-horizon
delegation, not just atomic tasks. The implication for R26 is that
BK1-BK5 should now be Layer 1, not Layer-BK after-the-fact (per
[[file:docs/wiki/2026-05-08-r25-case-studies.org]] R26 rec #20).

** Insight D — Claude moat is 59x layer1-matched, not 22x headline

[[file:docs/wiki/2026-05-08-r25-synthesis.org]] §"Headline numbers"
shows the moat /grew/ from R24's 48x to R25's 59x on the
layer1-matched slice. The 22x mix-aggregate headline is a
layer-allocation artifact (K5 ran more layer_bk + layer2 cells
where Claude scores higher per dollar). *FOSS pulled further ahead*,
the headline understated the win. This affects R26 messaging
(don't say "moat shrunk"), and informs the Picard-delegation
section of the go-forward config: K1+K2 is sufficient for
multi-file refactor; Claude escalation is no longer
bench-indicated.

* 3. Together Serverless Multi-LoRA pivot — kill the dedicated-endpoint plan

*Summary.* The R25 plan called for a dedicated H100 endpoint
($5.49/hr, =min_replicas=1=) to serve K20-foss-distill. Together's
serverless multi-LoRA support (released early 2025) makes this
unnecessary: fine-tuned LoRA adapters are served at the
*base-model per-token price* with zero idle cost. K20 deployment
becomes a 30-minute config change, not a $130-200/month commitment.
*Caveat (reviewer-verified):* the cited blog only names "Llama
3.1" and "Qwen 2.5" as supported base-model families — it does
NOT explicitly list =Qwen3-Coder-30B-A3B-Instruct=. The fallback
chain below is therefore load-bearing, not optional, until R26
preflight confirms the K20 base model is in the multi-LoRA roster.

*Expanded.* Source:
https://www.together.ai/blog/serverless-multi-lora-fine-tune-and-deploy-hundreds-of-adapters-for-model-customization-at-scale.
The blog explicitly covers the exact use case: register a LoRA
adapter, query the base-model endpoint with =model= = adapter ID,
pay base-model rates per token. No reservation, no idle, no
per-adapter dedicated infra. *The blog also leaves three things
under-specified*: (a) exhaustive list of supported base models
(only Llama 3.1 and Qwen 2.5 named — Qwen3-Coder family NOT
confirmed); (b) whether adapters trained via Together's own
fine-tune API are auto-registered or require a separate deploy
step; (c) minimum LoRA rank / target-module compatibility rules.
R26 preflight (§3 implementation step 1) MUST resolve all three
before launch, because the R25 LoRA training already shipped
=ft-985a8266= against =qwen3-coder-30b-a3b-instruct= and a
"base-model not supported for serverless multi-LoRA" failure
would force the fallback chain below.

** Implementation

1. *Preflight: confirm base-model serverless multi-LoRA support.*
   GET =https://api.together.xyz/v1/models= and grep for
   =qwen3-coder-30b-a3b-instruct=; check the model card for
   =serverless: true= AND =supports_lora_adapters: true= (or
   equivalent flag). If absent, hard-skip §3 and route to fallback
   chain. Acceptance: a smoke-test inference call to the base model
   must succeed AND a "list adapters" call (or equivalent) for the
   base must return a non-error response.
2. Verify =ft-985a8266= (K20 v1) is "completed" and adapter weights
   are accessible via =POST /fine-tunes/{id}/download= or attached
   to a serverless deployment ID. *Re-check rank + target_modules*
   metadata against Together's serverless multi-LoRA constraints
   (the blog references "Configurable LoRA rank" and "Layer-specific
   adapter application" but does not publish numeric thresholds).
3. Register the adapter via Together's serverless adapter API
   (=together fine-tune deploy --adapter ID= or REST equivalent).
4. Add K20 to =_round26_dials.py=:
   #+begin_src python
   "K20-foss-distill-v1": {
       "model_id": "qwen3-coder-30b-a3b-instruct",
       "lora_adapter": "daniel2501/k20-foss-distill-v1",
       "broker": "together-serverless",
       ...
   }
   #+end_src
5. Wire =_chat_completions= to pass the adapter ID via Together's
   serverless multi-LoRA query schema (=model="<base>:<adapter>"=
   or equivalent based on the API spec).
6. Probe behavioral effect — send a known training-distribution
   prompt; assert response shape differs from K1-base. This is
   the §2-B verification gate applied to K20.

** Fallback chain

If serverless multi-LoRA is unavailable for our base model
(=qwen3-coder-30b-a3b-instruct=), fall back to:
1. Predibase serverless fine-tuned LLMs.
2. DigitalOcean serverless fine-tuned (similar offering).
3. Doubleword Takeoff Serverless LoRA.
4. Spheron dedicated H100 PCIe at $2.01/hr (cheaper than Together's
   $5.49/hr dedicated; only used if every serverless option fails).
   *Reviewer note:* Spheron pricing/availability is not cross-checked
   in any prior org-llm doc; treat the $2.01/hr figure as unverified
   until R26 preflight confirms a working endpoint stand-up against
   the listed pricing page. RunPod ($1.39-2.99/hr) is the proven
   fallback per PM2 in =bench-arc-post-mortems.org= — keep RunPod
   ahead of Spheron in the fallback ordering until Spheron has a
   one-cell smoke result.

* 4. MCP server integrations — concrete shortlist

*Summary.* Five MCP servers align with org-llm's goals at clearly
different leverage-per-LOC ratios. Top priority is =org-mcp= +
=emacs-mcp-server= (rhblind, pure-elisp) — together they give the
specialist tool surface a real Emacs to drive, which unlocks
semantic verification (replaces regex post-hoc with editor-side
truth) and enables the new BK6-BK15 elisp tests in §6.

*Expanded.* MCP integration matters for R26 in two senses: (a) /the
harness/ uses MCP servers as additional verifiers (gold-standard
semantic check on every cell), and (b) /org-llm itself/ ships MCP
clients so user-facing agents reach the same elisp/org tools the
bench measures against.

*emacs-mcp-server (rhblind) v0.7.0 was released 2026-05-04* — four

caveats: (a) rhblind v0.7.0 is recent enough that breaking changes
between R26 launch + R27 follow-up are plausible; pin to a tag,
not =main=. (b) =org-roam-mcp= activity is harder to date (only 14
commits, no recent timestamp on home page); recommend a one-cell
smoke before relying on it for B1 grounding.

** Top-3 integration plans

*** =org-mcp= (laurynas-biveinis)

*Why first.* Direct mapping to org-llm's task verbs (capture,
refile, agenda, todo-state, deadline). The MCP tools become
specialist tool-surface entries; the harness gates B11/B20/B26 on
"did the org-mcp action succeed" rather than "did the regex see
the heading appear in diff".

*Integration LOC.* ~120 (subprocess launcher + tool-call adapter
in =org_llm/specialist.py=).

*Acceptance gate.* B11 (DEC draft) cell run via org-mcp's
=add-heading= primitive returns a parseable element with the right
property drawer, vs. current regex match on diff.

*** =emacs-mcp-server= (rhblind, pure-elisp variant)

*Why second.* Pure elisp, Unix-socket transport, no Python bridge.
Every BK6-BK15 elisp/org test in §6 needs a way to ASK Emacs "is
this defcustom valid; does this defface byte-compile; does this
ert-deftest run green?" The rhblind server answers each via JSON-RPC
to a real running Emacs.

*Integration LOC.* ~80 (start headless emacs daemon + connect
client per cell).

*Acceptance gate.* B25 (write new elisp) cell verifier returns
=byte-compile-file= success + =ert-run-tests-batch= clean exit.

*** =org-roam-mcp= (aserranoni)

*Why third.* Provides =search_nodes= / =get_node= / =get_backlinks=
to specialist agents. Grounds @atoz cross-link audit (B1) in the
real vault state instead of a frozen prefetch dict. R26 hypothesis:
@atoz with org-roam-mcp produces fewer fab UUIDs because the
vault's actual UUIDs are query-able.

*Integration LOC.* ~60 (just the MCP client wiring; server is upstream).

*Acceptance gate.* B1 fab_uuids count drops to 0 across n≥10 K1 cells.

** Defer to R27+

- =gptel + mcp.el=: client-side; great for user-facing chat, not
  bench-critical.
- =vault-mcp=: semantic search RAG. Useful but org-roam-mcp covers
  the bench's @atoz needs for B1.
- =mcp-local-rag= / =ClawMem= / vivekhaldar variant: redundant with
  the top-3 once those land.

* 6. New elisp + org-mode tests (BK6-BK15)

*Summary.* Current bench fixtures are largely wiki-edit shaped
(B1/B5/B11/B20) plus 5 BK long-horizon code/wiki tasks. The elisp
+ org-mode dimension that org-llm /actually targets/ as a product
is barely tested. R26 adds 10 new BK-level tests focused on ERT
authoring, org-babel, org-element parsing, org-roam node ops,
defcustom/defface authoring, org-table validation, capture
templates, and org-id management. Each ships a deterministic
verifier (Emacs-batch + ERT, or org-element parse + assertion).

*Expanded.* These tests measure what current bench misses: the
specialist's ability to write Emacs-shaped artifacts that
*actually compile and run inside Emacs*. The headless-Emacs
verifier (P6 from R25 design, §7 below) makes the verifier
gold-standard. The =emacs-mcp-server= (rhblind) integration from §4
is the in-loop validator. Tests written so the specialist must
edit a fixture file inside the worktree, then the verifier runs
=emacs --batch= against the worktree to score.

** Acceptance + scoring

Each task scores via:
- /Primary/: validator command exit 0 (binary 0/N where N = task
  difficulty weight, e.g. BK6=20, BK10=15, BK13=10).
- /Mech/: same as primary for these tests (the validator IS the
  gold-standard mech check).
- /Quality lint/: standard org/elisp lint (existing
  =quality_lint.py= + new tree-sitter validator from §7).

** Why these tests

1. *Org-llm IS an Emacs distro* — the [[file:docs/wiki/2026-05-08-org-llm-go-forward-config.org][go-forward-config]] §1
   bridge-crew matrix maps personas to tasks but the tasks
   themselves don't exercise Emacs semantics. BK6-BK15 close that.
2. *Reveals real-world ceiling* — K1's $0.0006/qpt holds on
   wiki/atomic shapes. Does it hold on /elisp authoring/? BK10
   + BK14 will tell us.
3. *Validates MCP integration leverage* — BK6/BK11/BK13 all run
   cleaner with =emacs-mcp-server= than with =emacs --batch=
   subprocess (no startup overhead, persistent state). Gives
   the §4 integration concrete payoff numbers.
4. *Composable with §7 verifiers* — every BK6-BK15 test feeds
   directly into the headless-Emacs cell verifier (P6 from R25
   design); no separate verifier infrastructure needed.

** Sample size + cost

n=8 per test × 10 tests × ~$0.02/cell average (K1) = *~$1.60* per
full BK6-BK15 sweep. Trivially affordable.

* 8. Areas of weakness still unaddressed

*Summary.* R25 evidence reveals four dimensions the bench still
cannot measure: real multi-day refactor (BK1-BK5 are 1-session
tasks), editor-state correctness (verifier is filesystem only),
persona-specific quality (no @atoz vs @data head-to-head data),
and user-feedback-loop scoring (no human-in-the-loop signal).

** Weakness 1 — Real long-horizon multi-day refactor

BK1-BK5 are *one-session* tasks: prefetch + edit + verify, all
inside ~5 min wall. Real org-llm work spans multiple sessions —
user starts a refactor on day 1, comes back day 3 to continue.
Bench has zero coverage of this.

*R27 prep.* Design BK16-BK20 as /multi-cell sequential/ tests
where cell N's worktree state is the input to cell N+1's brief.
Validator runs against final-cell worktree.

** Weakness 2 — Editor-state correctness

Current verifier is filesystem-only: did the file change as
expected. Doesn't catch "file is fine but Emacs can't open it
without warnings" or "the org-element tree is inconsistent in a
way Emacs hides but breaks =org-roam-db-sync=." The §7 headless-
Emacs verifier is /partial/ coverage; full editor-state needs a
running Emacs that the bench drives interactively. =gptel= +
=mcp.el= integration (R27) closes this.

** Weakness 3 — No persona-specific quality data

The go-forward-config doc §1 maps personas (@atoz, @data, etc.) to
recommended models. *No bench round has actually compared @atoz vs
@data on the same task with model held constant.* All R25 cells
used @data persona for code tasks and @atoz for wiki — the persona
variable is conflated with task family.

*R26 spike.* Add 10 cells: same task (B11), same model (K1), 5
cells @atoz brief + 5 cells @data brief. Score difference =
persona effect size. Cheap, decisive.

** Weakness 4 — No human-in-the-loop signal

Quality_lint + tree-sitter + headless-Emacs verifier all measure
correctness, not /goodness/. Whether a B11 DEC draft is
"compelling" or "well-structured" is currently unmeasured. Claude
moat (59x) is on correctness; the moat on /quality of writing/ may
be different.

*R28+ direction.* Add =scripts/_human_review_queue.py= that pushes
top-N cells per round to user review (thumbs-up/down). Aggregate
into a "human quality score" alongside primary/mech/lint. Rare
samples (n=10/round) but anchors the bench in real subjective value.
