* Summary

*Summary.* This primer is what Bridge Crew specialists read to know which
=org-llm <group> <verb>= commands to reach for during their work. CLI use
via Bash is reliable for FOSS specialists (round-3 R3-Hard verified shell
ops); MCP =tool_use= is not (round-6 finding). So when an agent needs
deterministic data — facts about the vault, agent registry, code state,
metrics, dbt pipeline, captain's log — they should *invoke the CLI*, not
ask another agent to look it up.

*Expanded.* Each agent gets the per-persona-relevant subset of this
primer injected into their system prompt. The full surface is too big
(~70 subcommands across 14 sub-typers) to dump verbatim; per-agent
distillation gives each specialist the verbs they'd actually reach for.
Pair with [[file:org-mode-per-agent-primer.org][org-mode-per-agent-primer.org]] (L1b) for org-mode-specific
expertise per persona.

* The general rule

When you (any specialist) need information from the org-llm system,
*prefer the CLI* over LLM reasoning:

#+begin_example
# bad: ask another agent or guess
# good: just run the verb
$ org-llm <group> <verb> [args]
#+end_example

CLI output is deterministic, free, and instant. Every CLI call you make
is a CLI call you don't have to make via expensive LLM inference.

* Anti-patterns (don't do these without explicit user authorization)

| ✗ | Why |
|---+-----|
| =org-llm tracker init= unsolicited | Mutates the user's vault state |
| =org-llm grant-root= / =grants edit= | Permission escalation |
| =org-llm dbt build / run= against prod | Runs the data pipeline; touches DB |
| =org-llm bridge-crew materialize= | Writes assistant config files |
| =org-llm self edit= / =rollback= | Mutates your own persona |
| =org-llm db= with mutating SQL | Writes to org-llm's state |

If a task implies one of these, *ask the harness or the user first*. Read-only
verbs (=list=, =show=, =review=, =diagnose=, =status=, =describe=, =query=) are
always safe.

* Worked example — @atoz uses CLI to bootstrap a cross-link audit

Task: "audit cross-links on docs/wiki/literate-tools.org."

Without CLI:
1. Read the file (LLM tokens)
2. Search for canonical owners (LLM tokens)
3. Hope the IDs are right (LLM tokens)

With CLI (cheaper + more reliable):
#+begin_src bash
# Step 1: known IDs (deterministic, instant, free)
grep -h "^:ID:" docs/wiki/*.org | awk '{print $2}' | sort -u > /tmp/known_ids.txt

# Step 2: target page mentions (deterministic)
grep -nE "Phase|DEC-|\\.org" docs/wiki/literate-tools.org

# Step 3: pull canonical owner for a specific concept
org-llm context show <node-id>

# Step 4: now apply edits with that pre-fetched intelligence
#+end_src

The deterministic steps replace ~3000 LLM tokens of "read + reason"
with ~50ms of shell. The LLM only does what only the LLM can: judge
which mention should link to which canonical owner.
