*finding-2 — over-eager recipe match.* The =count_across_vault=
trigger regex includes the word =frequency=, which fires on "tag
frequency", "exercise frequency", and any other "by frequency"
phrasing — not just on event-count questions. The runner
tokenised "top tags frequency" → built a nonsense regex →
returned 0 hits. =frequency= should be REMOVED from the trigger
words. Trigger words for =count_across_vault= should be:
counting *events* (=how many times=, =how often=, =count of=,
=tally=, =total=) — never bare =frequency=, which is too generic.

agent gave up on the pre-fetch (saw 0 hits → didn't trust it)
and emitted =org-llm_count_matches({...})= as PROSE in its
response. The current =_TOOL_CALL_PATTERNS[3]= only matches
=name{...}= (curly braces); this paren shape =name({...})=
slips through. =_extract_markdown_tool_call= also misses (no
```json fence). User sees a literal fake-tool-call string in the
chat. Add a paren-form pattern, or detect bare
=name(\{...\})= and treat the inner JSON as the args.

Severity of both: medium. Workaround: avoid the word
"frequency" when asking about tags; ask "what are my top 10
tags?" instead, which doesn't match the recipe and routes

* Thought-tracking analysis (Phase 22.5a)

The user's standing ask: *manager watches agents at zero
performance cost*. Today's implementation captures the agent's
narration as a =narration= manager-log entry, but ONLY for
turns where an orchestration recipe matched. Implications:

| turn shape                              | tracked?  | gap                                                  |
|-----------------------------------------+-----------+------------------------------------------------------|
| recipe match → pre-fetch → narrate      | ✓ yes     | full trace: recipe / tool_call / delegate / narration |
| recipe match (advisory, no runner)      | ✓ partial | recipe + delegate logged; narration captured        |
| no recipe (raw cloud forward)           | ✗ no      | nothing in manager-log; only the chat surface       |
| no recipe + LLM-driven tool_calls       | ✗ no      | tool_calls visible only in opencode session storage |

*finding-4 — non-orchestrated turns are invisible to the
manager log.* Today the user has no audit trail for "the agent
did stuff" turns that bypass the recipe layer. To track every
turn, =orch_buf= would need to fire on EVERY chat-eligible
request, not only when =_org_llm_recipe= is set. Worth
~5 lines in =llm_proxy.py= but watch the cost: every chat turn
already buffers nothing on the local-forward path; this would
add a small accumulator. Mostly free if we keep the buffer
capped at e.g. 8KB and only extract the head.

Recommendation: add a =proxy_capture_all_narrations= knob
(default false). When true, every cloud / local turn captures a
=narration= entry, not just orchestrated ones. Pairs naturally
with Phase 22.5b (explicit =<thinking>= tag extraction).

* Optimization opportunities

Code-review pass over today's diffs while the test runs:

** opt-1 — title-gen turns trigger redundant recipe pre-fetch

(See finding-1.) The =recent_activity_summary= recipe fires
twice per user turn — once for the actual answer, once for
opencode's automatic title generation. Cost: ~150ms of local
DB queries each title-gen request, no extra cloud calls but
tangible CPU on a busy session.

Fix shape: detect title-gen requests by checking the system
prompt for "summarize the conversation" + tiny =max_tokens= +
no =@<agent>= tag in the user content. Skip the recipe block
entirely.

** opt-2 — pre-fetch block dedupes don't cap noise SQL-side for nodes only

In =recipe_runner.py::_run_recent_activity_summary= the
captains-log filter is at the SQL layer (=Node.tags.like(…)=)
which is great. The file-level captains-log filter is
*post-query Python* (=base.startswith("captains-log")=). Both
work, but the file scan retrieves up to 200 rows from disk to
get the user-content 25 — wasted I/O.

Fix shape: also add the SQL filter for =File=
(=File.path.notlike("%captains-log%")=) and drop the limit to
~50. Saves 150 disk reads per recipe fire.

** opt-3 — narration buffer accumulates the whole stream

=orch_buf= is unbounded — captures every byte of the cloud
response. For a 5-paragraph reply that's tens of KB, all to
extract a 600-char excerpt. Memory pressure is irrelevant on
modern hardware, but the join + parse at the end takes O(N).

Fix shape: cap orch_buf at e.g. 16KB and stop appending after
that. The narration excerpt is truncated to 600 chars anyway
(=result_excerpt= column limit + the explicit slice), so we
only need enough bytes for the FIRST 600 chars of content
text. Most responses fit easily in 16KB.

** opt-4 — recipe runner's regex is rebuilt per turn

Each turn re-parses =_phrase_to_regex= from scratch, then
=org_count_matches= recompiles the resulting regex. Two
phases, both ~µs each, but for a hot path this is wasteful.

Fix shape: memoize =_phrase_to_regex(phrase)= on the
=phrase= input — same phrase always yields the same regex. A
=functools.lru_cache(maxsize=64)= takes 5 keystrokes.

** opt-5 — manager log JSONL writes are synchronous

=db.log_crew_action= writes to manager-log.jsonl synchronously
(open / append / close). For orchestrated turns we do this 3-4
times in quick succession (recipe → tool_call → delegate →
narration). On a slow disk this would serialise 4 fsyncs per
turn (10-40ms). Today's spinning rust would notice; SSDs
won't.

Fix shape: defer narration writes to a background thread (the
write order already preserves causality if we keep recipe /
tool_call / delegate synchronous and only narration deferred).
