* Optimization opportunities

Code-review pass over today's diffs while the test runs:

** opt-1 — title-gen turns trigger redundant recipe pre-fetch

(See finding-1.) The =recent_activity_summary= recipe fires
twice per user turn — once for the actual answer, once for
opencode's automatic title generation. Cost: ~150ms of local
DB queries each title-gen request, no extra cloud calls but
tangible CPU on a busy session.

Fix shape: detect title-gen requests by checking the system
prompt for "summarize the conversation" + tiny =max_tokens= +
no =@<agent>= tag in the user content. Skip the recipe block
entirely.

** opt-2 — pre-fetch block dedupes don't cap noise SQL-side for nodes only

In =recipe_runner.py::_run_recent_activity_summary= the
captains-log filter is at the SQL layer (=Node.tags.like(…)=)
which is great. The file-level captains-log filter is
*post-query Python* (=base.startswith("captains-log")=). Both
work, but the file scan retrieves up to 200 rows from disk to
get the user-content 25 — wasted I/O.

Fix shape: also add the SQL filter for =File=
(=File.path.notlike("%captains-log%")=) and drop the limit to
~50. Saves 150 disk reads per recipe fire.

** opt-3 — narration buffer accumulates the whole stream

=orch_buf= is unbounded — captures every byte of the cloud
response. For a 5-paragraph reply that's tens of KB, all to
extract a 600-char excerpt. Memory pressure is irrelevant on
modern hardware, but the join + parse at the end takes O(N).

Fix shape: cap orch_buf at e.g. 16KB and stop appending after
that. The narration excerpt is truncated to 600 chars anyway
(=result_excerpt= column limit + the explicit slice), so we
only need enough bytes for the FIRST 600 chars of content
text. Most responses fit easily in 16KB.

** opt-4 — recipe runner's regex is rebuilt per turn

Each turn re-parses =_phrase_to_regex= from scratch, then
=org_count_matches= recompiles the resulting regex. Two
phases, both ~µs each, but for a hot path this is wasteful.

Fix shape: memoize =_phrase_to_regex(phrase)= on the
=phrase= input — same phrase always yields the same regex. A
=functools.lru_cache(maxsize=64)= takes 5 keystrokes.

** opt-5 — manager log JSONL writes are synchronous

=db.log_crew_action= writes to manager-log.jsonl synchronously
(open / append / close). For orchestrated turns we do this 3-4
times in quick succession (recipe → tool_call → delegate →
narration). On a slow disk this would serialise 4 fsyncs per
turn (10-40ms). Today's spinning rust would notice; SSDs
won't.

Fix shape: defer narration writes to a background thread (the
write order already preserves causality if we keep recipe /
tool_call / delegate synchronous and only narration deferred).

** New findings

*** finding-6 — scope-modifier phrases break the count regex
While testing #2 ("how often have I exercised across the vault?"),
=count_across_vault='s phrase tokeniser folded "across the vault"
into the regex as content tokens:

#+begin_example
(?i)(\[X\]|\bDONE\b).*?\b(?:exercis|exercised|exercising|exerciss)
(?:.{0,12}\bacross\b.{0,12}\bvault\b)
#+end_example

→ 0 hits despite the user clearly having exercise entries.

Sibling of finding-5 (time-modifier "this year" — same shape).
Both surface the SAME root cause: the tokeniser strips =:agent:=
prefixes + a small set of stop words, but doesn't strip
*scope qualifiers* ("across the vault", "in my dailies",
"in all my notes") or *time qualifiers* ("this year", "last week",
"in the past month").

Severity: medium. Workaround: drop the scope/time clause from the
question. Real fix: extend
=org_llm/recipe_runner.py::_phrase_to_regex='s strip pass to
include both modifier classes before tokenisation.

*** finding-9 — harness-side direct-tool kwargs drift from real signatures
The headless harness invoked direct =org_tools= functions with
guessed kwargs that didn't match the actual signatures (e.g.
=org_grep(limit=20)= but the real signature is =max_results=,
=org_property_search(name=...)= but real is =prop=,
=doom_keybinds(query=...)= but real takes NO args). All eight
errors surfaced as =TypeError= in the harness's tool-result
preview.

Severity: cosmetic — these are HARNESS-side bugs (kwargs invented
in =/tmp/headless_campaign.py='s =NON_RECIPE_TOOL= map), not
system bugs. Agent-side calls flow through the MCP wrapper layer
(=mcp_server.py=) which already maps friendly names → real
signatures.

The lesson worth keeping: when wiring future test harnesses /
remote routines, derive direct-call signatures from
=inspect.signature= rather than hard-coding. Or always go via the
MCP shim.

** Reasoning capture (Phase 22.5b probe)

Every prompt was instructed to emit a leading =Reasoning: …= line
before its answer. Capture rate was 100% — every model+prompt
combination produced a reasoning line, ranging from 30-280
characters. Most were terse and surface-level ("Use
org-count-matches to count occurrences …"), but a handful
showed actual decision-tree reasoning ("=search_notes= instead of
a direct tool call due to type error" — llama3.2 on #8 noticing
the harness error and re-routing).

Implication for Phase 22.5b: a system-prompt =Reasoning:= probe
is portable, cheap, and yields useful signal across models that
DON'T natively emit =<thinking>= tags. Pair this with the
existing native-=<think>=-tag extractor for models that do.
Promotes Phase 22.5b from "explicit reasoning capture" (model-
dependent) to "universal reasoning capture" (works on any
instruction-following model).
