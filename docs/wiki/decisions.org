* Summary

*Summary.* The durable record of *directional* decisions for
org-llm — the choices a future contributor (human or agent)
would otherwise have to reverse-engineer from commits. One
heading per decision, with =:ID:= for org-roam linking, status,
date, context, decision, and consequences. Not every choice
goes here; only the ones that would surprise a future reader
or that we'd hate to re-litigate.

* Summary of when to write one

*Summary.* Write a decision entry when the choice is
*directional* (sets a default for future work), *non-obvious*
(a smart contributor would otherwise pick differently), or
*paid for* (we tried the alternative and it cost us). Skip
decisions that are obvious from the code, locally scoped, or
trivially reversible. If unsure: ask in
[[id:32f134ee-dc89-41a0-9a7b-930a7cad452a][captain's log]]
whether the decision belongs here, then either write the
entry or drop the question.

*Expanded.*

Triggers (write an entry):
- A new convention every contributor will need to follow
  ("the wiki is org, .md is for cross-tool surfaces only")
- Closing off an alternative we evaluated and rejected
  ("we considered libSQL; staying on SQLite because …")
- A trade-off where the loser is non-obvious
  ("vault-authoritative now → DB-authoritative in Phase 2026-05.17 — DB-as-cache + git-canonical pipeline;
  the inversion has costs and we accept them because …")
- A deferral with a trigger condition
  ("CODEOWNERS deferred until N agent reviewers …")

Anti-triggers (skip):
- The choice is visible in code or wiki and self-explanatory
- The choice is local to one file/function
- The choice will be reversed cheaply if wrong
- The choice is "use library X" with no real alternative

When in doubt, lean toward writing — a 5-line entry is cheap;
re-litigating a forgotten decision is expensive.

* Convention

Each decision is a level-1 heading with this shape:

#+begin_example
* DEC-NNN — short title
:PROPERTIES:
:ID:       <uuid>
:STATUS:   accepted | superseded-by-DEC-MMM | deprecated
:DATE:     [YYYY-MM-DD]
:DECIDERS: <names / instance handles>
:END:

*Summary.* One-paragraph TL;DR (per wiki Rule 2b).

*Context.* What forces are at play. What we knew at the time.

*Decision.* What we decided.

*Consequences.* What this commits us to. What it forecloses.
What might trigger revisiting.
#+end_example

Numbering: =DEC-NNN= is monotonic, three digits, never reused.
Superseded entries stay in place with =STATUS: superseded-by-X=
and a link to the successor — don't delete history.

The seed entries below establish the format. Future decisions
append at the end of the "Decisions" section.

* Decisions

** DEC-001 — Branching: trunk model with PR-to-main
:PROPERTIES:
:ID:       1f3eaffe-3edd-4d8f-9aa7-9aa9c5e35d9e
:STATUS:   accepted
:DATE:     [2026-05-04]
:DECIDERS: Daniel, Claude/opus-A
:END:

*Summary.* Primary integration is on the =trunk= branch;
everything merges to =main= via PR. Secondary streams
(human or agent) branch off =main= using the
=<who>/<slug>= naming scheme. =main= is protected; force-push
forbidden. Force-push to =trunk= requires a captain's-log
announcement.

*Context.* org-llm went from one developer to a parallel
human + agent team in May 2026. Without an explicit branching
model, instances were defaulting to direct =trunk= edits —
fine for one developer, breaks immediately at N>1.

*Decision.* Trunk-based development with PR-mediated merges to
=main=. =trunk= is the primary stream's working branch (the
maintainer's local-fast-path); secondary streams use named
branches off =main=. PRs target =main=, not =trunk=.

*Consequences.*
- All non-primary work is reviewable before merge.
- The maintainer's =trunk= velocity is unchanged.
- Force-push hygiene becomes a coordination signal (forbidden
  on =main=, announced on =trunk=, free on personal branches).
- Triggers revisit: if N humans regularly merge directly,
  collapse =trunk= into =main= and use only named branches.

** DEC-002 — Org-native first; .md only for cross-tool surfaces
:PROPERTIES:
:ID:       4a2ffd67-2ddc-4d12-9b18-86e7e15ec6a4
:STATUS:   accepted
:DATE:     [2026-05-04]
:DECIDERS: Daniel, Claude/opus-A
:END:

*Summary.* All durable project documentation lives in
=docs/wiki/= as =.org= files with =:ID:= properties for
org-roam linking. Markdown files are reserved for surfaces
that external tools auto-load and don't render =.org= well:
README.md (GitHub front page), CONTRIBUTING.md or .org (TBD),
AGENTS.md (cross-tool agent primer), .github/* templates.

*Context.* org-llm is "Claude Code for Org Mode" — the
file format IS the brand. But GitHub, Claude Code, opencode,
and Cursor all auto-discover certain =.md= filenames. Forcing
=.org= everywhere would lose those integrations; forcing
=.md= everywhere would lose org-roam graph + Emacs ergonomics.

*Decision.* Org is the default. =.md= is the exception, used
only where a cross-tool surface specifically requires it.
Every =.md= file at root or in =.github/= should link back
into the org wiki for the substantive content.

*Consequences.*
- The wiki concept graph stays whole.
- New contributors landing on README/CONTRIBUTING get a hop
  into the org wiki, not a separate .md tree.
- Updates: any concept page change ripples to the .md
  surfaces that reference it (per
  =feedback_keep_wiki_and_readme_in_sync=).
- Triggers revisit: if a tool we adopt only reads .org, we
  drop the corresponding .md.

** DEC-003 — Agents-as-SDLC; vault is substrate
:PROPERTIES:
:ID:       8e0c3b71-1f75-4a0f-9d3e-9b85f29c4ed1
:STATUS:   accepted
:DATE:     [2026-05-04]
:DECIDERS: Daniel, Claude/opus-A
:END:

*Summary.* org-llm's stance on SDLC for code projects (its own
or users') is: org-mode is the substrate (headings, properties,
agenda, clock, priorities, roam-links provide most of the data
layer "for free"); agents are the SDLC layer (judgment,
facilitation, cross-document synthesis, ceremony when
configured). Formality is a configuration knob
(=sdlc.formality = none | light | kanban | scrum=), not
separate products. The "none" level must stay genuinely free
of nags.

*Context.* The team going multi-developer raised the question
of formal SDLC. The org-llm thesis ("Claude Code for Org
Mode", agent-driven life management) means SDLC for code is
already in scope as a specialization, not a pivot. The risk
is generalizing too early into a Linear/Jira-shaped product
surface before we know what's load-bearing.

*Decision.*
1. Dogfood SDLC on org-llm itself first; do not generalize.
2. Use existing agents (=@atoz=, =@riker=) for
   PM-shaped work; promote new agents (=@scrummaster=,
   =@projectmanager=, etc.) only when patterns are
   undeniable, per agent-idea-interaction-lens and Phase 2026-05.20 — sync verb POC
   self-coded-tools.
3. Treat ceremony as opt-in, never as default.
4. Differentiator must be agent-native + vault-grounded +
   org-native; do NOT pursue feature-parity with Linear/Jira.

*Consequences.*
- The Phase-29-and-later roadmap gains an "SDLC arc"
  candidate (not yet committed; see
  [[id:43e1b335-656b-45ba-8d6d-7d9b9f2e9c4d][roadmap]]).
- Decision blocks attempts to add cross-project PM features
  before single-project dogfooding has shipped.
- We accept that the upper end of the formality spectrum
  (full Scrum) is *designed*, not *dogfooded*, until org-llm
  has a real multi-team user.

*Decision.* Skip CODEOWNERS for now. The trigger to add it

- ≥2 stable agent reviewers wired into PR review

*Consequences.*

- Future: when triggered, the file's first ownership lines
  will likely route =docs/wiki/*= → =@atoz=,
  =org_llm/dev_tracker_*= → =@riker=,
  [[file:../../org_llm/llm_proxy.py][=org_llm/llm_proxy.py=]] → maintainer, etc. — i.e., agent
  ownership of the surfaces those agents already steward.
- This decision is part of the
  "agents-as-SDLC" thesis (DEC-003); CODEOWNERS is a
  natural artifact of that thesis once non-human reviewers
  stabilize.

** DEC-005 — Strict claim-before-touch + commit hygiene + worktree escape hatch
:PROPERTIES:
:ID:       54843097-3bf9-447e-b8b8-54cbc0a0ed6b
:STATUS:   accepted
:DATE:     [2026-05-04]
:DECIDERS: Daniel, Claude/opus-B
:END:

*Summary.* The unified git strategy for org-llm. Builds on
DEC-001 (trunk + PR-to-main) by adding three operational rules:
*claim-before-touch is strict for everyone including the
maintainer*; *commit hygiene* (pull-rebase before push, explicit
file staging, =scope = phase= in conventional-commits format,
push immediately after commit); and a *worktree escape hatch*
when concurrent agents physically overlap on hot files. The
strict claim closes a loophole that ran silently across 414
solo-maintainer commits — fine at n=1, breaks at N≥2.

*Context.* On 2026-05-04 the project went from one
solo-maintainer to a parallel human + agent team (multiple
Claude Code / opencode instances, future @-agents). That same
day three commits landed in trunk in six minutes from different
agents (=docs(wiki):= → =feat(resolvers):= → =feat(primers):=)
with overlapping uncommitted edits to =orchestration.py= /
=mcp_server.py= / =db.py=. The existing
[[id:03be52bf-003f-4762-a274-e7c88f97847f][coordination.org]] Rule 1
already requires a claim before any =Edit=/=Write=, but n=1
muscle memory has been running without one — the rule reads
strict but operates soft. This decision flips it operationally.

The git log itself is evidence the existing flow works: 414
commits, zero merge commits, zero abandoned branches,
conventional-commits format strictly followed, every commit's
scope tied to a phase. The strategy preserves that velocity for
the maintainer's primary stream while adding the minimum
ceremony needed for parallel work.

*Decision.*

1. *Strict claim-before-touch — no maintainer exception.* Every
   contributor (human or agent) opens an =active-claims.org=
   STARTED heading before the first =Edit=/=Write= in a session.
   This applies to Daniel's solo sessions too. The license to
   skip the claim board ended on 2026-05-04 when N became ≥2.

2. *Commit hygiene rules.*
   - Stage files explicitly (=git add <path>=); never =-A= /
     =.= / =-u=. The git-safety-protocol bans this; DEC-005
     promotes it from agent-instruction to project rule.
   - =git pull --rebase= before =git push=. Concurrent commits
     resolve as fast-forwards or interleaves, never merges.
     The trunk graph stays linear (zero merge commits across
     414 commits is a feature; preserve it).
   - Conventional Commits with =scope = phase= (or
     =scope = component= when phase doesn't apply):
     =feat(primers): Phase 24.5b — …=,
     =docs(wiki): canonize agent-orientation pattern + …=.
     The scope token grep-anchors the phase narrative.
   - Push immediately after commit. Holding committed-but-
     unpushed work is a coordination violation when other
     agents are active — they can't pull-rebase against work
     they can't see.
   - Co-author tag stays for agent commits:
     =Co-Authored-By: Claude Opus 4.7 <noreply@anthropic.com>=
     (or equivalent for other agents). Preserves attribution
     lineage even when squashed/rebased.

3. *Worktree escape hatch.* When your planned scope overlaps a
   hot file (=orchestration.py=, =mcp_server.py=, =db.py=,
   =cli.py=, =llm_proxy.py=) that another contributor has
   uncommitted local changes on, you MUST either:
   - Coordinate via captain's log (=kind=coord=) and wait, OR
   - Spin up =git worktree add ../org-llm-<phase> origin/main=
     (or =origin/trunk= if you're on the maintainer's stream)
     and work there. The worktree shares =.git= with the main
     checkout — no clone, no remote-config drift; just a
     separate working dir for a separate branch.
   The list of "hot files" is the set the dev-tracker phase
   plans repeatedly schedule for edits; today's set is the
   five named above. Add to it (in this DEC) when a sixth
   surfaces.

4. *No PR gate until the trigger.* PRs to =main= remain the
   merge surface for secondary streams (DEC-001), but no CI
   gating, no required review, no PR template enforcement
   beyond what =.github/PULL_REQUEST_TEMPLATE.md= proposes.
   Trigger to add a CI gate: ≥3 regular human committers OR
   the first outside FOSS contributor (whichever is first),
   matching DEC-004's CODEOWNERS trigger.

*Consequences.*
- *Operational.* Daniel's solo sessions now post a claim before
  editing. Cost: ~30 seconds per session start. Benefit: agents
  spawning concurrently can see what's in flight without
  guessing from =git status=.
- *Velocity.* The maintainer's trunk fast-path is preserved
  (DEC-001 unchanged). Pull-rebase and explicit staging are
  habit-shaped friction that surfaces races loudly rather than
  letting them silently corrupt the working tree.
- *Worktree escape hatch.* Lets parallel agents proceed when
  they would otherwise have to wait for someone else's commit.
  The maintainer rarely needs it; secondary streams reach for
  it whenever DEC-001 would otherwise force them to coordinate
  before starting.
- *Forecloses.* No long-running feature branches that miss
  trunk by weeks. No squash-rebase-rewrite of public history.
  No CI ceremony before it amortizes. No "I'll claim later"
  escape valve.
- *Triggers revisit.* If we reach ≥3 regular human committers
  or first outside contributor, add CI + required review (and
  re-evaluate CODEOWNERS per DEC-004). If hot-file races
  recur despite the escape hatch, escalate the file to
  per-section locks or split it.

** DEC-006 — Supervision is deterministic by default
:PROPERTIES:
:ID:       cf17c89e-2a9e-46b0-9e3f-7c44d6f1bd92
:STATUS:   accepted
:DATE:     [2026-05-04]
:DECIDERS: Daniel, Claude/opus-C
:END:

*Summary.* When the agent layer needs supervision —
disambiguating a prompt, recovering from a wrong tool call,
spotting a confusion loop — that supervision runs as
*deterministic code* unless the confusion genuinely requires
reasoning. An LLM-based observer is an extra round-trip per
turn and the orchestration top priority (smoother + faster +
higher-quality than solo) fails the moment supervision taxes
latency. Sharply: /if a confusion can be detected by code, it
must be; LLM-based supervision is reserved for confusions that
genuinely need reasoning./ Implemented as the Phase 2026-05.02 — supervision trinity
[[id:43e1b335-656b-45ba-8d6d-7d9b9f2e9c4d][supervision trinity]] —
three registries (pre-flight resolvers, tool-failure recovery
hooks, confusion detector) that each accept new entries the
way the recipe registry accepts new recipes.

*Context.* The 2026-05-04 =@curator= bug surfaced the gap:
user said "@curator in org-llm, =wiki/superset.org=, fix it
up"; agent looked in cwd then =~/org/=, gave up. The actual
file was =docs/wiki/superset.org= in the repo. The user
asked for a generalizable fix — manager spotting the problem
without taxing speed — and pushed back on bandaiding the
specific path-resolution case. The conversation surfaced the
broader rule: pattern-matchable confusions are code's job;
reasoning-required confusions are the LLM's. Most agent
confusion is pattern-matchable.

*Decision.*

1. *Default mode is deterministic.* Pre-flight enrichment,
   recovery hooks, and confusion detection all run as pure
   code in registry-shaped modules. Adding a new resolver /
   hook / signal is one entry, not core surgery.

2. *LLM-based supervision is the exception.* Reserved for
   confusions that genuinely need reasoning — semantic
   equivalence judgments, cross-phrasing intent matching,
   subjective output quality. When invoked, prefer
   /async/off-the-critical-path/ shapes (manager quorum
   reviewing the audit log retrospectively) over inline
   round-trips.

3. *The trinity is the implementation surface.* Phase 2026-05.02 — supervision trinity
   ships three registries: 24.1 pre-flight resolvers, 24.2
   tool-failure recovery hooks, 24.3 confusion detector
   (24.4 manager quorum is the open-question slot for the
   exception case, async-only). Future supervision needs
   choose which registry to extend, not whether to spin a
   new layer.

*Consequences.*
- Architecture rule canonized in
  =docs/wiki/architecture.org= § /Design rule —
  supervision is deterministic by default/.
- Phase 2026-05.02 — supervision trinity trinity is the load-bearing surface;
  later phases (29 self-coded tools, 30 FOSS agent value-adds)
  treat the registries as the auto-promotion targets.
- Forecloses LLM-observer-per-turn shapes — those
  break the orchestration top priority and won't ship.
- Triggers revisit: if a class of confusion proves
  /unambiguously/ to need reasoning AND can't tolerate async,
  add a 4th registry slot (with the same shape) rather than
  abandoning the rule.

** DEC-007 — Wiki Rule 2b: every concept entry is Summary + Expanded
:PROPERTIES:
:ID:       7be1d9c4-4f50-4f6b-bbf8-69152f3a68a4
:STATUS:   accepted
:DATE:     [2026-05-04]
:DECIDERS: Daniel, Claude/opus-C
:END:

*Summary.* Every new concept, design rule, or architectural
decision in the wiki must lead with a =*Summary.*= paragraph
(1–3 sentences, the load-bearing claim) followed by
=*Expanded.*= prose. Both, every time. Not just one. Canonized
as Rule 2b in
[[id:d30c177e-5b09-4f52-95bf-bb2d36f663e8][wiki conventions]].

*Context.* Every wiki concept is read at two speeds: by a
future LLM/human looking up one fact (wants the summary), and
by someone learning the system (wants the full context). The
status quo (single prose section) buried the load-bearing
sentence inside the body, costing both audiences. Forcing the
author to write both up-front means the summary actually
exists and isn't just the first paragraph by accident.

*Decision.* Triggers (require both blocks): new design rule,
new top-level architecture section, new recipe / agent / tool
getting its own wiki page, substantial revision of an
existing concept page. Anti-triggers (one block fine): typo
fixes, link repairs, passing edits.

*Consequences.*
- Author cost: writing the summary forces clarification of
  the load-bearing claim. Five extra minutes; cheap.
- Reader cost: the summary covers ~80% of lookup needs in
  ~10% of the page; the rest stays available.
- The supervision rule (DEC-006) was the worked example of
  this convention applied to itself.
- Triggers revisit: if the summary/expanded split feels
  redundant on small pages, allow Summary-only on entries
  under ~150 words. Today's call: keep the rule strict
  to build the habit.

** DEC-008 — Phase 2026-05.02.01 — pre-flight resolvers wires at the @-prefix seam, not delegate-only
:PROPERTIES:
:ID:       8aa9e7d2-9f63-4ef3-9b25-3b1c7d2e8f5a
:STATUS:   accepted
:DATE:     [2026-05-04]
:DECIDERS: Daniel, Claude/opus-C
:END:

*Summary.* The pre-flight resolver enrichment fires inside
=intercept_agent_prefix= in [[file:../../org_llm/llm_proxy.py][=org_llm/llm_proxy.py=]] (the
@-prefix persona-swap seam), not only inside =delegate()=
in [[file:../../org_llm/mcp_server.py][=mcp_server.py=]]. The
=delegate()= wiring stays as a defensive belt-and-suspenders
for programmatic delegate calls; the proxy wiring is the
load-bearing path because every @-prefix-routed turn flows
through it. Eager-imports =org_llm.resolvers= at proxy
module-load time so the prewarm thread is finished before
the first user prompt and the cold-start budget never bites.

*Context.* The first cut of Phase 2026-05.02.01 — pre-flight resolvers wired the resolver
into =delegate()= only. Live verify against the motivating
=@curator/superset.org= bug failed to fire enrichment because
curator (running on cloud =qwen-2.5-72b= via the @-prefix
swap) called tools directly without going through
=delegate()=. The =manager-log.jsonl= was empty; my resolver
never ran. Reading
[[id:47ba2143-c53a-409a-8286-2b3759794608][llm-proxy.org]]
made the seam location obvious: =intercept_agent_prefix= (#6
in =DEFAULT_INTERCEPTORS=) is where every @-prefix turn gets
its persona swap, and the recipe pre-fetch (Phase 2026-05.07 — manager pre-fetch + agent narrates)
already mutates =agent_prompt= here. Resolver enrichment
slots in cleanly using the same pattern.

This is also the user's "don't bandaid" feedback applied:
wiring at =delegate()= solved a narrow case; the general
problem is "every agent dispatch deserves enrichment." The
@-prefix seam is that general dispatch surface.

*Decision.*

1. Resolver call moves to (or is duplicated in)
   =intercept_agent_prefix=, immediately after the recipe
   pre-fetch block, mutating =agent_prompt= the same way.
2. =delegate()= call site keeps its resolver call as a
   defensive layer for programmatic delegate invocations
   that don't traverse @-prefix.
3. =org_llm.resolvers= is eager-imported at module load
   in =llm_proxy.py= so =_prewarm_caches()= fires at proxy
   startup. First user prompt sees warm caches; the 80ms
   wall-clock budget stays comfortable.
4. The same wiring lesson applies forward: future Phase 2026-05.02 — supervision trinity
   sub-phases (recovery hooks, confusion detector) wire at
   the *broadest dispatch seam available*, not the narrowest
   convenient call site. The trinity's value compounds when
   each layer hits every turn, not just manager-mediated
   ones.

*Consequences.*
- Phase 2026-05.02.01 — pre-flight resolvers closes the motivating bug end-to-end via the
  @-prefix path; verified live (third turn of 2026-05-04
  session: agent's first tool call hit the absolute path).
- Resolver enrichment is now a shared seam with recipe
  pre-fetch; both mutate =agent_prompt= at the same site.
  Future contributors expecting ONE pre-flight surface get
  it.
- Sticky turns (=intercept_agent_sticky= prepends @<intent>)
  benefit transitively — sticky chains into agent_prefix and
  the resolver fires there.
- Pronoun-only follow-ups ("read it") still don't get path
  resolution because there's no token to extract. That's a
  separate enhancement (resolve from conversation history),
  noted but not in 24.1 scope.
- Forecloses the "wire at the most convenient site" lazy
  default. Future trinity work explicitly evaluates seam
  breadth before choosing wire-in.
- Triggers revisit: if pronoun-resolution becomes a recurring
  need, file as a 24.1.x sub-phase that pulls the last N
  user turns into the resolver's input.

** DEC-009 — Curated core agent team + extension path
:PROPERTIES:
:ID:       a4d1f7c3-6e29-4b8a-9f15-3d8e2c7b91a5
:STATUS:   accepted
:DATE:     [2026-05-04]
:DECIDERS: Daniel, Claude/opus-C
:END:

/Updated 2026-05-05 by [[id:573550f8-a6ee-4581-b16f-20cc4645df21][DEC-014]]: cap expanded ≤6 → ≤7 (Magnificent
Seven), binary core/extension framing extended to ternary +
agent-ify default. Body below preserved as original framing./

*Summary.* Org-llm ships an *opinionated curated core team*
of agents (manager + a small set of specialists — initial
likely =@picard= manager, =@spock= researcher, =@data= scribe,
=@boothby= hygiene) capped at ≤7 (per DEC-014; originally ≤6)
and provides an *extension path* for any agent the user (or
community) writes via Phase 2026-05.14.02 — DB-backed registry user-supplied agents and
Phase 2026-05.16 — literate MCP tools literate-tools. Two-tier population by design
(extended to ternary by DEC-014): out-of-the-box clarity from
the opinionated team; long-tail value from the extension
surface.

*Context.* During the 2026-05-04 mission walk, Daniel named
"the right mix of agents for the job" as a guiding principle
and surfaced the inherent paradox: the app must ship with a
specific team (so users get the dbt-shaped opinionated default
that makes /first usable/ achievable) AND must remain
extensible (so any agent anyone could write becomes a
first-class citizen). Today's roster of 19 agents is too many
for "core" — most are specialists or experiments and don't
gate the dream-state-vault thesis (β). The cull (Phase 2026-05.04 — cull walk —
core/addable extract) decides which stay core; this decision
captures the principle that drives the cull.

*Decision.*

1. *Curated core team is the OUT-OF-THE-BOX experience.*
   Ship ≤7 agents preconfigured (expanded from ≤6 by DEC-014 —
   the Bridge Crew). They cover the lead value
   (β: dream-state vault via agents) end-to-end. Selection
   criterion mirrors DEC-006: each core agent earns its keep
   against the lead thesis or it goes to the extension path.

2. *Extension path is first-class, not afterthought.*
   Phase 2026-05.14.02 — DB-backed registry (user-supplied agents) and Phase 2026-05.16 — literate MCP tools (literate
   MCP tools) are not "advanced" features — they are the
   mechanism by which the long tail of agent value lands.
   They get the same surface polish as the core team.

3. *Versioning lens.* /First usable/ for agents (criterion 2

** DEC-010 — Anti-capitalist FOSS, not just FOSS

*Summary.* Org-llm is FOSS *and* anti-capitalist — the

copyleft (AGPL-shape — definitive license deferred but the

exists, but only to *spread the practice*, not to capture
market share, grow MRR, or cultivate a profit funnel.

*Context.* During the 2026-05-04 mission walk Daniel surfaced

clarification: this is anti-capitalist, not just FOSS. The
existing Groq exclusion (in =memory feedback_no_groq=) is
already an instance of this principle — Groq is excluded not

makes the principle explicit so future vendor / dependency /
contribution decisions use the same lens.

1. *License family is copyleft.* Specific license (AGPLv3,

2. *Vendor exclusion lens.* Profit-extraction-shaped vendors

   technically FOSS-compatible) are excluded from the cloud

   first instance; future calls test against the same lens.
   FOSS-first, then anti-capitalist-first within FOSS.

3. *Marketing tone.* Project communications optimise for
   *spreading the practice* — explaining what org-llm IS and
   how to adopt it — not for funnel mechanics. No
   pricing/tiers/MRR/SaaS-shaped framing in any user-facing

** DEC-011 — DB is the universal interface; files are canonical storage
:PROPERTIES:
:ID:       9b73e26d-5c84-4f1a-bd35-2af18e4c7c93
:STATUS:   accepted
:DATE:     [2026-05-05]
:DECIDERS: Daniel, Claude/opus-C
:END:

*Summary.* Org files in a git repo are the *canonical, durable
storage*. The DB (SQLite + sqlite-vec) is the *universal
query/write interface* — every domain object has a SQL
representation, regardless of whether it durably lives in a
file or only in the DB. Some writes have higher latency
because they round-trip through file/git (e.g. captain's log
entries that need a commit before another device sees them);
that latency is explicit, not a leak. This collapses the
two-pillar tension between "Org is Code" and "DB-maximalism":
they're layered, not opposed.

*Context.* The original Phase 2026-05.17 — DB-as-cache + git-canonical pipeline framing said "DB becomes
truth, files become rendered UI" — pure DB-authoritative
inversion. The 2026-05-05 mission walk surfaced two related
clarifications: (1) at the bytes level, *everything is files*
(SQLite is a file, postgres is files, cloud buckets are
files-elsewhere), so "files vs database" was always a category
error; the real choice is which interface you put on the
bytes; (2) the user's lived requirement is multi-device sync
(laptop ↔ phone ↔ work-laptop), and git already solves
multi-writer distributed sync — using it would dissolve a
custom-sync engineering problem we'd otherwise have to build.
DEC-011 codifies the resolution: files are canonical (git
gives sync + history + auditability for free), DB is universal
interface (gives SQL power, mass-ops, observability,
introspectability — all the DB-max wins).

*Decision.*

1. *Files are canonical.* All durable state lives in committed
   files. Org content in =~/org/*.org=, configs in literate
   org files, dbt models in =dbt/=, tofu config in =infra/=,
   etc. Git is the version control + sync + audit substrate.

2. *DB is the universal interface.* Every domain object is
   queryable via SQL — including captain's log, configs,
   embeddings, agent baselines, vault facts, validation runs.
   No piece of state bypasses the DB query layer.

3. *DB is regenerable.* Each device maintains its own local
   DB, derived from the (synced) files via dbt + ingestion.
   The DB is in =.gitignore=. Loss of DB = re-derive from
   files. Zero permanent data loss.

4. *Latency tradeoffs are explicit.* Some writes have higher
   latency because they have to round-trip through file/git
   (commit, push, pull-on-other-device, re-derive DB). This
   is acknowledged, not hidden. UX accommodates it (e.g.
   mobile capture is offline-friendly; LLM enrichment defers
   to reconnect).

5. *Forward direction goes through dbt.* Files → parsed
   tables → derived models. dbt provides the schema, tests,
   incremental builds, lineage. See companion wiki:
   [[id:20046fc6-8b1e-4211-911b-b96f431d1f9e][dbt-pipeline.org]].

6. *Backward direction is a deterministic renderer.* Agents
   write via DB; engine renders the affected files
   deterministically (whole-file rewrite for now; surgical
   later). See [[id:5890fad2-9ba1-4801-ae8c-20daae475a8a][sync-architecture.org]] for the full cycle and
   [[id:50f49d19-6f98-4d03-85d5-87dfa19951ff][data-integrity-laws.org]] for agent-vs-human edit policies.

*Consequences.*
- *Phase 2026-05.17 — DB-as-cache + git-canonical pipeline scope rewrites.* Was "DB becomes truth, files
  become rendered UI"; now "files canonical, DB-as-cache, dbt
  pipeline." Narrower, safer, ships sooner. Captures most of
  the original DB-max wins without the bidirectional-sync
  complexity.
- *Multi-device sync becomes git, full stop.* No custom event
  log, no CRDT layer, no bespoke sync protocol. =git pull/push=
  is the entire mechanism. Conflict resolution = git's tools
  (with an org-aware merge driver as an upgrade path).
- *Catastrophic loss is recoverable for free.* Phone wipe →
  =git clone= + =org-llm init= + re-derive. Property cloud SaaS
  charges for; we get from layering.
- *Captain's log moves to a synced committed file* (per this
  decision) so it's regenerable from canonical state and
  visible across devices.
- *DB schema can evolve without migration ceremony* — drop
  the local DB, re-derive from files. Same file → same DB
  modulo the schema delta.
- *Forecloses* "DB is the durable home for X" for any state
  not also expressible as files. Anything that goes in the DB
  must round-trip to a file representation.
- *Triggers revisit:* if multi-device sync stress-tests reveal
  a write pattern git can't handle, escalate (CRDT layer, event
  log) — but only after demonstrating the gap. Default stays
  git-as-sync.

** DEC-012 — Per-device configuration via device-keyed Config
:PROPERTIES:
:ID:       b6c4f8a7-1e23-4d96-9f8b-7c1d52a4b3f1
:STATUS:   accepted
:DATE:     [2026-05-05]
:DECIDERS: Daniel, Claude/opus-C
:END:

*Summary.* The =Config= table primary key shifts from =(key)=
to =(key, device)=, with =device='(any)'= for global defaults.
Lookup picks the most-specific device match (current device >
=(any)=). Lets the same logical knob hold different values per
device — phone font size differs from work-laptop screen;
theme can be less-commie on the work machine; agent-write-active
defaults true on laptop, false on mobile. Drift between device
configs is the *feature*, not the bug.

*Context.* The 2026-05-05 mission walk surfaced this when
discussing multi-device shapes. The user's lived case: phone
needs large font; work laptop needs muted theme; laptop runs
=@boothby= nightly but phone shouldn't. Today the =Config=
table is keyed by =(key)= alone, so a knob change on one
device propagates to all (via committed literate config),
which is wrong. DEC-012 makes per-device variance first-class.

*Decision.*

1. *Schema change.* =Config(key, value)= →
   =Config(key, device, value)=, primary key =(key, device)=.
   =device='(any)'= is the global default. Each device knows
   its own identifier (hostname or fixed
   =~/.config/org-llm/device-id=).

2. *Lookup precedence.* Current device > =(any)= default.
   Engine reads the most-specific value at runtime.

3. *Literate config respects device-specificity.* Device-aware
   =:DEVICE:= property on headings and/or per-device override
   files (=org-llm-config.phone.org=,
   =org-llm-config.work-laptop.org=). Round-trip preserves
   device.

4. *Migration.* Existing =Config= rows become
   =(key, '(any)', value)= rows; no semantic change for users
   without per-device customization.

5. *Pattern reuse.* Same shape extends as needed:
   =AgentBaseline=, =SidebarOverlay=, etc. — anything that
   should plausibly differ per device gets the =device=
   column.

*Consequences.*
- *Schema migration on =Config= table* (and any table that
  inherits the pattern). Per [[id:9b73e26d-5c84-4f1a-bd35-2af18e4c7c93][DEC-011]] DB regenerates from
  files; user-facing migration is invisible (literate config
  is the source of truth and the new schema reads it
  unchanged).
- *Device identity becomes a load-bearing concept.* Hostname
  works for unique machines; a generated device-id covers
  edge cases (multiple machines with same hostname,
  ephemeral containers). Worth a small TODO to specify.
- *Sync semantics stay clean.* Files (literate config) sync
  via git like everything else; each device picks its own
  rows on read. No custom per-device sync logic.
- *Agent-write-active becomes per-device by default* —
  =@boothby= runs nightly on laptop, read-only on mobile.
  Avoids "two agents on two devices fighting over the same
  drift on the same night" (per scenario 6 of the mission
  walk).
- *Forecloses* "one global config for everything" assumption
  in code paths that read knobs. Every read must pass the
  current device identifier.
- *Triggers revisit:* if vault-keyed config (separate from
  device-keyed) becomes a need (e.g. one user, multiple
  vaults, different theme per vault), extend the same shape:
  =Config(key, vault, device, value)=. Today's call: device
  only.

** DEC-013 — Two-tier tool architecture: data tools (dbt) + effect tools (MCP)
:PROPERTIES:
:ID:       e1f47a83-3df0-4b2c-9265-7c2e1d8a4f63
:STATUS:   accepted
:DATE:     [2026-05-05]
:DECIDERS: Daniel, Claude/opus-C
:END:

*Summary.* Org-llm tools split into two named tiers: *data tools*
(implemented via dbt; ~90% of the surface) and *effect tools*
(implemented via MCP registration; ~10%). Data tools manipulate
data through SQL — read queries (dbt models), write operations
(dbt operations + render hook), history capture (dbt snapshots),
quality contracts (dbt tests), reusable SQL chunks (dbt macros).
Effect tools cause side effects on foreign systems — LLM dispatch
(=delegate=), browser (=open_url=), shell, granted-fs reads,
network. Default *strongly toward dbt* unless the tool's primary
purpose is foreign-system effect. Mechanistic name (dbt-tools,
MCP-tools) is used in code/grep; functional name (data tools,
effect tools) is used in docs/architecture/conversation.

*Context.* The 2026-05-05 mission walk surfaced the symmetry:
a dbt model has the exact shape of an agent tool (input/output/
contract/docs). When 90% of the existing tool surface (search,
ask, count, walk, capture, hygiene, vault facts) is data-shaped,
unifying it under one substrate (dbt) collapses two parallel
systems into one. The remaining 10% (LLM dispatch, browser,
shell) bridges to foreign systems where dbt doesn't fit and
stays as MCP. Daniel locked it: "dbt/mcp is now an architectural
policy."

*Decision.*

1. *Two tiers, named both ways.* Mechanistic = dbt-tools /
   MCP-tools (where the code lives, what registers them).
   Functional = data tools / effect tools (what they do, what
   guarantees they offer).

2. *Default is dbt.* If a new tool's primary purpose is data
   manipulation (read, write, transform, aggregate), it ships as
   a dbt model / operation / macro / snapshot. Justifying the
   exception is the cost; defaulting is free.

3. *MCP is reserved for foreign-system effects.* LLM dispatch,
   browser drive, shell, network calls, FS-side-effects. These
   stay non-dbt because forcing dbt onto pure-side-effect tools
   is Rube Goldberg.

4. *Write-side trick.* Pure dbt models are read-only by design,
   but data tools include write surfaces via *dbt operations*
   (=run-operation=) + *render hook* (DEC-011 deterministic
   file rendering). This keeps write-side tools in the data
   tier, not pushed to MCP.

5. *Three Laws apply differently.* Data tools enforce the Three
   Laws automatically — operations on local DB don't touch open
   user buffers until the render hook fires; the render hook IS
   the enforcement point. Effect tools enforce the Three Laws
   per-tool (each tool decides its own policy: =delegate= can't
   overwrite a buffer, =shell= could clobber anything, etc.).

6. *Substructure inside each tier* is the standard dbt /
   MCP catalog:

   #+begin_example
   data tools (dbt-tools)
   ├── models       — read-side queries; views or tables
   ├── operations   — write-side; INSERT/UPDATE + render hook
   ├── snapshots    — append-only history capture
   ├── tests        — declarative contracts agents trust
   └── macros       — parameterised SQL chunks

   effect tools (MCP-tools)
   ├── dispatch     — delegate, spawn-subagent
   ├── browser      — open_url, browser_command
   ├── shell        — subprocess, file ops
   ├── granted-fs   — read_file, list_directory (allowlist)
   └── network      — http fetches, webhooks
   #+end_example

*Consequences.*
- *Phase 2026-05.04 — cull walk cull becomes operationally clearer.* Every "tool"
  candidate gets categorized: data → dbt, effect → MCP, then
  either core (gates lead value) or addable (per DEC-009).
- *Phase 2026-05.20 — sync verb POC self-coded tools target dbt by default.* The
  promotion path (audit-log → propose model → tests pass →
  register) is dbt's natural shape. Effect-tool synthesis is
  rarer + harder; dbt majority makes the loop tractable.
- *Phase 2026-05.21 — multi-judge validation multi-judge applies cleanly to data tools* —
  comparing model output against past LLM-produced answers is
  the dbt-natural validation. Effect-tool validation is
  per-tool bespoke.
- *Federation across vaults extends only the data tier* (per
  [[id:20046fc6-8b1e-4211-911b-b96f431d1f9e][dbt-pipeline.org]]); effect tools stay per-device because
  their foreign systems do.
- *Captain's log gains a kind=data vs kind=effect dimension*
  — analytics over agent tool use becomes natural.
- *Forecloses* one-off "agent tool registry" parallel to dbt's
  model registry; everything goes through one of these two
  surfaces.
- *Triggers revisit* if a third tier emerges that doesn't fit
  either (e.g. some streaming/realtime use case where dbt's
  build cycle doesn't apply and MCP isn't right either). Today
  the binary split is a strict win.

Promotion gates: =trunk → acpt= on smoke + author-ready; =acpt → prod=
on ≥24h dogfood-without-surprise + tag bump. Agent-vs-human dogfood
marking (per user, 2026-05-05): test items carry =:test:agent-runnable:=
or =:test:requires-human:=; agents run as much of acpt-tier dogfood as
possible. Promotion provenance recorded in captain's log
(=promoted_by=agent-X | daniel=). Per-environment Config keying
(=Config(key, device, env, value)= per [[id:b6c4f8a7-1e23-4d96-9f8b-7c1d52a4b3f1][DEC-012]]+this).

*Context.* The 2026-05-05 cull walk surfaced a parallelism need:
Phase 2026-05.01 — physical extraction (~3000 LoC delete) is high-risk for daily-driver
stability; other dev work (Phase 2026-05.02.02 — recovery hooks/24.3, mobile build, DEC-015
chat surface) shouldn't block on it. DEC-001 (trunk + PR-to-main)
covers code-branch isolation but not *runtime* isolation — the user
daily-drives the same install they develop on, which means risky
dev work and stable use share runtime state. The user named the
gap explicitly: "want to develop the LoC delete while allowing
other work in parallel… also a concept of dev/acpt/prod."

The Phase 2026-05.01 — physical extraction use case is the trigger; the framework generalises
to all future risky work and to org-llm's use *as a dev tool* for
the user's own projects (per [[id:8e0c3b71-1f75-4a0f-9d3e-9b85f29c4ed1][DEC-003]] agents-as-SDLC).

*Decision.*

1. *Three tiers, two axes.*
   - Code branches: =trunk= (dev) → =acpt= → =main= (prod).
   - Install slots: editable (=dev=) / =uv tool install --from
     git@…@acpt= / =uv tool install --from git@…@v0.X.Y= (prod).
   - Daily-driver = prod by default. Risky work = dev.

2. *Promotion gates (lightweight).*
   - =trunk → acpt=: smoke tests pass + author calls "ready".
   - =acpt → prod + tag=: ≥24h dogfood-without-surprise + semver bump
     + signed tag.

3. *Agent-vs-human dogfood marking.*
   - Test items carry =:test:agent-runnable:= or =:test:requires-human:=.
   - Agents run all =agent-runnable= as part of acpt promotion.
   - =requires-human= blocks prod promotion until user signs off
     (=org-llm self test --signoff=test-id=).

4. *Promotion provenance.*
   - Every promotion writes to captain's log (=kind=promotion=) with
     =promoted_by= field: =agent-X= or =daniel= (or human handle).
   - Distinguishes agent-promoted (low-stakes auto-promotion) from
     human-promoted (high-stakes sign-off).

5. *Per-environment Config.*
   - Schema: =Config(key, device, env, value)= — extends DEC-012.
   - Lookup precedence: full-match > device-only > any > MODEL_DEFAULTS.
   - =ORG_LLM_ENV= env var per uv tool slot (defaults to =dev=).

6. *First baseline.* =acpt= branch created from current trunk =bfb9c48=
   on 2026-05-05; tagged =v0.1.0-acpt0=. First =trunk → acpt= promotion
   is implicit (initial baseline). First =acpt → prod= awaits the
   24h dogfood window + agent-runnable test pass.

*Consequences.*

- *Phase 2026-05.01 — physical extraction unblocks.* Extraction work runs on =dev/26-2-extraction=
  branch off main; promotes to trunk → acpt → prod through the gates.
  Other dev work continues on trunk in parallel; conflicts resolved at
  promotion time, not edit time.
- *Daily-driver stability protected.* User can roll back to a prior
  prod tag if a promotion goes sideways; risky dev never touches prod
  install.
- *Agent-driven acpt dogfood scales* without user attention bottleneck.
  Most acpt promotions can happen "lights-out" (agent-promoted); only
  human-required sign-off blocks prod.
- *Generic framework applies to user projects too.* When org-llm is
  used as a dev tool (per DEC-003), the same three-tier model + agent/
  human marking applies to user-project tests. =@riker= (Bridge
  Crew, per DEC-014) understands the framework.
- *Config key-space explodes by 3×.* Mitigations: lookup precedence
  + sensible defaults at "(any)" mean most knobs only ever land at
  the broadest scope; only env-divergent ones (like =cloud_first=,
  =agent_write_active=, =log_level=) need explicit per-env values.
- *Forecloses* "one slot, one branch" assumption; "trust the editable
  install for production" assumption; auto-merge-without-acpt-gate.
- *Triggers revisit.* If the gate ceremony slows a one-person team down
  more than it saves, collapse acpt → trunk and use only main+tags.
  If 5+ humans regularly merge, we'll already have CI gates on PRs to
  main per DEC-005's trigger condition; the SDLC tiers compose with
  that, not replace it.

** DEC-017 — Stack composition vs. integration: two relationship modes
:PROPERTIES:
:ID:       7d4e1a9c-8b62-4f37-9e5d-c1a9f3b8e6d2
:STATUS:   accepted
:DATE:     [2026-05-05]
:DECIDERS: Daniel, Claude/opus-A
:END:

*Summary.* Org-llm has two distinct relationship modes with
external software, and they have different license rules.
*Integration* — org-llm talks to X as peer / dependency /
external service — is open to any license; X's company shape
gets sniffed under [[id:2c8f6b1d-4e9a-4c3f-86b7-9d5e1f2a8c47][DEC-010 — anti-capitalist FOSS]] but X's
license itself can be anything. *Stack composition* — X is
forked, embedded, or owned as an org-llm component — is
*FOSS-only*, extending DEC-010's anti-enclosure rule into the
org-llm tree itself. The user's framing: "org-llm may /allow/
integration with Claude, Claude is not part of the org-llm
stack. org-llm may (if warranted) fork, say, Superset and make
Superset a component of org-llm if so desired."

*Context.* Through 2026-05-04 the project lacked an explicit
distinction between "we ship X as a dependency / talk to X over
a wire" and "we own X as an org-llm component." DEC-010 covered
license posture for the org-llm tree but didn't name the lane
that lets *closed-source* peers (Claude, GitHub) sit at the
table without contradicting anti-enclosure. The dev-tracker's
2026-05-05 Agor research entry made the gap concrete: Agor is
BSL 1.1 until 2029-01-15 and Apache 2.0 thereafter, which
forecloses *stack* membership now while leaving *integration*
clean. Without DEC-017, every yellow-zone license argument has
to be re-litigated from first principles.

*Decision.*

1. *Two modes, named.*
   | Relationship                     | Meaning                                                       | License rule                          |
   |----------------------------------+---------------------------------------------------------------+---------------------------------------|
   | *Allow integration with X*       | org-llm talks to X as peer / dependency / external service    | X can be any license                  |
   | *X is part of the stack*         | X is forked / embedded / owned as an org-llm component        | *FOSS-only*; extends DEC-010          |

2. *Stack rule (FOSS-only).* If org-llm forks X, vendors X
   into the tree, or owns X as a component, X must be
   compatible with the copyleft family chosen in
   [[id:2c8f6b1d-4e9a-4c3f-86b7-9d5e1f2a8c47][DEC-010 — anti-capitalist FOSS]]. Permissive-FOSS upstreams
   are absorbable (relicense at fork). Yellow-zone licenses
   (BSL, SSPL, source-available) are *not* stackable while
   the restrictive clause is active; revisit at the
   change-date.

3. *Integration rule (any license, with a sniff test).*
   Integration targets aren't bound by license — closed
   models (Claude), proprietary services (GitHub), and
   yellow-zone projects (Agor under BSL) are all fair
   integration peers. The DEC-010 anti-capitalist sniff still
   applies at the *vendor / company shape* level (Groq is
   excluded as a vendor even though it's technically
   FOSS-compatible); the license itself is not the gate for
   integration mode.

4. *Yellow-zone flagging.* Integration with BSL /
   source-available targets is permitted but flagged: no
   doc-copy claim that they're "part of org-llm," no
   stack-membership framing in marketing or wiki, and a
   change-date watch in the dev-tracker so the integration
   posture re-evaluates automatically when the license
   converts.

5. *Current ratifications (snapshot).*
   - *Claude (Anthropic model + Claude Code CLI)* —
     integrate-only, never stack. Closed-source; cannot be
     forked into org-llm. The developer using Claude Code as
     a dev tool is orthogonal to org-llm's stack composition.
   - *Agor (=preset-io/agor=)* — integrate-now under BSL 1.1,
     fork-and-stack *maybe* post-2029-01-15 when BSL → Apache
     2.0. Three modes:
     1. *Pre-2029:* personal pilot incubation only.
        Integration-mode; principles + vocabulary borrowable
        (already exercised in [[id:7dcbce8b-0941-48ec-a17d-c623ba00883a][side-quests.org]] § Agor
        prior-art and [[id:30d4ee70-0472-4bcb-a02e-efde52bef3c6][architecture.org]] design rule 5).
        *No public / FOSS-distribution claims around Agor as
        part of org-llm; no fork; no n=many shipping.*
     2. *Post-2029-01-15:* license auto-converts to Apache
        2.0. Re-evaluate fork-and-stack-component using three
        years of accumulated personal-pilot experience as the
        foundation for any FOSS-distribution roll-out.
     3. *Never while BSL active:* stack membership is off the
        table.
   - *Superset (Apache 2.0)* — currently integrate (Phase 2026-07.01 — Apache Superset dashboards
     dashboards talk to a Superset instance). FOSS-licensed,
     so fork-and-stack is *available* if warranted; not
     currently chosen, but the option is live under the stack
     rule.

6. *Defaults rule (FOSS-only baked-in).* Even within the
   integration lane — where any-license peers are allowed —
   *defaults baked into runtime code must be FOSS-licensed*.
   Concretely: a closed-API model can be a user-selectable
   *option* (e.g. =org-llm claude= subcommand, catalog entry
   for =anthropic/claude-sonnet-4.6=, askbook =claude= backend,
   proxy routing to =anthropic/*= prefixes), but it must NOT
   appear as the value of a default config field, the
   recommendation an unconfigured user lands on, or a fallback
   target when no model is set. The integration surface stays;
   the auto-fill goes. Implemented 2026-05-05 EST: the
   validation framework's =judge_model= default flipped from
   =claude-opus-4-7= to =qwen/qwen-2.5-72b-instruct= (Apache
   2.0); the =cloud_fast_model= config commentary dropped its
   =anthropic/claude-haiku-4.5= suggestion. The FOSS-first
   gate (=proprietary_models_enabled=, default =false=) was
   already enforcing this for cloud recommendations and
   failover routing — this rule extends the same posture to
   judge / fallback / suggestion-text defaults that previously
   slipped through.

7. *Doc-recommendation rule (signposting allowed).* In
   user-facing docs, *recommending* an integration (naming it,
   describing how it composes, providing setup hints) counts
   as *integration signposting* — explicitly allowed.
   Recommending an integration is *not* the same as
   shipping it as a stack dependency or as a baked-in default.
   Concretely, doc copy may say "org-llm integrates with Agor
   for multi-agent coordination — set it up via =agor init=
   then point org-llm at it" without violating the BSL-1.1
   pre-2029 stack-membership prohibition. The line is: *we
   describe how the integration works; we don't bundle the
   integration partner into our distribution.* Resolved
   2026-05-06 EST in answer to [[id:1e75cdba-f743-456d-9d0f-07b9e0da33ac][multi-agent-org-llm.org]] open
   question § License & posture (1).

*Consequences.*

- DEC-010's anti-enclosure rule is now *layered*: license
  family fixed for the org-llm tree (DEC-010); integration
  lane explicitly opened for non-FOSS peers (DEC-017);
  vendor sniff test applies to both lanes.
- Future "should we adopt X?" arguments split cleanly: ask
  *which mode* before asking *which license*. Many
  arguments collapse once the mode is named.
- The dev-tracker Agor entry's framing question ("value
  over native Claude Code subagents") is wrong shape under
  DEC-017 — Claude Code is a developer tool, not part of
  the org-llm stack baseline. Correct comparison baseline
  is org-llm's own multi-agent surface (proxy + @-personas
  + delegate.fork + scout pattern). Fixed in the entry.
- Forecloses: ad-hoc "let's just vendor X" decisions for
  yellow-zone projects; marketing claims that frame
  integration peers as stack components; treating Claude
  Code subagents as the org-llm-side baseline for
  multi-agent work.
- Triggers revisit: any license auto-conversion (Agor's
  2029-01-15 trigger is the first); any time a candidate
  upstream sits ambiguously between modes (e.g. a project
  we'd integrate today but might fork tomorrow — DEC-017
  says: pick one explicitly, write the change-date if
  applicable).

** DEC-018 — License: AGPL v3.0 (or later)
:PROPERTIES:
:ID:       ffbbdcfb-094d-4d06-b8f9-8ff9e9328878
:STATUS:   accepted
:DATE:     [2026-05-06]
:DECIDERS: Daniel, Claude/opus
:END:

*Summary.* The org-llm code tree is licensed *AGPL-3.0-or-later*
— the GNU Affero General Public License v3, with the standard
"or any later version" upgrade clause. AGPL is the chosen
realisation of [[id:2c8f6b1d-4e9a-4c3f-86b7-9d5e1f2a8c47][DEC-010 — anti-capitalist FOSS]]'s deferred
license call: it is the strongest copyleft compatible with
the existing dep tree (Apache 2.0 + GPL + MIT/BSD), it closes
the SaaS-hosting enclosure hole via §13 (network-use trigger),
and it carries OSI/FSF approval — keeping org-llm inside the
"really FOSS" tent while still being structurally
anti-enclosure. Vault content is *not* covered (org-roam files
are user data, not org-llm code).

*Expanded.* DEC-010 fixed the *family* (copyleft, anti-enclosure,
share-alike) but explicitly deferred the *specific* license,
flagging "likely AGPLv3" as the lean. The scoping memo
(=/tmp/license-decision-2026-05-05.md=) compared eight options
across five dimensions: anti-enclosure strength, anti-capitalist
fit, dep-tree compatibility, OSI/FSF approval, adoption signal.
AGPLv3 was the only license that scored well on all five
without compatibility blow-ups.

*Context.*

- DEC-010 (2026-05-04) committed to copyleft, banned permissive,
  banned commercial-enclosure, banned CLA-with-relicense; the
  specific license was open.
- The dep tree includes Apache 2.0 (ollama, dbt-core, sqlite-vec),
  GPLv3 / Emacs (Doom + emacs core, on the integration side per
  [[id:7d4e1a9c-8b62-4f37-9e5d-c1a9f3b8e6d2][DEC-017]]'s integration vs. stack distinction), MIT/BSD
  (most Python deps). Apache 2.0 → AGPL is one-way compatible;
  MIT/BSD trivially compatible.
- The 2025 industry signal converged on AGPLv3 as the
  anti-enclosure-without-bad-faith Schelling point: Redis
  abandoned SSPL → AGPLv3, Elastic added AGPLv3 alongside ELv2,
  Sentry adopted AGPLv3 long-form. SSPL is treated as a poison
  pill by Debian/Fedora and by community discourse; ACSL/CSL/HL3
  fail OSI/FSF approval and break dep-tree compat.
- The user's framing in DEC-010 ("anti-capitalist, not just
  FOSS") was tested against declarative options (HL3, ACSL) vs.
  structural options (AGPL, EUPL). The structural reading won:
  DEC-010 also forecloses CLA-with-relicense, which signals
  "stay redistributable inside the FOSS commons" — i.e. accept
  OSI/FSF as the credibility tent.

*Decision.*

1. *License is AGPL-3.0-or-later.* The "or any later version"
   clause lets future AGPL revisions (e.g. an AGPLv4 if FSF
   ships one) apply automatically. Repository =LICENSE= file
   is the canonical GNU AGPL v3 text fetched verbatim from
   the FSF / GitHub licenses API; *not paraphrased*.
2. *=pyproject.toml= carries the SPDX identifier* via
   =license = { text = "AGPL-3.0-or-later" }= and the OSI
   trove classifier =License :: OSI Approved :: GNU Affero
   General Public License v3 or later (AGPLv3+)=.
3. *Vault content is excluded.* The license covers org-llm
   code (Python, elisp, TypeScript, dbt SQL, shipped templates).
   It does *not* cover the user's =~/org/= vault — those are
   user data, owned by the user, distributed only with
   explicit user action.
4. *Fallback if AGPL ever blocks something genuinely valuable:*
   EUPL v1.2 (rec'd in the scoping memo). EUPL has explicit
   GPLv3/AGPLv3 compatibility appendix, so a future relicense
   to EUPL is mechanically clean. Not on the table now;
   recorded as a known escape hatch consistent with DEC-010's
   "trigger revisit" clause.
5. *Contributor model unchanged from DEC-010 §4.* No CLA;
   contributions inbound under AGPL-3.0-or-later by submission;
   no relicensing path that would let a corporate sponsor
   re-enclose.

*Consequences.*

- *DEC-010 is now fully realised.* The deferred license call
  is closed; future "what license?" questions point at this DEC.
- *Vendor / integration sniff test* (DEC-010 §2 + [[id:7d4e1a9c-8b62-4f37-9e5d-c1a9f3b8e6d2][DEC-017]]) still
  applies. AGPL is the *outbound* license for the org-llm tree;
  it does not change the rules for who we *integrate* with.
  Closed-source integration peers (Claude, GitHub) are unaffected
  per DEC-017's two-mode framework.
- *README license section flipped GPL-3.0 → AGPL-3.0-or-later*
  on 2026-05-06 EST. Prior README copy was inherited drift, not
  a deliberate license claim; no historical commits ever
  distributed under GPLv3 (org-llm has not yet shipped a tagged
  prod release).
- *Stack-composition rule (DEC-017 §2) tightens.* "FOSS-only,
  copyleft-compatible" now means "AGPL-3.0-or-later compatible"
  in concrete terms. Apache 2.0 absorbable (one-way relicense
  at fork). Permissive MIT/BSD absorbable. GPLv3 absorbable
  upward to AGPLv3 (FSF-provided compat). BSL / SSPL / source-
  available remain non-stackable.
- *Forecloses* permissive relicensing, open-core / dual-license
  shapes, CLA-based corporate-relicense pipelines, hosted-service
  enclosure (the §13 trigger blocks it), proprietary forks
  distributed without source.
- *Triggers revisit:* (a) FSF publishes AGPLv4 — "or-later"
  clause auto-applies, no DEC needed; (b) EUPL v1.2 becomes
  necessary as fallback (e.g. AGPL paranoia blocks valuable
  contributions from corp-employed devs whose employers
  blanket-ban AGPL but allow EUPL) — file new DEC referencing
  EUPL's GPLv3/AGPLv3 compat appendix; (c) anti-capitalist
  intent statement filed as separate =LICENSE_PHILOSOPHY.md=
  / README pull-quote per DEC-010's "spread the practice" tone.

** DEC-019 — Versioning: Hybrid SemVer + acpt suffix
:PROPERTIES:
:ID:       08281ee7-b2ae-4126-b081-5885828be5e0
:STATUS:   accepted
:DATE:     [2026-05-06]
:DECIDERS: Daniel, Claude/opus
:END:

*Summary.* Org-llm uses *Hybrid SemVer + acpt suffix*: prod
releases tagged =vMAJOR.MINOR.PATCH= (strict SemVer), acpt
candidates tagged =vMAJOR.MINOR.PATCH-acptN= (incrementing N
within a target MINOR), trunk / dev builds versioned
=MAJOR.MINOR.PATCH+devSHA= (PEP 440 local-version, derived
from git). Promotion gate strips the suffix: =v0.2.0-acpt3=
that survives the [[id:e2c47df1-3a86-4f9e-9d13-7c4b8e2f5a91][DEC-016]] 24h dogfood window becomes
=v0.2.0=. v1.0 cuts only when the gate items in
[[id:81d0f3bc-4b91-4cb3-8d22-5a83c3f6f7e2][whole-picture.org § The versioning shape]] all land — Phase
24.2 (recovery hooks) ✓ today, Phase 2026-05.02.03 — confusion detector (confusion detector)
pending, Phase 2026-05.01 — physical extraction (physical extraction) pending, retrieval-
bug sweep, cross-platform install validation (macOS + Ubuntu).

*Expanded.* This formalises the path already started: =v0.1.0=
is the current =pyproject= version, =v0.1.0-acpt0= was the first
acpt-tier tag (DEC-016 baseline, 2026-05-05). The scheme makes
DEC-016's three branch tiers directly visible in the version
string itself, which means a glance at =org-llm --version=
tells you which tier the install came from without consulting
config.

*Context.*

- DEC-016 (2026-05-05) created three SDLC tiers — dev / acpt
  / prod — with code branches (=trunk → acpt → main=) and
  install slots (=editable / acpt-pinned / tag-pinned=) but
  did not specify the version-string shape.
- The scoping memo (=/tmp/versioning-scheme-2026-05-05.md=)
  compared six schemes: SemVer, CalVer, ZeroVer, Channel-based,
  Hybrid SemVer + acpt suffix, plus the implicit "no scheme."
  Hybrid won on three counts: (a) preserves the v1.0 milestone
  as a *meaningful* event matching the "first usable" ladder,
  (b) maps 1:1 onto DEC-016's tiers without inventing parallel
  structure, (c) already running in the wild (=v0.1.0-acpt0=).
- whole-picture.org § The versioning shape (2026-05-05) named
  five stages of "first usable" — (a) personally usable today
  → (e) self-sustaining ecosystem — and pinned v1.0 ≈ stage (c)
  stranger-installable. That gives the version scheme a
  concrete ratchet: v1.0 is not "we feel ready," it's "the
  named gate items all closed."
- Pre-1.0 SemVer is technically permissive (the spec says
  "anything goes" before 1.0), but org-llm uses the stricter
  local convention below to make the version number actually
  carry information during the 0.x era.

*Decision.*

1. *Three version forms, one per tier:*
   | Tier | Branch | Install slot          | Version form              | Example                     |
   |------+--------+-----------------------+---------------------------+-----------------------------|
   | dev  | =trunk= | editable              | =X.Y.Z+devSHA= (PEP 440)  | =0.2.0+dev.g4828f94=        |
   | acpt | =acpt= | uv tool, acpt-pinned  | =vX.Y.Z-acptN= (git tag)  | =v0.2.0-acpt0=, =v0.2.0-acpt1= |
   | prod | =main= | uv tool, tag-pinned   | =vX.Y.Z= (signed git tag) | =v0.2.0=                    |

2. *PEP 440 translation at PyPI publish time* (when org-llm
   eventually publishes wheels): =vX.Y.Z-acptN= → =X.Y.ZaN= for
   sdist filenames; =X.Y.Z+devSHA= passes through unchanged
   (PEP 440 supports local version identifiers). Translation
   is automated by the release script, not hand-edited.

3. *Bump rules.*
   - *MAJOR* — breaking change to a stable surface (post-1.0:
     CLI verbs, on-disk vault contract, =~/.config/org-llm/=
     schema, public Python API; pre-1.0: only used if a major
     conceptual reset happens — unlikely while 0.x).
   - *MINOR* — new feature batch shipped (new agent, new MCP
     tool, new CLI verb, new wiki concept that affects user
     workflow). Pre-1.0, MINOR *may* break compatibly per
     SemVer §4 — documented as such in CHANGELOG / wiki.
   - *PATCH* — fix or doc-only / hotfix-tier acpt cycles.
   - *acptN suffix* — increments per acpt iteration within a
     target MINOR; resets to =acpt0= when the target MINOR
     advances.

4. *=pyproject.version= rule.* Holds the *next prod version
   being cooked.* So during the =v0.2.0-acpt0..N= window,
   =pyproject.version = "0.2.0"=. Immediately after =v0.2.0=
   ships, flip =pyproject.version = "0.3.0"= so dev builds
   downstream of the prod tag carry the right next-prod
   anchor. Trunk dev installs encode their actual identity
   via the =+devSHA= local-version suffix derived from
   =git describe= at install / runtime.

5. *Promotion gate is "strip the suffix."* When acpt-tier
   passes the DEC-016 24h dogfood window + agent-runnable
   tests + human sign-off (where required), the same SHA
   gets re-tagged as =vX.Y.Z= (no suffix). =org-llm self
   promote --to=prod --version=vX.Y.Z= enforces this rule
   and refuses to skip the suffix-strip step.

6. *v1.0 cut criteria.* v1.0 ships when *all five* gate
   items in whole-picture.org § The versioning shape are
   green: Phase 2026-05.02.02 — recovery hooks (recovery hooks), Phase 2026-05.02.03 — confusion detector (confusion
   detector), Phase 2026-05.01 — physical extraction (physical extraction), retrieval-bug
   sweep, cross-platform install validation (macOS + Ubuntu).
   Snapshot 2026-05-06 EST: 24.2 shipped today; 24.3 + 26.2
   pending; retrieval + cross-platform pending.

7. *0.x → 1.0 transition example.* MINOR-per-feature-batch
   pre-1.0: =v0.1.0= → =v0.2.0-acpt0..N= → =v0.2.0= → … →
   when v1.0 gates close → =v1.0.0-acpt0..N= → ≥24h dogfood
   → =v1.0.0=. v1.0 is also the moment FOSS-public announce
   lands per [[id:2c8f6b1d-4e9a-4c3f-86b7-9d5e1f2a8c47][DEC-010]]'s "first usable = stranger-installable"
   alignment.

*Consequences.*

- *DEC-016 is now operationally complete* — three tiers AND
  three version forms. No more hand-waving about tag shape.
- *The version string is self-documenting.* =org-llm
  --version= alone tells a user / agent / log scrape which
  tier they're in. No need to consult =ORG_LLM_ENV= or
  =uv tool list= to disambiguate.
- *PyPI publish path is unblocked* whenever org-llm decides
  to publish — translation rule is fixed; alpha-release
  semantics (=0.2.0a3= for =v0.2.0-acpt3=) match standard
  Python ecosystem expectations.
- *Pre-1.0 SemVer ambiguity is resolved* by the stricter
  local bump rules above. =0.x= still honestly signals "API
  may shift between MINORs," but each shift carries
  intentional meaning (feature batch vs. fix).
- *Forecloses* CalVer (no breaking-change signal), ZeroVer
  drift (v1.0 has a concrete gate now, not a vibes call),
  channel-based dual-history (DEC-016 already gives us tiers
  without parallel branches), unmarked rolling releases,
  silent post-1.0 breaking changes.
- *Triggers revisit:* (a) we hit v1.0 → strict SemVer
  promises kick in, MAJOR bumps now carry real cost; (b) we
  decide to publish to PyPI before v1.0 — translation rule
  works but adds publish step at every promotion (file as
  separate decision when the time comes); (c) acpt iteration
  count blows past =acpt9= regularly — likely signals MINOR
  granularity is too coarse, revisit feature-batch boundary
  rule.
