* Summary

*Summary.* =multi-agent-org-llm= is the named feature of org-llm
where /agent teams build big things for you/. The unit is a *team*
(a structured grouping of multiple agents, often heterogeneous), not
a lone agent. Teams have two lifetimes: *spike* (one-off, time-boxed,
dissolves on completion) and *long-lived* (perma-roles, persist
across sessions, evolve toolsets + roster). Implementation is
delivered via the *Agor integration* (per [[id:190baa35-06d1-4b34-a67d-2926859f47cb][DEC-017]] —
integration-only pre-2029-01-15); we do *not* build a parallel
multi-agent runtime.

*Expanded.* This page is the canonical definition of
=multi-agent-org-llm= — what it is, what shapes it takes, where it
lives in the stack, and what's native vs. integrated. Until
2026-05-05 the feature was named (per memory
=project_agor_is_multi_agent_integration=) but not canonized in
the wiki; this page closes that gap. The /scope/ is Agor as a
companion tool for org-llm's @-agents to coordinate at runtime
(plus assists to org-llm's runtime functioning) — Agor as a
dev-workflow tool for the maintainer is out of scope here.

* Purpose

/Agent teams build big things for you./

"Big" = work that one agent or one human can't do alone. Three
concrete shapes framed as team-coordination work:

- *Multi-agent vault sweep* — =@boothby= captains a heartbeat-fired
  team where =@geordi= drift-checks, =@atoz= link-fixes,
  =@spock= cross-references. Each runs in its own worktree session
  against a shared boardId; results converge to one canvas card
  before any vault writes land.
- *Coordinated phase extraction* — Phase 2026-05.01 — physical extraction — physical extraction
  dispatches extractor + test-runner + doc-updater + reviewer as
  four sibling sessions on one boardId; they query each other via
  =mode:"btw"= without blocking the captain.
- *Cadenced cross-cutting analysis* — daily-review long-lived team
  fires from Agor's scheduler (=Scheduled: daily-review=), pulls
  vault facts deterministically, then narrates via the @-prefix
  proxy seam in one cloud call per agent.

Solo opencode can do many things; =multi-agent-org-llm= is for
the things that need a *team*.

* The unit is a team

A *team* is a structured grouping of multiple agents (Bridge
Crew members + extension-path personas), assembled for a job.
Teams are the next concept layer above the @-agents (per
[[id:190baa35-06d1-4b34-a67d-2926859f47cb][DEC-009 — curated core agent team + extension path]] /
[[id:190baa35-06d1-4b34-a67d-2926859f47cb][DEC-014 — Bridge Crew]] roster) — composing them, not
replacing them.

/Team is a new concept in org-llm./ Until this page (2026-05-05),
the wiki canonized agents (per [[id:a8f4c2e1-9b3d-4e5f-87a6-c1d2e3f4b5a6][agents.org]]) and the manager
pattern (=@picard= → =delegate()=), but never the team layer
above them. =multi-agent-org-llm= is where the team concept
enters the wiki. The Bridge Crew roster is the population;
teams are how that population organises around work.

A team has: a *roster* (which agents); a *captain* (usually
=@picard=, sometimes a domain specialty captain); a *purpose*; a
*lifetime* (spike or long-lived); a *toolset* (evolves); a
*workspace* (worktree(s) + canvas board(s) when integrated via
Agor); and an *audit trail* (captain's log + per-member journal +
Agor session genealogy).

* Two team lifetimes

| Lifetime         | Shape                                                   | Dissolve trigger                                |
|------------------+---------------------------------------------------------+-------------------------------------------------|
| *Spike team*     | Rises up for one-off / time-boxed work                  | Job ships (PR merged, report delivered, etc.)   |
| *Long-lived team* | Perma-roles; persists across sessions; evolves over time | Goal sunset (rare); roster reshape (more common) |

*Both shapes validated 2026-05-06.* The /spike-team/ pattern ran
end-to-end against the license-decision investigation (3 children,
factual SSPL→AGPLv3 correction caught by =@spock= on cross-check —
solo =delegate()= would have rubber-stamped the prior wrong draft);
canon prior to 2026-05-07 listed both shapes as designed-not-run.
The /long-lived team/ pattern validated as a 1-tick smoke of the
vault-hygiene team (=@boothby= captain + =@geordi= drift +
=@atoz= link-fixes) — PASS within a single 24 h JWT window, daily-
cron promotion gated on the token-refresh primitive (now landed —
see § /Role of the Agor integration/ /What changes/ below).
*(verified 2026-05-07 EDT)*

*Transitions between lifetimes.* A spike team can graduate to
long-lived when its job recurs (one vault-cull spike that proves
useful weekly becomes the vault-hygiene long-lived team). A
long-lived team can disband when its goal sunsets (drift-detection
team dissolves once auto-classifier reaches steady-state). The
substrate is the same — assistants + boardId — only the schedule
attachment and =memory/{date}.md= retention shift.

* Teams evolve

A team is not a fixed roster — it's an evolving unit:

- *Toolsets adapt* as the team's work surfaces new needs. Agents ask
  before installing tools (per memory =feedback_agent_tool_install_rule.md=) and install in venvs.
  Self-coded tools per Phase 2026-05.20 — sync verb POC retire LLM-driven steps when the
  pattern is stable. /Concrete example./ The vault-hygiene team
  begins with =@boothby= calling =delegate('geordi', …)= for
  drift heuristics; once a heuristic stabilises (e.g. "tag
  taxonomy duplicate detection"), Phase 2026-05.20 — sync verb POC promotes it to a dbt
  model + first-class data tool, and the team's per-cycle LLM
  cost drops while throughput climbs. The agent roster doesn't
  change; the toolset under it does.
- *New agent types emerge* to fill specialty roles within teams.
  Phase 2026-05.14.02 — DB-backed registry — user-supplied agents library (literate config in
  =~/org/org-llm-agents.org=) is the mechanism; community-shareable
  per [[id:190baa35-06d1-4b34-a67d-2926859f47cb][DEC-014 — Bridge Crew]].
- *Role composition drifts* — what each member does within a team
  shifts as the team learns its shape; not pinned at team-formation.

* Role of the Agor integration

Per [[id:190baa35-06d1-4b34-a67d-2926859f47cb][DEC-017]] (stack composition vs. integration), Agor is
*integration-only* until 2029-01-15 (BSL 1.1 → Apache 2.0 auto-convert
date), and the integration is *what we call =multi-agent-org-llm=*.

The integration's role is to provide:

- The *team substrate* — boards (canvas containers) + assistants
  (perma-role members with =SOUL.md= / =IDENTITY.md= / =USER.md= /
  =memory/{date}.md= identity files) + sessions (ephemeral worker spawns)
- The *async-peer-query primitive* — =agor_sessions_prompt(mode:"btw")= /
  =subsession= for inter-agent communication mid-turn
- The *worktree-per-session* anchor — sessions pinned to isolated git worktrees
- The *scheduler* for long-lived team heartbeats (cron-style, Handlebars-templated)
- The *cross-tool delegation* primitive (Claude/Codex/Gemini/OpenCode override per spawn)
- The *team-observability surface* — multiplayer canvas, facepile, shared terminal

*MCP surface shape — progressive disclosure (not flat).* =tools/list=
on the Agor MCP server exposes only two tools: =agor_search_tools=
and =agor_execute_tool=. All other capabilities (=agor_sessions_spawn=,
=agor_sessions_prompt=, =agor_artifacts_publish=, =agor_assistants_list=,
…) are *discovered* at runtime via =agor_search_tools= and *invoked*
indirectly via =agor_execute_tool({toolName, arguments})=. Prompts
that say "use =mcp__agor__agor_sessions_spawn=" no-op against
v0.17.3; the working shape is to nudge the agent through the
discovery indirection. *(verified 2026-05-07 EDT — was assumed flat
in canon prior to the 2026-05-06 smoke run)*

What the integration does *not* replace:

- The *@-prefix proxy seam* per [[id:190baa35-06d1-4b34-a67d-2926859f47cb][DEC-008 — Phase 2026-05.02.01 — pre-flight resolvers wires at the @-prefix seam]]
  (per-message persona swap) — stays at the proxy
- The *Phase 2026-05.02 — supervision trinity supervision trinity* (pre-flight resolvers + recovery hooks + confusion detector) — stays native
- The *vault as canonical truth* per [[id:190baa35-06d1-4b34-a67d-2926859f47cb][DEC-011 — DB is universal interface; files canonical]] — stays native
- The *captain's log* (=org_llm/logbook.py= rotated event records) — stays native

Agor sits *above* org-llm's engine layer, not at the proxy seam.

*What changes if the integration is adopted.* The team primitives
build on Agor's substrate (assistants + boards + sessions +
scheduler) instead of on a parallel org-llm runtime; we *don't*
build a multi-agent runtime, a custom scheduler, or a per-assistant
memory store. The dependency means a daemon (=agor daemon=) needs
to be running locally for team sessions to spawn — but the @-prefix
single-agent path keeps working untouched if Agor is down. The
whole arrangement re-evaluates at the BSL → Apache 2.0 change date
(2029-01-15) per [[id:190baa35-06d1-4b34-a67d-2926859f47cb][DEC-017 — stack composition vs. integration]].

*Validated primitives + known v0.17.3 bugs (state as of 2026-05-07

* Coordination patterns

How *teams* of agents use Agor to coordinate. Each pattern names
the Agor primitive, the org-llm need it serves, and the seam where
the two compose.

** Sibling-session by boardId

*Summary.* All members of a team open sessions on the *same*
=boardId=; sibling-discovery is "list sessions on my board." The
board IS the registry — the captain doesn't need a separate one.
*Captains spawn siblings sequentially via one-=claude -p=-per-spawn
invocation* (not parallel; see also "Async peer query" coordination
note below). *(3-member team verified end-to-end 2026-05-06 EDT
via vault-hygiene pilot; cost $0.21 wall 257s.)*

*Expanded.* Each role spawns a session pinned to a worktree on
the team's shared board; members see each other in the facepile.
Maps cleanly to Bridge Crew roles, each as one assistant
with its own =model_role=. Replaces in-process =delegate()=
when peers must remain alive across multiple captain turns.

*Sibling-spawn pattern (verified 2026-05-06 EDT).* Captains that
spawn 2+ children must do so via *one =claude -p= subprocess per
spawn*, not by queueing multiple =agor_sessions_spawn= tool_uses
inside one captain context. Two reasons: (1) claude-code+sonnet
under MCP indirection does not honor parallel-tool-use — it
serializes into multiple assistant messages anyway; (2) multiple
queued tool_uses in one captain context, combined with token-budget
pressure + informational =rate_limit_event= pings, can stall the
captain mid-narration (round-1 D2 + round-2 R2-Model both
reproduced this stall). Refresh =mcp_token= via =GET
/sessions/{captain_id}= between spawn invocations to preserve
captain MCP context. /Pattern in/ =scripts/_r2_d2.py=.

*Sibling-discovery shape (verified 2026-05-06 EDT).* Within an
Agor session, peer enumeration is =GET /sessions?worktree_id=<wt>=.
=session.genealogy.children= is a /list of session ID strings/
(not list[obj]); to read any child's =fork_origin= or other
metadata, callers must =GET /sessions/{child_id}= individually.

** Async peer query (=mode:"btw"=)

*Summary.* Agent A asks agent B a focused question mid-turn
without blocking; B's answer arrives as a /new session/ with
=fork_origin:"btw"= + =callback_config.callback_mode:"once"=,
which the caller polls (or the daemon invokes via callback).
Fills a real gap in org-llm. *(end-to-end verified 2026-05-06 EDT
via Pilot R2-B; concrete child session
=019e000e-2305-70d9-bb8e-5735e577652f=.)*

*Expanded.* =agor_sessions_prompt(mode:"btw", target:<peer>,
prompt:…)= spawns an ephemeral child session tagged with
=fork_origin:"btw"=; its =callback_config.callback_mode= is
=once=, so the answer materialises exactly once — either by the
caller polling genealogy for the new child or by the daemon
firing the callback. The child auto-archives on completion. (The
v0.1 smoke harness confirmed the actual shape; canon prior to
2026-05-07 incorrectly described it as "answer returns inline via
callback when A next checks.") Today's =delegate()= is
synchronous-string-return; it can't ask =@geordi= a clarifier
mid-turn without forcing the caller to wait. Use case: =@atoz=
mid-wiki-sweep asks =@spock= "is this the canonical link?"
without halting the sweep.

*Discovery shape (verified 2026-05-06 EDT — canon-correcting).*
The =btw= ephemeral child lands on the *target's*
=genealogy.children=, NOT the *caller's*. =forked_from_session_id=
points at the target; =callback_config.callback_session_id= points
at the caller. To find btw children spawned by AGENT_A targeting
AGENT_B, inspect AGENT_B's =genealogy.children=, GET each child,
filter by =fork_origin == "btw"=. Round-2 R2-B initially probed
the caller's children and found nothing — fix landed in
=scripts/_r2_b.py=.

** Scheduled heartbeat

*Summary.* Long-lived teams attach cron-style schedules to their
boardId; each tick spawns a =Scheduled: <worktree>= session that
reads =HEARTBEAT.md= and executes the team's recurring work.

*Expanded.* Fills the [[id:c4e2d3a1-7f9b-4c5e-8d6a-2b3f4e9c1d57][agent-time-awareness.org]] § Layer 3
(cross-cutting orchestration) gap. Daily-review team: cron
=0 8 * * *= → Handlebars prompt with =board.custom_context= →
captain narrates over deterministic vault-fact reads. Honors
[[id:190baa35-06d1-4b34-a67d-2926859f47cb][DEC-006 — supervision is deterministic by default]]: heartbeat
fires data tools first; LLM narrates pre-fetched data.

** Scout-pattern dispatch

*Summary.* Captain spawns a specialist child session with a
focused context window; specialist returns via the session
genealogy callback. Generalises today's =delegate()=. The
mechanism — =agor_sessions_prompt(mode:"fork", …)= — is also the
spike-team primitive validated 2026-05-06 (license-decision
pilot, factual correction caught by =@spock=). *(verified
2026-05-07 EDT — no separate =agor_sessions_fork= tool exists)*

*Expanded.* =agor_sessions_prompt(mode:"fork", …)= creates a
sibling-from-shared-worktree child with a curated context slice
(not the parent's full history). =@picard= dispatches =@spock=;
=@spock= runs in its own session under the shared worktree,
emits artifacts + summary; the result is reachable from
=@picard='s session tree even after =@picard='s turn ends.
"Delegate the call, *keep* the thread." Canon prior to
2026-05-07 referenced =agor_sessions_fork= as a tool name —
there is no such tool in v0.17.3; the dispatch surface is
=agor_sessions_prompt= with the =mode= argument.

** Cross-tool escalation

*Summary.* When an agent's work needs a different *tool* (not
just a different model), the spawn carries a per-call assistant
override (Claude vs. Codex vs. Gemini vs. OpenCode).

*Expanded.* Today =delegate(model_override=…)= overrides only
the model. Agor's spawn-override goes higher: the child runs
under a *different cloud-coding tool* with that tool's full
toolbelt. Must respect [[id:190baa35-06d1-4b34-a67d-2926859f47cb][DEC-017 § 6 — Defaults rule]] —
proprietary backends are user-selectable, never default.

** Shared multiplayer terminal

*Summary.* Spike teams working on overlapping scope get a
real-time canvas with live cursors + facepile, layered above the
worktree escape hatch.

*Expanded.* DEC-005's worktree escape hatch separates working
trees. Agor's multiplayer canvas adds a *visible* coordination
surface above that: agents see each other's cursors, zone-
templated prompts fire when artifacts move into review zones,
humans can drop in to spot-check. Worktree isolation stays;
canvas adds situational awareness.

** Captain's-log + session-genealogy reconciliation

*Summary.* Agor's session genealogy tree is reconciled into
org-llm's captain's log so provenance is unified.

*Expanded.* Each Agor session retains prompts/responses on disk
as a tree (parent → spawn / btw / fork edges). On session end, a
bridge writes a =kind=team-session= entry to captain's log with
=boardId=, =sessionId=, =parent=, =assistant=, =model=,
=duration=. Vault stays canonical (per [[id:190baa35-06d1-4b34-a67d-2926859f47cb][DEC-011]]); Agor's DB stays
its own truth for session bodies; captain's log is the join key.

* "Anything else" — non-coordination assists

Uses of Agor that aren't strictly team-coordination but help
org-llm's runtime functioning.

** Live artifact preview

*Summary.* Agents emit React/JSX/TS into a worktree and call
=agor_artifacts_create=; Sandpack renders it live in-browser.

*Expanded.* Use cases: =@geordi= drafts a chart before
committing to a Superset card; =@atoz= previews a wiki
layout; an agent emits an interactive form to capture a
multi-option decision. Artifact source lives at
=.agor/artifacts/<id>/= — file-based per [[id:190baa35-06d1-4b34-a67d-2926859f47cb][DEC-011]]; render is
ephemeral.

** Message Gateway (Slack / GitHub)

*Summary.* =@agor= mention on Slack DM, GitHub PR, or issue
spawns a thread-bound session; follow-ups continue the same
session; agent replies post back as bot comments.

*Expanded.* Lets the user trigger a team from outside Emacs.
Use case: open a PR, tag =@agor= asking =@atoz= to verify
cross-refs; gateway spawns the session, =@atoz= sweeps, posts
findings as a PR comment. Outbound-only transport (Slack Socket
Mode / GitHub polling) keeps webhooks off the user's network.

** Persistent agent memory substrate

*Summary.* Per-assistant =SOUL.md= / =IDENTITY.md= / =USER.md= /
=memory/{date}.md= fills the filed-not-built Layer 2a per-agent
journal slot in [[id:739868a9-f62c-43de-ac1d-1671d483a2c1][standing-orders.org]].

*Expanded.* The standing-orders memory model names three layers;
Layer 2a (per-agent observations) is partially served today by
=crew_log= + captain's log but lacks a clean per-agent journal.
Agor's =memory/{YYYY-MM-DD}.md= is exactly that shape. Layer 2b
(cross-agent standing orders) stays in =AgentBaseline= because
the broadcast semantics need DB indexing the files don't.

** Worktree-per-session as hygiene

*Summary.* Every Agor session is pinned to its own git worktree;
no two sessions touch the same working directory.

*Expanded.* Generalises [[id:190baa35-06d1-4b34-a67d-2926859f47cb][DEC-005]]'s worktree escape hatch from
"reach for it when scopes overlap" to "always-on by default."
Long-running risky work (Phase 2026-05.01 — physical extraction extraction, mass-cull walks)
runs with zero contention against the maintainer's primary
stream. Cleanup: =git worktree remove= + session archive.

** Per-assistant =.agor.yml= env templating

*Summary.* Each assistant carries its own =.agor.yml=; honors
per-device + per-env config keying per [[id:190baa35-06d1-4b34-a67d-2926859f47cb][DEC-012]] / [[id:190baa35-06d1-4b34-a67d-2926859f47cb][DEC-016]].

*Expanded.* =@boothby= on laptop runs nightly hygiene with full
write access; same agent on phone is read-only. =Config(key,
device, env, value)= already encodes that policy in DB;
=.agor.yml= is where it lands at runtime. Encrypted secrets stay
in the daemon DB, not the worktree.

** Canvas + facepile + cards as review surface

*Summary.* Batched agent output gets a user-facing review
surface — canvas zones for staging, facepile for "who worked on
this," cards for non-code workflow items.

*Expanded.* Today the user reviews agent output in the opencode
TUI (linear chat) or via a sidebar widget (single-pane). For
larger jobs (a multi-agent vault sweep, a Phase extraction
review), spatial review beats linear scrolling. Cards (beta)
extend the surface to non-code items — review queue for a
research roundup, capture-promote staging, etc. *This does not
replace the org-buffer for editing* per the DEC-015 candidate
chat-surface decision; canvas is review, not authoring.
