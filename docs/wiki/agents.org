#+TITLE: Agents — what they are and how they work
#+FILETAGS: :wiki:agents:architecture:overview:

* What agents are

In =org-llm=, an *agent* is a *named persona + tool roster + model
choice* that gets injected as the system prompt when the user
addresses it (=@<name>=). The proxy layer
([[id:47ba2143-c53a-409a-8286-2b3759794608][LLM proxy]]) detects the
=@-tag=, swaps the system prompt to the agent's persona, and lets
the underlying LLM answer with that voice + tool defaults.

Three things make an agent an agent (and not just a system
prompt):

1. *Persona* — a paragraph telling the LLM who it is, what tools
   it owns, and what defaults to apply (lead with a tool call,
   never invent vault content, hedge unless certain, etc.).
2. *Tool roster* — the subset of [[id:72c7e988-1a60-4624-8090-fe1f7d9ef6a8][MCP]] tools the agent is told to
   reach for. The MCP server exposes everything; the persona
   *narrows* what the agent reaches for first.
3. *Model role* — which configured model handles the agent's
   work (=chat_model= / =fast_model= / =code_model= /
   =creative_model= / etc.). Lets the user route fast scans
   through a small model while keeping deep reasoning on the
   bigger one.

The unit is *cheap*: one entry in =_PRECONFIGURED_AGENT_PROMPTS=
in [[file:../../org_llm/cli.py][=org_llm/cli.py=]] (built-in) or one heading in
=~/org/org-llm-agents.org= (user-editable, literate). No new
runtime, no extra process. Adding an agent is 4-5 lines of
persona text.

pass. The underlying capability still exists; the surface changed.

* Invocation paths

There are four ways an agent gets engaged. They compose; one user
turn may exercise more than one.

** 1. Direct =@-tag=

#+begin_example
@scribe save this as a journal entry: …
#+end_example

The proxy's =intercept_agent_prefix= parses the leading =@<name>=,
looks up the agent in the registry, REPLACES the system prompt with
the agent's persona, and forwards the request unchanged. One agent,
one turn.

** 2. Auto-route

#+begin_example
what's on my schedule this week?
#+end_example

No =@-tag=. The proxy's =intent_classify= scores the message
against every agent's =triggers= list, picks the highest-scoring
match (≥ =proxy_auto_route_min_score=), and routes there. Falls
back to the session's default agent (usually =@researcher=) when
no triggers fire. Knob: =proxy_auto_route_to_agent= (default off).

** 3. Manager-mediated delegation

User asks =@crew= a multi-domain question. =@crew='s persona
calls =org-llm_delegate(agent, prompt, context)=. The MCP layer
runs the specialist with its own persona + model, splices the
result back into =@crew='s context. Manager log captures every
hop in =crew_log=.

Special-cased: =classify_items(items, criterion)= for filter /
criterion calls. Used to be =delegate('classifier', …)=; promoted
to a first-class MCP tool in 2026-05-03 because it was never
user-facing.

** 4. Recipe pre-fetch (the proxy intercepts AHEAD of the LLM)

The lightest layer:
[[id:3ed81ee4-e28d-4daf-87fb-c1645b58a05c][recipes]] are regex →
deterministic-tool → pre-fetch shortcuts that fire BEFORE the
agent sees the message, when the question shape is known. The
agent then narrates over the pre-fetched data in one cloud call
instead of round-tripping to call the tool itself. Two recipes
ship today: =count_across_vault= and =weather_aware_agenda=. The
mechanism is opt-in per recipe, validated via the A/B harness in
[[file:../../scripts/recipe_ab_harness.py][=scripts/recipe_ab_harness.py=]] before any new entry is added.

* How agents compose with the rest of the stack

#+begin_example
            user types message
                 │
                 ▼
   ┌──────────────────────────────────────────────────────┐
   │  proxy.intercept_agent_prefix                        │
   │   1. parse @<name>?                                  │
   │   2. swap system prompt to agent's persona           │
   │   3. (recipe layer) match_recipe + execute_recipe    │
   │      → inject pre-fetch block when applicable        │
   └──────────────────────────────────────────────────────┘
                 │
                 ▼
   ┌──────────────────────────────────────────────────────┐
   │  cloud or local LLM (per agent's model_role)         │
   │   • emits tool_calls into MCP server                 │
   │   • OR narrates over pre-fetched data                │
   └──────────────────────────────────────────────────────┘
                 │
                 ▼
   ┌──────────────────────────────────────────────────────┐
   │  MCP server                                          │
   │   • routes tool_calls to org_tools / vault_facts /   │
   │     weather / delegate / classify_items / …          │
   │   • returns structured results back to the LLM       │
   └──────────────────────────────────────────────────────┘
                 │
                 ▼
   final answer rendered in the chat surface (opencode TUI,
   sidebar, or =org-llm ask= one-shot)
#+end_example

The proxy layer is invisible — opencode thinks it's talking to a
single LLM endpoint. The agent injection, recipe pre-fetch, and
tool-call repair all happen between opencode and the upstream
model. See [[id:47ba2143-c53a-409a-8286-2b3759794608][llm-proxy.org]]
for the full interceptor chain.

* Customising

The built-in registry is a *floor*. Users override at any level
via the literate file =~/org/org-llm-agents.org=:

#+begin_src org
,* summarizer                                                    :agent:
,:PROPERTIES:
,:DESCRIPTION:    My fast tl;dr specialist (uses small fast model)
,:MODEL_ROLE:     fast_model
,:TRIGGERS:       summary, summarise, summarize, tl;dr, in N sentences
,:END:
,
,You are a fast summarizer. Compress without losing meaning.
,Match the user's requested length exactly. Preserve names,
,dates, numbers, direct quotations. Lose stylistic flourish.
,If summarising a tool result, cite source paths.
#+end_src

Round-trips:
- =org-llm agents --tangle= writes the file from current built-ins +
  DB rows.
- =org-llm agents --apply= reads the file → DB rows.
- User entries override built-ins by name. Built-ins the user
  didn't redefine carry over.

This is how you re-add =@summarizer= / =@extractor= / =@writer=
as specialists with their own model_role: just add a heading. The
trigger lists in the built-in =@geordi= / =@scribe= won't conflict
because the user override registers a NEW agent name.

* Design rules (from the 2026-05-03 rationalisation)

The agent surface went from 21 → 17 in one pass after a
persona-by-persona audit. The rules that drove the cuts (reusable
for future calls):

1. *Default surface should be simple.* If two agents have ≥80%
   trigger overlap and similar tool roster, they're the same
   agent in practice — merge.
2. *Granularity stays available via the literate file.* Anyone
   wanting per-shape model routing (a tiny fast =@summarizer=, a
   creative =@writer=) breaks them out themselves; the built-in
   set ships the umbrella.
3. *If an agent is only invoked by other agents (never by the
   user), it's a tool, not an agent.* =@classifier= got demoted
   to =classify_items= for this reason.
4. *Personas earn breadth, not just feature parity.* A
   speculative agent ("I want a weather agent") often becomes a
   real agent only after we identify the broader category it
   belongs to (weather → @almanac → external context). One agent
   covering five future tools beats five narrow agents covering
   one each.
5. *Add via [[file:agentsmith.org][@agentsmith]].* The meta-agent
   is the canonical onboarding for a new persona — interviews
   you, drafts the entry, suggests triggers, validates against a
   test prompt before it lands.
