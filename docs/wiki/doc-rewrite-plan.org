* Summary

*Summary.* This page scopes the eventual multi-agent doc rewrite. It
enumerates every page in =docs/wiki/=, classifies each, identifies the
highest-leverage rewrite candidates, and proposes a rewrite style
template + dispatch protocol. User reviews this page, picks a subset,
then a pool of agents executes the rewrite against it.

*Expanded.* The rewrite is a Phase 2026-05.21 — multi-judge validation-flavored stress test
(multi-agent A/B) on a real doc-quality task — not a synthetic eval.
Three surfaces compared head-to-head: Claude Code subagent pool,
=org-llm= CLI agents, opencode session. Each surface gets the same
scoped batch of pages, produces independent rewrites, and the Phase
30.4 multi-judge scores faithfulness, tone, conciseness, and
cross-reference integrity. Best output replaces the original; losing
outputs are kept as review notes. This page is the *dispatchable
artifact* — once the user picks a subset and weights the rubric, an
agent pool can execute against it without further scoping.

The dev-tracker TODO under "Doc rewrite stress test" (Phase 2026-05.21 — multi-judge validation
candidate) is the parent ticket; this page scopes its inputs.

* The dispatch protocol

** Three surfaces, one job per page

For each page in the chosen subset:

| Surface           | Spawn shape                                       | Sandbox / branch                          |
|-------------------+---------------------------------------------------+-------------------------------------------|
| Claude Code pool  | =Task= subagent per page (one shot, then exit)    | Worktree per agent OR distinct branch     |
| org-llm CLI       | =@atoz= or =@docsmith= dispatch via MCP           | Distinct branch; coordination claim       |
| opencode session  | Single user-driven session, page-by-page          | Distinct branch; coordination claim       |

Each surface produces *one rewritten file per page*. Three outputs per
page total. None overwrites the original until judging.

** Phase 2026-05.21 — multi-judge validation multi-judge scores each output

The judge is one Opus-class call per page-output triple, blinded to
which surface produced which file. The judge returns a structured
verdict on:

- *Faithfulness* — does the rewrite preserve every load-bearing claim
  and reference from the source? No invented features, no dropped
  details that downstream pages rely on.
- *Tone match* — anti-capitalist FOSS framing per DEC-010, technical
  voice consistent with current wiki, no SaaS/funnel/MRR bleed.
- *Conciseness* — bloat down, signal up; aim 200–500 lines for concept
  pages.
- *Cross-ref integrity* — every =[[id:...]]= resolves to an existing
  node; every =[[file:...]]= path exists; no broken links introduced.
- *Wiki Rule 2b compliance* — Summary + Expanded blocks present and
  formatted correctly; this is a hard gate, not a soft preference.
- *Org-is-Code inheritance* — a rewrite must respect the design rule
  that org files are part of the toolchain (commit-able, lintable,
  diff-reviewable). No prose that breaks that contract.

** Best output replaces the original

- Winner overwrites =docs/wiki/<page>.org= on a single rewrite branch.
- The two losing outputs are saved to =docs/wiki/_rewrite-notes/<page>-<surface>.org=
  for human review (kept out of the active wiki via filename prefix).
- Judge verdict + per-criterion scores are appended to a campaign log
  at =docs/wiki/_rewrite-notes/_campaign-log.org=.

** Coordination

- Each surface holds a claim in
  [[id:281ddc58-169b-4f35-bab6-03f59c1df359][active-claims.org]] for the
  pages it's rewriting; surfaces work on distinct branches; merge
  happens after judging, not during rewriting.
- Re-Read every page immediately before editing — parallel streams
  invalidate session caches.

* Style template

The rewrite is bound by these rules. A rewrite that violates any of
these is a regression, regardless of how good the prose reads.

- *Wiki Rule 2b — Summary + Expanded.* Every concept page leads with
  =* Summary= containing =*Summary.*= (1–3 sentences, top-of-page
  abstract) and =*Expanded.*= (one paragraph context, why-this-matters
  framing). Canonized in
  [[id:d30c177e-5b09-4f52-95bf-bb2d36f663e8][wiki-conventions.org]]
  Rule 2b. Existing TL;DR / "What this is" / "What this page is"
  blocks should be folded into the Summary block, not duplicated
  alongside it.
- *Cross-ref integrity.* Every =[[id:...]]= must resolve. Every
  =[[file:...]]= path must exist. The rewrite agent runs a link sweep
  before declaring done; broken links are a hard fail.
- *Tone — technical, tight, anti-capitalist.* Per DEC-010 in
  [[id:190baa35-06d1-4b34-a67d-2926859f47cb][decisions.org]]: no
  funnel, no SaaS, no MRR, no growth-hacking copy. The wiki describes
  a FOSS tool a user installs and owns; copy reflects that.
- *Org-is-Code inheritance.* Per architecture.org § design rule: org
  files are toolchain primitives. They're committed, diffed, linted,
  reviewed. Rewrites preserve that — no decorative whitespace,
  consistent property block ordering, no inline timestamps that churn
  every commit.
- *Length budget.* Concept pages: 200–500 lines. Pages over 500 lines
  must justify the bulk (e.g. roadmap, dev-tracker, decisions are
  catalogs, not concepts). Pages under 200 lines are fine if they're
  genuinely small concepts.
- *Cull stale Phase-X early notes.* Phase descriptions that have
  shipped should be replaced with a one-line status + commit ref, not
  preserved in their original speculative shape.
- *Preserve =:ID:= properties.* Never regenerate a page's =:ID:= —
  those are addressable from elsewhere in the wiki. Rewrite the body,
  keep the property block.
- *Preserve =:CREATED:= dates; bump =:UPDATED:=.* The created date is
  history; the updated date marks the rewrite.

* Open questions for user

The dispatch can't run until these are answered. Suggested defaults
in parens; user picks or overrides.

1. *Subset to dispatch?* (Default suggestion: Wave 1 only as pilot —
   12 pages, foundational concepts, lowest-risk learning signal.)
2. *All three surfaces in parallel, or one as pilot?* (Default: pilot
   one surface — Claude Code subagent pool — on Wave 1, then add
   org-llm + opencode for Wave 2 once the protocol is debugged.)
3. *Scoring rubric weights?* The judge has six criteria; default
   weighting is equal. Likely better: faithfulness × 2.0,
   cross-ref-integrity × 1.5, Wiki Rule 2b × 1.5, others × 1.0.
4. *Auto-merge winning output, or human-review first?* (Default:
   human-review the first wave; if win-rate per surface stabilises,
   auto-merge subsequent waves with the gating criterion that no
   judge score drops below 0.7.)
5. *Where do losing outputs live?* (Default proposed:
   =docs/wiki/_rewrite-notes/<page>-<surface>.org=, gitignored from
   org-roam indexing via filename prefix.)
6. *Branch strategy?* One branch per surface, or one branch per page?
   (Default: one branch per surface for the wave, merge per-page after
   judging.)
7. *Judge model?* Opus 4.7 is the default Claude judge in Phase 2026-05.21 — multi-judge validation
   eval. Confirm or override.
