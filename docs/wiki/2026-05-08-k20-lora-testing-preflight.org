* Summary

*Summary.* R25 budgeted $8–15 for K20 v2 LoRA training but it
didn't run. The risk isn't the train — R19 trained K20 v1
cleanly on Together (3 epochs, 30 steps, 53.6 MB adapter) — the
risk is /serve/. Together's 30-attempt deploy daemon failed every
hardware × shape combo with "configuration not available for this
model"; the model trained but Together's serverless tier won't
host it. This document tracks zero-to-low-cost pre-flights we
can run /now/ to bypass that wall and de-risk v2 spend.

*Expanded.* Bypass plan: we own the adapter weights (53.6 MB
PEFT artifact, downloadable via =together fine-tuning download
-c adapter=). With weights in hand, Together becomes one of many
serving options; RunPod vLLM with =--enable-lora= becomes the
primary path. Pre-tests focus on (1) artifact integrity, (2)
chat-template parity (silent LoRA-killer), (3) actual deploy on
RunPod, (4) corpus quality for v2. All under $3 combined; most
$0.

** F3 — Chat-template parity GAP (silent quality killer)

The training-time template lives ONLY in =chat_template.jinja=
(6211 bytes, sha256=5a38bfa058332662). The companion
=tokenizer_config.json= has =chat_template= = empty string.

*Why this matters.* vLLM (and most serving stacks) auto-load
the template from =tokenizer_config.json["chat_template"]=.  If
we push this adapter to HF as-is and serve, vLLM will fall back
to the BASE model's template (Qwen3-Coder-30B-A3B-Instruct's
default). Inference token sequences will not match what the
LoRA was trained on → silent quality regression that no
=trainer_state.json= eval loss would catch.

*Mitigation.* Two options:
1. Inject the template into =tokenizer_config.json= before HF
   push: =cfg["chat_template"] = open("chat_template.jinja").read()=
2. Always pass =--chat-template /path/to/chat_template.jinja=
   to vLLM at serve time.

Recommend (1) — embed once, ship — to avoid the silent-default
trap on any future serve. Sample render confirmed standard
ChatML format:
=<|im_start|>system\n...<|im_end|>\n<|im_start|>user\n...<|im_end|>\n<|im_start|>assistant\n=

* Decisions log

** [2026-05-08] PIVOT — adapter ownership over Together-tier upgrade

Considered: pay for Together account tier upgrade to unlock
serverless deploy. Rejected: even if it works, we'd be locked
into Together's deploy quirks for v2/v3/v4. Owning the adapter
artifact (which we now do, $0) makes Together one of N options
and aligns with FOSS-first principle.

** [2026-05-08] HF_HUB_ENABLE_HF_TRANSFER=1 silent killer

Smoke v2 (vllm:v0.20.1, correct image) launched cleanly but
=/v1/models= stayed at proxy 403 for 13+ min. GraphQL runtime
showed =cpu=99% gpu=0% memory=2%= — container alive and busy
but not serving. Root cause: =HF_HUB_ENABLE_HF_TRANSFER=1= env
was set, but =hf_transfer= package is NOT in the stock
=vllm/vllm-openai= image. =huggingface_hub= errors out + retries
in a tight loop, burning pod time at 99% CPU with zero download
progress.

Also caught: original =containerDiskInGb=80= is too tight
(rule of thumb: image_gb + 2 × model_gb + 20 = ~150 for our
30B model). Bumped to 150 for v3.

Smoke v3 launched 22:32 UTC with: =HF_HUB_ENABLE_HF_TRANSFER=
unset, =containerDiskInGb=150=, runtime-stats logging every poll
so we see CPU/GPU live. Two new recipes added to AR6 catalog:
=hf_transfer_missing= and =runpod_container_disk_too_small=.

Cumulative smoke spend so far: ~$0.22 (12 + 4.5 min @ $1.39).

** [2026-05-08] vLLM image too old for Qwen3-MoE

First smoke launch used =vllm/vllm-openai:v0.6.5= (Dec 2024).
Pod reached =desiredStatus=RUNNING= and =runtime=null= for 5+
min — symptom of container init stuck on =from_pretrained=.
Same root cause as R19 LoRA training auto-heal recipe
"qwen3_moe arch missing — bump transformers to 4.51.3":
v0.6.5 ships transformers 4.46.3 which predates Qwen3MoE
support.

Bumped to =v0.20.1= (May 2026) which has Qwen3 support
baked in. Cost of the misfire: ~$0.12 (5 min × $1.39/hr).

Added recipe candidate to AR6 catalog (=vllm_image_too_old=)
in next iteration.

** [2026-05-08] RunPod REST migration — GraphQL deprecated

Initial smoke launcher used =api.runpod.io/graphql= mutations
(=podFindAndDeployOnDemand=) and got 403 Forbidden. The
GraphQL surface still serves /reads/ (balance, gpuTypes) but
pod-launch /writes/ now require =rest.runpod.io/v1=. Migrated
=scripts/_k20_v1_runpod_smoke.py= to REST.

Two REST gotchas worth recording for AR6:
1. =POST /v1/pods= with empty =\{\}= body LAUNCHES a default pod
   ($1.89/hr). No dry-run mode; validation only fires for
   /extra/ keys not /missing/ ones. Always include explicit
   =gpuTypeIds= + =imageName= even on probe calls.
2. =POST /v1/pods= returns *HTTP 201 Created*, not 200. Code that
   checks =status_code == 200= will believe launch failed and
   skip teardown — pod silently keeps running on your dime.
   Always accept =(200, 201)=.
