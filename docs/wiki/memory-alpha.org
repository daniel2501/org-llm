#+TITLE: Memory Alpha — the Trek framing for DB-authoritative inversion
#+FILETAGS: :wiki:concept:phase25:naming:framing:
#+OPTIONS: toc:1 num:nil

* What this is

A naming + conceptual frame for the Phase 2026-05.17 — DB-as-cache + git-canonical pipeline inversion. Instead
of describing Phase 2026-05.17 — DB-as-cache + git-canonical pipeline in dry shop-talk ("DB-authoritative
inversion"), describe it via the Trek concept of *Memory
Alpha* — the Federation's central library, a planetoid that
houses all cultural and scientific knowledge, accessible to any
member from any starship.

In Trek (TOS S3E18 /The Lights of Zetar/), Memory Alpha is the
central source of truth; planetary archives are local mirrors;
individual research databases (Memory Prime, in extended
fiction) are specialised authoritative subsets. Real-world: the
Trek wiki at memory-alpha.fandom.com is itself named after the
in-universe library — fans built the in-universe repository as a
real-world DB. That recursion is the spirit org-llm wants for
its own state.

(the DB inversion itself) is Phase 2026-05.17 — DB-as-cache + git-canonical pipeline.

The core re-frame: org-llm's DB is your *personal Memory
Alpha*. Your =~/org/*.org= files are the printed extracts you
carry between starships. The Phase 2026-05.17 — DB-as-cache + git-canonical pipeline work is teaching the
system that the library is canonical, not the printed extracts.

* Why this naming

"DB-authoritative inversion" is technically precise and dry.
"Memory Alpha mode" carries:

1. *A coherent vocabulary* — pairs naturally with names already
   in the codebase (=Captain's Log=, =@atoz=/Mr. Atoz, the
   starfleet-core agent pack with Trek birth-names like
   =picard=, =spock=, =data=, =janeway=, =boothby=, =riker=,
   =geordi=).

2. *An accessible mental model* — most users will grasp "central
   library + planetary mirrors" faster than "vault-authoritative
   vs DB-authoritative inversion + round-trip-fidelity canary".

3. *Built-in survival theme* — Memory Alpha was attacked in /The
   Lights of Zetar/; the survival of knowledge is a recurring
   Trek beat. Maps cleanly to backup, audit, recovery — exactly
   what =doctor=, =log --reflect=, and the audit-log loop
   already do.

4. *No commitment to over-renaming* — the technical phrase "DB
   inversion" stays valid in code, commit messages, and
   developer-facing docs. The metaphor lives in user-facing
   surfaces (verbs, persona language, README).

* The Phase 2026-05.17 — DB-as-cache + git-canonical pipeline arc as Memory Alpha construction

Mapping the six sub-phases (per [[id:43e1b335-656b-45ba-8d6d-7d9b9f2e9c4d][roadmap.org]] § Phase 2026-05.17 — DB-as-cache + git-canonical pipeline) onto
the metaphor:

| sub-phase | technical name              | Memory Alpha framing                                                         |
|-----------+-----------------------------+------------------------------------------------------------------------------|
| 25.1      | DB as full mirror            | The library ingests all extant printed extracts. Round-trip byte-equal.      |
| 25.2      | backup + restore             | Memory Alpha gets disaster-recovery procedures. =memory-alpha snapshot=.     |
| 25.3      | WAL + concurrency hardening | Multiple researchers + agents can query simultaneously without corruption.   |
| 25.4      | git ingestion as audit/history | Every edit is preserved as a versioned record — Memory Alpha gains *time*.   |
| 25.5      | DB-authoritative engine ops | Mass operations happen in the library; printed extracts re-render from it.   |
| 25.6      | full inversion              | The library is canonical. Printed extracts become a UI surface. Phase done.  |
| (Phase 2026-05.04 — cull walk)| beyond SQLite (DuckDB / Postgres) | Memory Alpha gets a new substrate when the planetoid runs out of room.  |

Round-trip fidelity is the survival check. Per the roadmap:
"if 25.1 can't achieve byte-equal on the dev's vault within ~5
days, reconsider." That's the canary the Memory Alpha frame
inherits — if extracts and the library disagree, the library
isn't ready to be canonical.

* Verb proposals (UX surface)

Three verbs that the Memory Alpha frame motivates and that
nothing in the current verb space fills cleanly:

| verb                          | what it does                                                                |
|-------------------------------+-----------------------------------------------------------------------------|
| =org-llm memory-alpha sync=   | Re-render =~/org/*.org= files from current DB state. The "extract" verb.    |
| =org-llm memory-alpha verify= | Walk every file ↔ DB row and report disagreements. The audit verb.          |
| =org-llm memory-alpha snapshot= | DB Online-Backup-API dump before destructive ops; pairs with restore.     |

These compose with Phase 2026-05.17.02 — DB-as-cache step 2's =backup= / =restore= verbs
rather than replacing them: =memory-alpha snapshot= is the
*pre-mutation* gesture (snapshot before a risky verb runs);
=backup= is the *scheduled* / cron-flavour version.

* What this is NOT

- *Not a code-wide rename.* The =VaultFact=, =History=,
  =CrewLog= tables keep their names. The =db.py= module stays
  =db.py=. Memory Alpha is a metaphor for the user-facing
  framing, not a refactor mandate.
- *Not a marketing layer that hides the technical reality.* The
  inversion still has all the same constraints (round-trip
  fidelity, WAL concurrency, conflict resolution via git
  merge). The Trek naming should never elide a real engineering
  decision.
- *Not a Federation cosplay.* The wiki should *use* the metaphor
  where it carries weight, not pile on Trek references for
  flavour. One coherent layer (DB framing + agent birth-names +
  Captain's Log + Mr. Atoz) is the budget.
