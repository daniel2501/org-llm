* What this is

The detailed phase catalog and forward-looking project plan for
=org-llm=. The README has a short overview pointing here; this is
the source of truth for "what's done, what's next, what's
later."

Phases are organic milestones, not a calendar cadence. A phase
advances when a chunk of work feels done and the next chunk has
shape. =Phase X.Y= sub-phases let one parent theme (e.g. "insight
cards" = Phase 12) ship in slices without renumbering the world.

** How to read this page

- *Status* on each phase: =shipped=, =in progress=, =planned=,
  =wishlist=. Shipped phases have a commit hash anchor; planned
  ones reference the code TODO that names them.
- *Phase numbers can have gaps* (no Phase 4, no Phase 14). When a
  chunk got absorbed into the previous or next milestone, the
  number was retired rather than reassigned.
- *Sub-phases stay open* until the parent retires; a Phase 12.6
  that's still =planned= doesn't block a Phase 13 that already
  shipped.

* Status snapshot                                              :snapshot:

- *Standing top priority:* orchestration that is *smooth*,
  *beneficial*, *faster than solo*, and *higher quality than
  solo* — all four, simultaneously. No architecture is worth
  shipping if it trades any one of those. Phase 20.x
  (full-crew LLM manager) was reverted in this session because
  it traded speed AND quality; Phase 22 (recipe injection at
  proxy time, zero extra round-trips) was accepted because it
  cleared all four bars.
- *Currently:* late beta. Core flows (index → embed → ask →
  capture → launch) are stable. Most active recent surface is
  Phase 22 v2 (manager pre-fetch + agent narrates).
- *Latest shipped (2026-05-03):*
  - *Phase 21.1 — DB-backed vault fact store (first cut).*
    New =vault_fact= table + =org_llm/vault_facts.py= with
    =register_inferrer= / =get_fact= / =get_all_facts= and
    mtime / ttl-aware invalidation. Three inferrers:
    =vault_stats= (572 files, 138 dailies, 182k nodes for this
    user), =tag_taxonomy= (top 30 tags), =routine_chores=
    (recurring chores from last 30 dailies; REJECT-first

    structured-tool_calls repair (which costs +1 cloud call).

    Second runner in =recipe_runner.py= (after
    =count_across_vault=). Manager queries =Node= + =File=
    tables directly (mirroring the inline =list_recent_nodes=
    / =recent_files= MCP tools, dedupes captains-log noise),
    injects 20 nodes + 25 files into the agent prompt, agent
    narrates with one cloud call. Ahead of the scheduled
    2026-05-17 review agent — that agent now has one fewer
    recipe to assess.

    Categorised by recipe / tool: counting, recent activity,
    tags, search, link graph, properties, orphans, agenda,
    metadata. Each prompt names the expected recipe + describes
    a passing answer + lists regression flags.
  - *Phase 22 v2 — manager pre-fetch + agent narrates.* When a
    recipe matches, the proxy executes the underlying tool
    itself (zero LLM cost), injects the result into the agent
    prompt as a compact =MANAGER PRE-FETCH= block, then lets the
    agent narrate in ONE cloud call. Tool use is enforced because
    the result is already in context — the agent doesn't have to
    "decide" to call the tool. New module: =org_llm/recipe_runner.py=
    (=_run_count_across_vault= + =format_prefetch_block=). Validated
    end-to-end: "in dailies, how many times have I made my bed?"
    → 17ms manager pre-fetch + ~6s qwen3:4b narration → "Based on
    the dailies, you've made your bed 10 times..."
  - *Phase 22.6 manager-side markdown-JSON tool-call repair.*
    When a model emits a fenced ```json {tool_calls:…} ``` block
    instead of a real tool call (the Phase 20 regression shape),
    the proxy extracts it, executes locally for known org tools,
    and returns a final assistant message — no second cloud call.

  - *Phase 22.6.1 — six new pure-python org tools.* =org_link_graph=,

- New [[file:../../extensions/opencode/src/auto-session.tsx][=extensions/opencode/src/auto-session.tsx=]] — at plugin

  the safer default for the auto-session opener.)

** 17.1j–o: slow-LLM watcher + cloud relaunch
- New [[file:../../extensions/opencode/src/slow-llm-watch.tsx][=extensions/opencode/src/slow-llm-watch.tsx=]] — watches
  =message.updated= events from outside the LLM loop. If the AI
  hasn't started responding within =sidebar_slow_llm_threshold_ms=
  (default 25s), the plugin aborts the call, runs
  =org-llm doctor --power-boost --no-diagnose= as a subprocess,
  and injects the diagnostic into chat as a permanent record.
- =sidebar_slow_llm_confirm= (default true): plugin waits for
  =/syscloud= confirmation before applying. Users can flip false
  to auto-apply once they trust the flow.
- =sidebar_slow_llm_auto_relaunch= (default true): on apply, the
  plugin spawns a detached =org-llm launch= and exits the current
  opencode. The new launch reads the stashed pending prompt and
  auto-resubmits via cloud — no manual "Ctrl+C twice + rerun."

* TODO [#A] Planned — Phase 21: deterministic vault inferrers :planned:
SCHEDULED: <2026-05-15 Fri>

Phase 20.x landed a manager pattern that consults specialist LLM
agents for things the primary doesn't know. But many of the
"things the LLM doesn't know" about the user's vault are
*deterministic* — a regex sweep + counts answers them in 10ms,
not 5-30 seconds of cloud LLM time.

The =infer_capture_style= tool (shipped with Phase 20.x) is the
first concrete instance. Generalise it: a small library of
deterministic vault inferrers + an on-disk cache + an MCP-tool
wrapper for each. Each inferrer answers ONE crisp question about
the user's vault by scanning samples and counting patterns,
caches the result keyed by directory + newest-mtime, and
invalidates only when the underlying files actually change.

** What gets inferred (concrete first list)

| inferrer                | answers                                     |
|-------------------------+---------------------------------------------|
| capture_style           | header-cookie / header-todo / bullet-cookie / plain (DONE) |
| tag_taxonomy            | most-used tags + categories the user prefers |
| date_format             | YYYY-MM-DD vs ISO vs custom in headlines/filenames |
| heading_depth           | typical max nesting in this surface         |
| priority_usage          | does the user use [#A]/[#B]/[#C]? if yes, distribution |
| scheduling_pattern      | SCHEDULED vs DEADLINE vs neither; common offsets |
| roam_link_density       | how often the user cross-links via [[id:…]] |
| filename_convention     | YYYY-MM-DD.org vs YYYYMMDDHHMMSS-slug.org   |
| capture_section_titles  | recurring level-1 categories (chores, work, …) |
| voice_register          | sentence-length distribution, formal/casual tells |
| code_language_mix       | for code corpora — top languages by file count |

Each lives as a function in =org_llm/style_infer.py= (or sibling
modules), exposed via a single MCP tool family
=org-llm_infer_<topic>(...)= so agents can call them by name
without needing to know the internals.

** Why this matters

- *Speed*: replaces "have the LLM read 3 files and infer" loops
  that cost 15-30s with sub-100ms deterministic calls.
- *Correctness*: regex+counts beat LLM "general impression" on
  yes/no pattern questions (e.g. "does the user use [#A]?").
- *Consistency*: the same inferrer answer is reused across
  agents and turns, eliminating the "scribe says it's
  header-cookie, classifier says it's bullet-cookie" drift.
- *Auditability*: every inferrer's output is just a dict of
  counts + a verdict. Easy to log to crew_log, easy for the user
  to sanity-check.

** Roll-out

*** 21.1 — Inferrer infrastructure
- Common cache path =~/.cache/org-llm/inferrer-cache.json=
  keyed by =(inferrer_name, dir_path)= → result dict.
- mtime-aware invalidation: cache entry includes the newest-
  mtime among the sampled files; mismatch = rerun.
- TTL ceiling at 24h regardless of mtime stability.
- Helper =register_inferrer(name, fn)= so adding a new one is
  a 5-line change.
- =org-llm inferrer-cache= CLI verb to inspect / clear.

*** 21.2 — Five-inferrer first cut
- =capture_style= (DONE)
- =tag_taxonomy=, =priority_usage=, =date_format=,
  =scheduling_pattern=
- Wire into existing agents: scribe (style + tags),
  triager (tags + priorities), planner (scheduling).

*** 21.3 — Aggregate: =vault_profile()=
- One MCP call returns ALL the inferrer outputs as a dict.
- Used by the org-llm primary agent's startup sequence so the
  whole crew has a shared profile of "this user's vault" by
  the time the first request lands. Refreshed lazily on
  subsequent calls.

** Open questions

1. Do we need per-directory profiles or one vault-wide profile?
   Dailies vs notes vs code corpus may have different
   conventions. Lean: per-directory with a fallback to vault-
   wide when the dir has no samples.
2. Should the inferrer cache be in =db.Config= (durable, queryable
   via dbt) or a flat JSON (faster, simpler)? Lean JSON for
   speed; dbt analytics over inferrer drift can cron-snapshot
   into the DB.
3. How to test? Sample fixtures + golden-file inferrer outputs.

* TODO [#A] Planned — Phase 19: built-in vault git-sync       :planned:
SCHEDULED: <2026-05-12 Tue>

Today users syncing =~/org/= across machines have to run their
own git wrapper (cron, magit, =git auto-commit-mode=, etc.). Make
this a first-class org-llm capability: pull on launch, commit +
push on quiescence, surface conflicts in the sidebar. Load-bearing
for the cross-machine flow, the Routines integration (=Weekly GTD
review= can only safely commit if local sync is the source of
truth), and the *org-agenda-agent* (which needs a stable on-disk
agenda to reason against).

** Roll-out in three slices

*** 19.1 — =org-llm sync= verb + launch/shutdown hooks (MVP)
- New CLI: =org-llm sync= runs =git pull --rebase= then
  =git add -A && git commit -m "auto: <slug>" && git push=
  against the configured remote/branch. =--dry-run= prints the
  diff. =--no-push= for read-only sync.
- =launch= grows a pre-flight pull (configurable via
  =git_sync_pull_on_launch=) so a freshly-opened TUI starts on
  the latest revision.
- TUI exit hook commits + pushes pending changes (configurable
  via =git_sync_push_on_exit=). Crash-safe: orphaned changes
  picked up on next launch's quiescence pass.
- Auth: reuses whatever the existing =~/org= remote uses (SSH /
  HTTPS+token / GitHub CLI). No new credential surface.

*** 19.2 — Auto-embedder daemon piggyback (steady state)
- Daemon already inspects mtimes; add a =git_sync= cycle that
  fires after N seconds of quiescence (default 30s).
- Single-flight lock: one sync at a time, no overlap with the
  embedder's own writes (the daemon DOES write the SQLite db,
  but never the org files themselves — distinct paths).
- Squash window: =git_sync_squash_within_minutes= (default 5)
  amends the most recent auto-commit instead of stacking, so the
  history stays readable.
- Backoff: rebase failures bump the next attempt by 2× up to a
  ceiling, then surface to the sidebar.

*** 19.3 — Conflict surfacing + recovery UX
- Sidebar gains a =SYNC= row: =✓ clean=, =⏳ pulling=,
  =⚠ N pending=, =✗ conflict in <path>=.
- On =CONFLICT (content)= during rebase: abort the rebase, leave
  the working tree untouched, and write a captain's-log entry +
  notify via the sidebar. The user resolves manually; sync
  resumes on the next clean pass.
- =org-llm sync --resolve= helper that opens the conflicted file
  in the user's editor (=$EDITOR= or =doom= bridge) and runs
  =git rebase --continue= on save. Optional: LLM-assisted
  three-way merge for prose-only conflicts (org headlines), gated
  by a knob.

** Config surface

| key                                | default | meaning                                                    |
|------------------------------------+---------+------------------------------------------------------------|
| =git_sync_enabled=                 | false   | master switch; off until 19.1 lands                        |
| =git_sync_remote=                  | origin  | remote name                                                |
| =git_sync_branch=                  | main    | branch                                                     |
| =git_sync_pull_on_launch=          | true    | =launch= runs =git pull --rebase= first                    |
| =git_sync_push_on_exit=            | true    | TUI exit commits + pushes                                  |
| =git_sync_daemon_quiescence_s=     | 30      | seconds of no-changes before the daemon syncs              |
| =git_sync_squash_within_minutes=   | 5       | amend window for stacked auto-commits                      |
| =git_sync_policy=                  | auto    | =auto= (commit+push) / =prompt= (ask) / =off= (read-only)  |
| =git_sync_commit_template=         | "auto: {slug}" | message template; =\{slug\}=, =\{n_files\}=, =\{date\}= placeholders |

** Open questions

1. *Embedder corpus DB* — =~/org/.cache/= and =sqlite= live
   alongside the .org files. Auto-add to =.gitignore= on first
   sync, or refuse to sync if they're tracked? (Leaning: refuse,
   with a one-shot =org-llm sync --gitignore-cache= helper.)
2. *Two-machine race* — both machines edit the same file inside
   the squash window; one wins, the other rebases. Acceptable?
   The 19.3 conflict UX should make the loser's path visible.
3. *Initial onboarding* — first-time users without a remote get a
   no-op =git_sync_enabled=false=. Walk them through =gh repo
   create --private daniel-org= during =install-tools=, or wait
   for the user to ask?
4. *opencode-write conflict* — when the LLM writes to a file
   (Phase 16.x co-edit) and the daemon syncs mid-write. Lock the
   file during LLM writes; the daemon already needs single-flight
   anyway.

** Why this is Phase 19, not a wishlist item

Three downstream features can't ship cleanly without it:
- *org-agenda-agent* (above) needs a stable on-disk agenda;
  without sync, the remote routine reads stale state.
- *Co-edit org files* (=#B=, below) wants to write back to the
  vault — sync makes those writes durable across machines without
  the user thinking about it.
- *Multi-vault federation* (wishlist) is unbuildable without
  a working single-vault sync first.

* How phases get numbered                                    :process:

- A *Phase X* is a coherent theme that ships in slices.
- *Phase X.Y* sub-phases are the slices. They land independently;
  the parent phase isn't "done" until the last slice ships AND no
  more =planned= slices are outstanding.
- *Numbers can be skipped or retired* when a chunk gets absorbed
  into a different theme. Phase 4 was absorbed into Phase 5; Phase
  14 was absorbed into Phase 15. The retired number doesn't get
  reassigned.
- *Commit messages* prefix the phase: =feat(insights): Phase 12.5 —
  engagement table=. Grep =git log --grep="Phase "= to find every
  phase landing.
- *Sub-phase numbering* is loose. 12.6 + 12.7 are reserved for
  planned work; if a 12.8 idea shows up first, it can take the
  next available number.
