#+TITLE: Cloud-or-local routing
#+FILETAGS: :wiki:concept:cloud:routing:
#+OPTIONS: toc:nil num:nil

* What it is

The decision tree =org-llm= uses to pick *where* an LLM call
runs: locally via [[https://ollama.com][Ollama]], or remotely via
a configured cloud provider (RunPod, Vast, Lambda, TensorDock,
Salad, Paperspace, CoreWeave, OpenRouter, HuggingFace, etc.).

The default is *auto*: cloud when configured AND an API key is
in =pass=; otherwise local. =--cloud= / =--local= flags override
per-invocation.

* Why this matters

Local Ollama is private, free, and limited by the host's RAM /
VRAM. Cloud is fast, sometimes higher quality, but costs and
sends prompts off-box. The right choice depends on:

- The model the call needs (does it fit locally?)
- The user's connection + cloud budget
- Whether the prompt contains sensitive content
- Whether speed matters for this verb (interactive vs batch)

Auto-routing tries to pick the right one without making the user
think about it on every command.

* The decision flow

#+begin_example
launch / ask / chat / etc. invoked
        │
        ├── --cloud flag? ──→ require cloud configured + key in pass; route cloud
        │
        ├── --local flag? ──→ route local (Ollama)
        │
        └── neither (auto):
             ├── cloud_provider + cloud_model + cloud_endpoint set in Config?
             │   AND a key exists in pass for that provider?
             │       └── YES → route cloud
             │       └── NO  → route local
             └── verbose probe failures fall back to local
#+end_example

A "hung opencode is almost always a weak local model timing out"
— so when cloud is wired up the auto path defaults to using it,
even though local is the privacy-first identity. =--local= is
always one flag away.

* Cloud provider catalog

Auto-refreshing pricing catalog at =org-llm cloud --refresh-catalog=
covers ~9 providers with FOSS / free-tier options. Each provider
entry stores:

- Endpoint URL pattern
- Model catalog (which models are available)
- Pricing tier (free / per-token / per-hour-GPU)
- Auth pattern (API key, OAuth, etc.)

The user picks one with =org-llm cloud --configure=, which
prompts for the API key, encrypts it via [[https://www.passwordstore.org][pass]], and writes
=cloud_provider= / =cloud_model= / =cloud_endpoint_url= to
=Config=.

** Groq exclusion

[[https://groq.com][Groq]] is deliberately excluded from the
catalog and providers list. Don't add it.

** FOSS-first gate (Phase 2026-05.06 — proxy expansion)

Every catalog row carries a =license_tier= field — one of:

- *foss* — Apache 2.0 / MIT / BSD-licensed weights. Truly open.
  =openai/gpt-oss-*=, =deepseek/deepseek-r1=, =qwen/qwen-2.5-*=.
- *open_weight* — redistributable weights with use restrictions
  (Llama 3 community licence, Moonshot K2 licence, etc.). Not OSI-
  approved but the user can run them locally and keep the code path.
- *proprietary* — closed-API only. Anthropic Claude, OpenAI GPT-4/5,
  Google Gemini.

The config knob =proprietary_models_enabled= (default *false*) gates
whether proprietary rows are visible to:

- =org-llm cloud --tune= recommendations
- The proxy's cloud-failover target resolver (a closed-API
  =cloud_model= with the gate off → no failover, request lands in
  the legacy 502 path)
- The =org-llm claude= subcommand (refuses to run with a clear
  message when the gate is off)

Open-weight rows are unaffected. Auto-refresh on launch keeps
classifying new OpenRouter rows by tier as they land, so users
opting in via =org-llm config proprietary_models_enabled true=
immediately see the next-flagship Claude / GPT release without a
manual refresh.

The catalog still SHIPS proprietary rows and the auto-refresh keeps
them current — opting in is one flag, not a re-fetch. We considered
splitting into separate catalog files but the metadata-tag approach
keeps the data model simple and lets the gate move freely both
directions.

* Hardware-aware fallback

Even with cloud configured, =org-llm= probes local hardware
before routing local — RAM check (does the chat model fit in
free RAM with a generous safety margin?) + VRAM check (is a GPU
available with enough headroom?). When both checks fail and
cloud is configured, it routes cloud automatically (=power_boost=).

* Cloud-first bypass (=proxy_cloud_first=)

When the user knows local hardware can't realistically serve
their =chat_model= (low free RAM, no GPU, thermal throttling),
=proxy_cloud_first=true= skips the local upstream entirely on
chat completions — every request routes directly through the
cloud-failover machinery. Saves the per-request
=proxy_first_byte_timeout_ms= wait that would otherwise
preempt every cold local attempt.

Onboarding step 6c offers this automatically when free RAM
falls below 1.2× the configured =chat_model='s estimated
footprint AND a cloud provider is configured. Toggle manually
any time:

#+begin_src sh
org-llm config proxy_cloud_first true
org-llm config proxy_cloud_first false   # back to local-first
#+end_src

The two cloud paths are distinguishable in the audit log
(=intercepted_by= field): =cloud_first= for the bypass path,
=cloud_failover= for the TTFB-triggered retry. Both inherit the
context-overflow retry chain — when a cloud free-tier model
rejects with =400 context length=, the proxy retries with
=cloud_failover_compressed_tools= (descriptions trimmed,
schemas stripped — drops a 64-tool MCP inventory from ~19k →
~3k tokens), then falls back to =cloud_failover_no_tools=.

Net user-visible impact on RAM-constrained hardware: a
tools-using prompt drops from ~40s end-to-end (30s local stall
+ 10s cloud) to ~9.5s direct.

* Provider config in opencode

The =org-llm launch= flow writes BOTH providers (Ollama + cloud)
into =.opencode/opencode.json= when cloud is configured. opencode's
in-session model picker can switch between them without re-launching.
=use_cloud= only decides which one is the DEFAULT (the top-level
=model= field).

* How to configure

** Env vars
- =ORG_LLM_CLOUD_PROVIDER= — override the provider per-invocation
- =ORG_LLM_CLOUD_MODEL= — override the model
- =ORG_LLM_CLOUD_ENDPOINT_URL= — override the endpoint
- =ORG_LLM_PASS_PREFIX= — directory under =pass= for keys
  (default =org-llm/=)

** CLI flags
#+begin_src sh
# Configuration
org-llm cloud --configure                # interactive picker
org-llm cloud --providers                # list configured providers
org-llm cloud --refresh-catalog          # update pricing data
org-llm cloud --test                     # round-trip ping the configured cloud

# Per-invocation routing
org-llm ask "..." --cloud                # force cloud
org-llm ask "..." --local                # force local
org-llm launch --cloud                   # opencode workspace, cloud-default
org-llm launch --local                   # privacy-first
org-llm launch -n                        # dry-run; key is REDACTED in output
#+end_src

** Conversational
- Inside opencode: switch the active model via the model picker
  (Ctrl+M); both providers are listed.
- Natural language: "switch to cloud" / "use local for this" —
  the model can call =set_config= against =default_route=
  (planned; today the user re-launches with the flag).

** Permissions
- =launch --cloud= writes the API key into
  =.opencode/opencode.json= which is chmod'd =0600=. Don't
  commit this file; the launch flow writes it to a vault-relative
  path that should be in =.gitignore=.
