no broker was ever selected because OpenRouter rejected the request at
the model-validation layer.

* 4. K2 max_tokens=4096 — did it apply?

*No.* The constant is dead code.

#+begin_src python
# /home/daniel/repos/org-llm/scripts/_round25_dials.py:245
_R25_VARIANT_MAX_TOKENS = {
    "K2-kimi-k2.6": 4096,
    "K15-kimi-thinking": 4096,
}
#+end_src

~grep -n _R25_VARIANT_MAX_TOKENS scripts/_round25_dials.py~ returns
*one* hit — the definition. No reader exists. The downstream call site
=run_specialist_for_cell= (line 1084) builds ~SpecialistTask(...)~ with
no ~max_tokens~ field; ~SpecialistTask~ in =org_llm/specialist.py= does
not accept max_tokens at all (it's a fixed default in the
~_chat_completions~ helper at line 531 = 8000).

*Evidence the cap did not fire.* K2 events show 11 iters with
~finish_reason=length~ and ~final_text_chars~ values 22,646 / 24,251 /
24,987 / 25,365 / 25,990 / 26,091 / 26,160 / 26,492 / 26,536 / 26,879 /
27,727. At Kimi's ~3.5 chars/token these correspond to ~6,500–7,900
output tokens — consistent with the 8000 default ceiling, not 4096. If
the 4096 cap had fired we would expect ~14k chars per length-iter.

*K2 score: 486 across 50 cells, despite the leak.* K2 still placed
second on the leaderboard. The runaway-prose failure mode hurts
specific cells but the variant's overall quality is high enough that
"fix the cap" is a tail-improvement, not a save.


* 5. WALL_CAP analysis

16 ~WALL_CAP_KILLED~ events in stdout.log. *All* are K2-kimi-k2.6 on
B1 (the literate-tools.org wiki entry). Timestamps span 19m45s
(10:47:37 → 11:07:22) — that's ~5 K2 cells per minute hitting the
400s wall during the K2 burst. With ~_R25_VARIANT_BUDGETS K2-kimi-k2.6:
n=50~ and a B1 cell that prints heavy prose, the wall cap is doing
load-bearing work; without it, R25 would still be running.

*Reading.* The K2 wall-cap kills are the *symptom* of the missing
max_tokens cap. The Kimi model gets stuck producing 25k-char prose
dumps inside the iteration loop; with finish=length forcing a re-call
at iter+1 still un-toolcalled, it loops until the harness wall-cap
kills it. Wiring the 4096 cap (§4 fix) should drop wall-cap hits
toward zero.


* 6. R26 advisory — concrete routing changes

Top-5 actionable, ranked by expected delta:

1. *Wire the K2 max_tokens cap.* This is the highest-leverage R26
   change. Add ~max_tokens: Optional[int]~ to =SpecialistTask=, thread
   it through =_chat_completions= (override default=8000), and read
   ~_R25_VARIANT_MAX_TOKENS~ in =run_specialist_for_cell=. Expected
   effect: 11 length-iters → ~0; wall-cap hits 16 → ~0–2; K2 cost-per-
   cell drops ~30% (less wasted output tokens).

2. *Modal-Kimi route for K2.* Set ~MODAL_KIMI_ENABLED=1~ in R26 launch
   env. Modal vLLM has deterministic ~max_tokens~ via the OpenAI-style
   payload, sub-second TTFT, and bypasses Parasail's runaway-prose
   path entirely. The infra is already in place (line 254–255). Pair
   with the §1 cap as belt-and-braces.

3. *Drop K34 and K35 OR fix the model slugs.* Both are net-negative —
   one wasted cell + one wasted warmup probe each, score=0. Either:
   (a) replace K34 with a working DeepSeek-V3 chat slug (e.g.
   =deepseek/deepseek-chat-v3-0324= already proven by K8, so K34
   becomes redundant), and K35 with the live llama-3.1-405b OpenRouter
   slug; OR (b) drop both from ALL_VARIANTS until a verified large-FOSS
   slug list exists. Recommend (b) for R26 unless the specific large-
   FOSS test is load-bearing — K33 alone covers the 480B Qwen3 case
   (with the renaming caveat below).

4. *Rename K33 — it's not 72B.* The variant ID =K33-qwen3-coder-72b=
   maps to OpenRouter slug =qwen/qwen3-coder= which Together serves as
   a 480B-A35B MoE (same as K11). Either rename to
   =K33-qwen3-coder-480b-tools-on= (with a real dial difference vs
   K11 — e.g. tool_surface or temperature) or drop as a duplicate.
   The R25 single-cell score=12 cost=$0.71 vs K11 cost=$0.0 (errored
   on B1) is not a meaningful comparison.

5. *K17-glm46 — re-pin or drop.* SiliconFlow served 10/10 (deny held)
   but produced 9/10 max_iters loops. *The model is the problem*, not
   the broker. R26 options: (a) drop K17 from ALL_VARIANTS — GLM-4.6
   has now produced loops on DeepInfra (R24) and SiliconFlow (R25)
   without a known healthy alternate; (b) try a third broker (Z-AI is
   denied; Novita serves z-ai/glm but never observed; Atlas/Together
   don't list GLM-4.6); (c) cap iterations to 8 specifically for K17
   to bound loss. Recommend (a) until the loop pattern is understood.
