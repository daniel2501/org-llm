#+TITLE: R17 wall-time + parallelism analysis — input to R18 tuning
#+AUTHOR: Claude
#+DATE: 2026-05-08

* TL;DR

- Real wall: *1110.7 s = 18.51 min* over 59 cells, $4.4488.
- Sum of cell walls: 2255.3 s. Achieved parallelism *2.03x* of ideal 8x → efficiency *25.4%*.
- The single dominant cause is one long pole: *K15-kimi-thinking on B1 took 756.1 s = 12.6 min*. It alone defines the layer1 critical path and pushes the whole run from ~9 min to ~19 min.
- Adaptive abort fired in *5 cells*; all five had score=0 — *no false positives detected*.
- *3 cells dodged adaptive abort* via the K7-thrash pattern (failed-edit attempts reset silent_streak). Worst is K11-qwen3coder/B11/layer2: *171.6 s, 15 iterations, 10 consecutive failed edits, 13 self-correction nudges, 1 successful edit*.
- Three concrete R18 levers: *(a)* fail-edit-streak abort, *(b)* per-cell hard wall cap, *(c)* never co-schedule a known thinking model with downstream-blocking layers.

* 2. Parallelism efficiency

Layer wall times come from the run log timestamps; cell wall is from
=cell_result.json::specialists[i].duration_seconds=.

#+CAPTION: Parallelism efficiency by layer (8-way ThreadPoolExecutor)
| layer  | wall (s) | sum cell wall (s) |    n cells | achieved x | efficiency | bottleneck                      |
|--------+----------+-------------------+------------+------------+------------+---------------------------------|
| layer1 |    794.0 |            1074.2 |         15 |       1.35 |      16.9% | K15-kimi-thinking (756.1 s)     |
| layer2 |    191.0 |             562.0 |         28 |       2.94 |      36.8% | K11-qwen3coder B11 (171.6 s)    |
| layer3 |    126.0 |             431.2 | 12 (6×2)   |       3.42 |      42.8% | K1-qwen30 B1 d8_min (121.6 s)   |
| TOTAL  |   1110.7 |            2255.3 |         59 |       2.03 |      25.4% | layer1 long pole dominates      |

- Layer1 burns 794 s of which 756 s = K15 alone. With K15 dropped, layer1 wall would compress to ~135 s (next longest = K2-kimi-k2.6 errored cell or 73.8 s = K17-glm46). *Counterfactual whole-run wall: ≈8.7 min instead of 18.5.*
- Layer2 efficiency (36.8%) reflects the K11-qwen3coder thrash holding one slot for 171 s while 27 other cells finish in ~100 s of work.
- Layer3 is six sub-batches of 2 cells, run sequentially per-dial. Each sub-batch is 2-cell × 8-worker = trivially parallel; the bottleneck there is *batch sequencing*, not parallelism.

* 4. Adaptive abort effectiveness

Detection rule: cell terminated with final =silent_streak >= 2= *and*
=edits_applied_count == 0=.

| variant         | layer           | task | wall (s) | iters | score | verdict       |
|-----------------+-----------------+------+----------+-------+-------+---------------|
| K1-qwen30       | layer2          | B7   |     10.8 |     4 |   0.0 | true positive |
| K1-qwen30       | layer2          | B5   |     12.9 |     3 |   0.0 | true positive |
| K11-qwen3coder  | layer2          | B7   |     12.9 |     4 |   0.0 | true positive |
| K1-qwen30       | layer3_d6_tool  | B1   |      8.0 |     4 |   0.0 | true positive |
| K11-qwen3coder  | layer3_d6_tool  | B1   |      6.7 |     4 |   0.0 | true positive |

- *5 fires; 0 false positives* (no aborted cell scored >0).
- Total wall saved: aborted at ~10 s each instead of running to default
  iteration cap (~20-iter safety) → roughly *50–100 s saved* across these 5
  cells. Modest in absolute terms; valuable as a guardrail.

The abort is *under-tuned*, not over-tuned: it never fires when the model is
actively making (failed) edits. See section 5.

* 6. R18 adaptive-abort + parallelism recommendations

** 6a. New abort triggers (replace silent-only rule)

Replace the single =silent_streak >= 2 AND edits == 0= rule with a
disjunction of three:

#+CAPTION: Proposed R18 abort triggers
| trigger | rule                                                         | rationale (R17 fit)                                                   |
|---------+--------------------------------------------------------------+-----------------------------------------------------------------------|
| A       | =silent_streak >= 2= AND =edits_applied == 0=                | keeps R17's 5/5 true-positive guardrail                              |
| B       | =consecutive_failed_edit_iters >= 3= regardless of edits     | catches K11/B11 (would fire at iter 4–5, saving ~140 s of 171 s)     |
| C       | =self_correction_nudges >= 5=                                | redundant but cheap signal; K11/B11 had 13                            |
| D       | =wall_seconds >= per_cell_hard_cap=                          | catches K15-class thinking-model stalls if the model is non-essential |

Trigger B is the new primary lever. The R17 instrumentation already emits
=tool_result.ok=False= and we can derive consec_failed_edit_iters from
existing =iter_total_edit / iter_failed_edit= counts.

** 6b. Per-cell hard wall cap

#+CAPTION: Proposed wall caps by model class
| model class                     | wall cap (s) | precedent                              |
|---------------------------------+--------------+----------------------------------------|
| thinking (K15)                  |          240 | iter 1 alone was 354 s in R17 — costly |
| frontier non-thinking (K2, K8)  |          180 | covers p99 (135 s) with headroom       |
| efficient (K1, K11, K17, K19)   |           90 | covers p99 (~50 s) with headroom       |
| any                             |          300 | absolute global ceiling                |

A 240-s cap on K15-kimi-thinking would have killed it after iter 4
(produced 4/5 edits, saved 432 s = 7.2 min). Run wall would compress from
18.5 min → ~11.3 min (saving ~40%).

For R18, recommended default: *180 s soft cap, 300 s hard kill, with
per-variant overrides for thinking models*. Under no circumstances let any
single cell hold a worker for >5 min.

** 6c. Hedged retry strategy for HTTP errors

R17 saw very few HTTP errors emitted (1× warmup 504, embedded 429/5xx in
tool obs). The proxy is already retrying silently. For R18:

- *Per-API-call timeout*: 90 s hard. p99 normal iter is ~60 s; 90 s is
  pessimistic. On timeout, fire one hedged duplicate request to the same
  provider; whichever returns first wins.
- *Provider rotation on consecutive timeouts*: if the same provider hits
  3 consecutive timeouts in a worker thread, mark it cold for 60 s and
  route to fallback (OpenRouter auto-route).
- *Surface retry events*: emit an =api_retry= event into events.jsonl so
  R19 can re-mine without log-grepping.

** 6d. Parallelism — schedule the long pole first

The single biggest wall lever is *not* abort tuning, it's scheduling:

- *Identify thinking / slow models pre-run* (K15, K2 in R17 setup).
- *Submit them at t=0 of layer1*, before the cheap-fast variants.
- Better: run K15 in a *pre-warm side-pool* concurrently with the
  layer1 tournament. The K15 result is just one row in the leaderboard; it
  doesn't gate layer2 unless K15 wins (it didn't — score=10).
- *Skip K15-kimi-thinking from layer-promotion eligibility entirely* — it's
  too expensive in wall to be a stability candidate even if it scores well.

A two-line change to the layer1 submit order (long-pole-first) plus a
240-s cap on the K15 worker would have brought R17 from 18.5 min to
~11 min without changing any quality output.

** 6e. K11-qwen3coder special case

K11-qwen3coder is *not* uniformly slow (median 16.3 s). It's a *bimodal
risk*: most cells fast and productive, but tail-heavy when its edit format
hits a guardrail it can't recover from. Recommendation:

- Apply trigger B (consec_failed_edit_iters >= 3) — this catches K11/B11.
- Keep K11 in the routing pool; the median is competitive.
- File a follow-up on the APPEND-ONLY guardrail wording — the model never
  understood "0 deletion lines" after 13 nudges, suggesting the nudge text
  itself needs revision.
