# AGENTS.md — primer for agent runtimes opening this repo

This file is auto-loaded by opencode, Claude Code, Cursor,
Codex, and similar agent runtimes when they open the org-llm
repository. It exists to orient an agent in one read, then hand
off to the org-mode wiki for substance.

> Org-native first: this `.md` is a cross-tool surface
> ([`docs/wiki/decisions.org`](docs/wiki/decisions.org) DEC-002).
> Everything durable lives in `docs/wiki/*.org`.

## Two `AGENTS.md` files — naming overlap

This project has **two** files named `AGENTS.md`:

- **`/AGENTS.md`** (this file) — the durable, version-
  controlled primer that cross-tool agent runtimes (opencode,
  Claude Code, Cursor, Codex, etc.) auto-load when they open the
  repository. Same content for everyone; tracked in git.
- **`.opencode/AGENTS.md`** — generated by `org-llm launch` on
  every session; opencode auto-loads it. Vault-specific and
  dynamic (current model, sidebar state, etc.); not tracked.

The two don't conflict — they're loaded by different tools at
different lifecycles, and they orient agents at different
layers (project-shape vs. runtime-shape). When in doubt,
you're reading the right one if it's at the repo root. A
formal DEC entry on this overlap is queued for
[`docs/wiki/decisions.org`](docs/wiki/decisions.org).

## What this project is

**org-llm** — "Claude Code for Org Mode." An agent-driven life-
management toolkit built on org-mode + Emacs + a FOSS LLM stack
(Ollama, sqlite-vec, MCP). Multi-agent, vault-grounded, opinionated.

For the full picture, read
[`docs/wiki/00-index.org`](docs/wiki/00-index.org) — concept map
across embeddings, RAG, MCP, the LLM proxy, the agent roster, and
more.

## Coordinate before you touch — non-negotiable

This repo is developed concurrently by multiple humans and
agent instances. Before your first `Edit` / `Write`:

1. **Read** [`docs/wiki/coordination.org`](docs/wiki/coordination.org)
   in full. Four rules: claim before touch, one branch per
   logical arc, re-Read before Edit, no silent wiki edits.
2. **Claim** by appending a `STARTED` heading under "Active
   claims" in
   [`docs/wiki/active-claims.org`](docs/wiki/active-claims.org)
   identifying yourself, your files, your branch, and start time.
3. **Close** by flipping `STARTED` → `DONE`, adding a `:CLOSED:`
   timestamp, and moving the entry to "Recently closed".

Stale claims (>4h, no commits/updates) are subject to announced
reclaim — see coordination.org.

## Style rules that apply to your edits

- **Re-Read before Edit.** Always. Parallel streams invalidate
  earlier snapshots.
- **Edit > Write.** Diff-based edits are concurrent-safe; whole-
  file overwrites silently clobber.
- **Summary + Expanded** on every new wiki concept page (Rule 2b).
- **File-link mentions** for every in-repo path in wiki/org
  output (Rule 2a). Helper:
  `org_llm/logbook.py:org_file_link()`.
- **Announce wiki edits** in conversation/commit/PR. Always.
- **Branches:** `<who>/<slug>` off `main`. Don't share branches.
  PR target is `main`.
- **Decisions:** if your change embeds a directional choice,
  add a `DEC-NNN` entry to `docs/wiki/decisions.org` in the
  same PR.

## Quality gates (apply before declaring done)

Every change is tested against three gates (see
`docs/wiki/architecture.org` for the longer form):

1. **Really good at the job.** The change does what it claims.
2. **Not too complex.** Cost is justified.
3. **Manages required complexity well.** Whatever complexity is
   load-bearing is well-shaped.

Plus the project-side discipline:

- Typecheck/build/dry-run *yourself* before asking a human to
  visually verify. Don't punt verification.
- Update `docs/wiki/now.org` if the change is user-visible.
- Update `docs/wiki/dev-tracker.org` if the change closes a
  tracker entry (eventually `@riker` will own this; manual
  for now).
